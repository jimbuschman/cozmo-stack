## Decisions (the manager's, recorded for audit)

- **MD1: layer ownership.**
  - M5 owns everything in the streamer and TrackLayerComponent: the live idle, keep-alive, blinks, darts, glitch and the idle stack.
  - M7 owns what calls or configures them: PushIdle/RemoveIdle callers, the Hiccup timeout, the DesiredFaceDistortion degree and behaviour eye shifts.
  - M8 owns PlayAnimationAction's tag handling (A26).
  - M9 owns the custom song (A7). M6 owns Wwise audio.
- **MD2: OpenCV.**
  - The four functions the engine uses (fillConvexPoly LINE_4, ellipse2Poly, warpAffine INTER_NEAREST, resize INTER_LINEAR) are ported from stock OpenCV 3.1.0. The shipped build was compared against stock on the engine's paths and matches (gap3).
  - Rounding assumes the default FPSCR mode, round-to-nearest-even. No VMSR write exists in the engine or OpenCV libraries; other in-process libraries were not checked.
  - M3-018's resize claim now rests on gap3 D1..D7.
- **MD3: the four shipped JSON clips** (ANIMATION_TEST, anim_qa_firmwaremessaging_01, anim_triple_backup, soundTestAnim) are loaded like any other clip. That is the engine behaviour.
- **MD4: continuous keep-alive streaming** (M5-028) is the engine behaviour and is reproduced. It streams a FaceImage every 33 ms while idle. The robot's handling is HARDWARE_ONLY (M5-036), and the next hardware run records it.

#### The findings that change the most

1. **Abort does send the robot something.** When the streamer's tag (+0xA0) is non-zero, `Abort` broadcasts the engine-to-game (E2G) message AnimationAborted{tag}. `RobotEventHandler` subscribes to that E2G tag (95), and the broadcast is delivered synchronously, so its handler calls `Robot::AbortAnimation`, which sends **AbortAnimation 0x8D** reliably. This contradicts M5-023.
2. **The backpack-lights track is loaded and streamed.** `Animation::DefineFromFlatBuf` does not call the stub. It converts each FlatBuffer BackpackLights table to JSON and loads it with `SetMembersFromJson`. The shipped clips have 7140 such keyframes in 111 files. While one is active, **BackpackLights 0x98** is sent every stream frame. This contradicts M5-016.
3. **Sprite face frames have two variants.** Each frame is stored twice, once with the even rows cleared and once with the odd rows cleared. `GetFrame` picks one by `_firstScanLine`. M5-013 describes a single variant, which is incomplete or wrong.
4. **`~Robot` sends before the streamer is destroyed.** It calls `AbortAll`, which sends AbortAnimation 0x8D and runs StopAllMotors. M5-022 says nothing is sent.
5. **The streamer never looks at enabledAnimTracks (robot+0x348).** The only reader is the debug viz. Track locking is left to the firmware. Only the live idle checks MovementComponent locks.
6. **StartOfAnimation is not the first message.** It is buffered after the first frame's AudioSample/AudioSilence.

#### Findings that change the most

1. **The dart and the eye shift share a generator, but the per-shift limits are thrown away.** The first `GenerateEyeShift` overload (0x0058CFC4), used by `AddOrUpdateEyeShift` (LiveIdleTurn, TurnInPlace, ITrackAction), overwrites the caller's xMax and yMax with values computed from a default face's bounding box. The effective limits are always 17 and 12. The "64/32" in M5 A35 is never used. The M7-007 statement that 0x0058CFC4 "clamps the shift against the bounding box" misreads this function, and it is also the wrong overload for the dart.
2. **The first keep-alive dart does not ramp in.** `KeepFaceAlive` creates the `KeepAliveEyeDart` layer with a single keyframe whose trigger equals the duration, and no neutral keyframe at 0. That layer contributes nothing until the trigger, then jumps to the shift. Only later darts (added with `AddToPersistentLayer`) interpolate. This partly contradicts M7-007 ("ramps to its gaze").
3. **A persistent layer holds its last keyframe; it does not repeat.** When its iterator reaches the end, every keyframe before the last is erased, the iterator is placed on the last keyframe, and the layer's stream time is put back by one frame. After that the layer re-applies the same face every frame. Removal cross-fades from the *current keyframe* (not the interpolated face) to the neutral face over the given duration, on a new non-persistent layer.
4. **One bad keyframe truncates a clip; it does not remove it.** The load stops at the first failing keyframe. Earlier tracks, and the keyframes already added to the failing track, stay. The half-built clip stays in the container under its name, and the loader ignores the error.
5. **Clips load from `assets/animations/` and `config/engine/animations/`, on 4 workers.** Each directory is listed with readdir and no sort. Loading runs on 3 threads plus the calling thread, in contiguous chunks, under one mutex. The cross-file order of definition is therefore not fixed by the binary. The shipped `.bin` files contain no duplicate clip names (997 unique).
6. **Blink: 7 table frames plus a restore keyframe.** Triggers are 33, 66, 99, 132, 165, 198, 298 and 331. Frame 4 flips `_firstScanLine` at generation time, not at display time. The older "seven-frame squash" note is right about the scale table.
7. **The interlace offset moves the eye polygons, not only the cleared rows.** `DrawEye` adds `_firstScanLine` (0 or 1) to the y of every transformed eye-polygon point.

**What was not compared.** These are libopencv_core helpers:
- _InputArray/_OutputArray getMat and create;
- Mat::clone and Mat::convertTo (warpAffine's M copy; float → double and double → double are exact in stock);
- parallel_for_ over TBB. The invoker code I read makes every output pixel/row independent of the partition, so the split cannot change results.

The linear/cubic branches of warpAffine, and LineAA/Line2, were not diffed beyond their dispatch, because the engine doesn't use them. With these exceptions, all four functions are fully diffed for the engine's parameters, and **no difference from stock 3.1.0 was found**. Whatever "-dirty" changed, it is not in these paths.

##### Existing records contradicted by the source
- **M5-021** (EQUIVALENT_IMPLEMENTATION, "even-odd scanline fill equals the left-chain/right-chain fill"). The shipped fillConvexPoly **also draws every edge with a 4-connected LineIterator line before the fill** (A4/A8/A9). It then fills [(x1+0x8000)>>16, (x2+0x8000)>>16] from 16.16 edges stepped by a truncating-division dx (A6/A7). The record's evidence doesn't cover either behaviour, so its equivalence argument doesn't hold as written. The source is now fully recoverable from A1–A10.
- **M5-gap2 Q1.11 remainder**: the "neutral face assumed" gap is settled (K4/K5). It is the raw default face, not `_resetData`.

##### Records whose evidence is too weak to keep their status
- **M3-018**: the claim "exact for the 160→320/240→240 case on every OpenCV path" is now supported by D1–D7, which show the NEON path is the one taken on the device and equals the C path. The record should cite these addresses rather than assert it.

##### Open questions
1. FPSCR rounding mode at run time: default RN (ties to even) is assumed. Only the three libraries were scanned for VMSR, so an FPSCR change elsewhere in the process is HARDWARE_ONLY / unverified.
2. The engine-side type of warpAffine's M matrix (CV_32F or CV_64F) was not re-read. Either way convertTo to double is exact in stock, but core's convertTo was not diffed.
