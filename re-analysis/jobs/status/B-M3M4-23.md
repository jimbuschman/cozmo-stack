## Production path and bounded correction

The host vision worker owns UpdateObservedMarkers' FrameGate and its +0x74 append window. Robot-message/engine/action paths include lift attach/release, moved/stopped cubes, origin migration, connection changes, forgetting, and markerless insertion. They previously could update the world or BroadcastObjectPoseChanged while that other frame had the flag set. They now acquire the same reentrant frame gate before any object lock; engine docking, Delocalize and ComputeLiftPose acquire it before robot PoseTreeGate. LiftPose is a shared parent of carried objects, so its indirect world-pose write is included.

Source recheck: 0x004ED62E is specifically RobotManager::UpdateRobotConnection, followed by UpdateAllRobots at 0x004ED648 (which calls Robot::Update at 0x0052F6E4). It is not a direct vision function call. This confirms the checked single-engine-thread scheduling boundary; no new native helper behavior was inferred from the row's shorthand. This job adds host serialization, not a native mutex or a new thread.

The flag itself is unchanged: successful frames clear it at the native tail; a failed AddAndUpdateObjects still leaves it set as before. Guards do not invent a clear on failure. Existing in-frame recursive mutation remains allowed on the owning thread.
