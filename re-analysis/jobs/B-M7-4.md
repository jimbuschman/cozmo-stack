**Today:** `FreeplayStack.cs:169` creates the manager, so a SevereNeeds Set before Freeplay (for example the
automatic wakeup at connection) skips DisableReactionsWithLock with a visible MISSING.

**The engine** constructs the manager in the Robot constructor:
- ctor at 0x0050FCAC, stored at robot+0x44 (0x0050FCB0);
- InitConfiguration (0x00510388) and InitReactionTriggerMap (0x00510396) run inside the same constructor, before
  AIComponent::Init (0x005103DC);
- it is destroyed with the robot (0x00511126..0x0051112C).

Locks taken while the map is empty are not saved: DisableReactionsWithLock returns at 0x005A2824.

1. **Create one manager per native robot,** when the stack builds the native robot. Destroy it when that robot is
   destroyed. A reconnect gets a fresh manager with no locks.
2. **Populate its reaction trigger map at that point,** from the shipped config, in the existing registration order.
   - Where a reaction behaviour needs an input that exists only inside FreeplayStack (vision locator, manipulation,
     whiteboard), bind it when Freeplay supplies it. Don't drop the trigger entry; lock state lives on the entry.
   - If an entry can't be created before Freeplay, report a visible MISSING naming it. Don't invent a placeholder.
3. **FreeplayStack uses the robot's manager** instead of creating its own. Its Dispose must not destroy the manager or
   clear locks: native locks persist until removed or until the robot is destroyed.
   - `ManipulationSystem.ReactionLocks` and the SevereNeeds DisableReactions/RemoveReactions recipients bind to the
     robot's manager from robot construction.
   - Remove B-M15-12's "reaction recipient absent outside Freeplay" MISSING.
4. **Everything else stays the same:** what DisableReactionsWithLock and RemoveDisableReactionsLock do, the tables,
   and the current behaviour switching. Locks on existing entries keep their per-trigger semantics.
5. **Tests** (label reach, give the old value, show each fails on the old code, dispose everything):
   - automatic wakeup with Repair Critical before any Freeplay stack: the reaction lock is applied to the real entries
     (old: MISSING and no lock);
   - the lock survives creating and disposing a FreeplayStack;
   - robot destruction drops the manager, and a reconnect starts with no locks;
   - the existing reaction and behaviour tests still pass.
