# M8-framework gap 1 extraction: the IAction timeout and the BehaviorHelperComponent helper stack

- Job: R-BEH (M8-framework), gap pass 1.
- Date: 2026-09-29.
- Kind: read-only extraction. Evidence is instructions in `resources/lib/armeabi-v7a/libcozmoEngine.so` (ELF ARMv7/Thumb). `re-analysis/decomp/libcozmoEngine/` was used only to navigate; its addresses were checked against the `.so`.
- Scope: Q1, the M8-008 correction (does `CalibrateMotorAction` have a timeout?); Q2, the M8-011 gap (`BehaviorHelperComponent::DelegateToHelper` and the helper-stack runtime).
- Conventions: symbols carry no Thumb bit. A vtable slot value with bit 0 set is a Thumb pointer; the instruction address is that value with bit 0 cleared. `this` is r0 on entry. The IAction vtable is the symbol `_ZTVN4Anki5Cozmo7IActionE` = 0x010214a0 (GOT entry 0x103eb20); the stored vptr is symbol+8 = 0x010214a8. The CalibrateMotorAction vtable is `_ZTVN4Anki5Cozmo20CalibrateMotorActionE` = 0x01021944 (GOT entry 0x103eb48); stored vptr = 0x0102194c. Ghidra renders both vtables at +0x10000; the relocations above are the correct values.

**Q1 verdict: `CalibrateMotorAction` HAS a timeout, 30.0 seconds.** It does not override the slot, so it inherits `IAction`'s default vtable[+0x2c] thunk at 0x0052b0c2, which returns 0x41f00000 (30.0f). `IAction::UpdateInternal` arms +0x74 on the first update (the -1.0f from the constructor is only the "not started" sentinel) and fails the action at start+30 s with 0x03000018. `CheckIfDone` 0x00547d38 only tests `Robot::IsHeadCalibrated` (0x004a9a18) / `Robot::IsLiftCalibrated` (0x004ab14c) and returns 0x01000000 until both requests are satisfied; after 30 s it is not consulted again. The policy review's "no timeout" is wrong; the verifier is right.

Note: M9-002 already records this same `IAction::UpdateInternal` mechanism at 0x00540D1C (60 s per-step for `TriggerAnimationAction`). M8-008 contradicts that sibling record's evidence.

## Existing records

**Contradicted by the source**

- **M8-008** (COMPATIBILITY_POLICY, M8-framework). Current title: "The head recalibration wait: the engine has no timeout, this stack keeps a backstop". Its evidence says "There is no timeout behind it. IAction's constructor writes -1 to the action's timeout at +0x74 ... which is the engine's 'no timeout', and CalibrateMotorAction does not override it. So the engine waits as long as it takes." The source contradicts this: the -1.0f is a sentinel (Q1.2), the deadline is start + vtable[+0x2c] (Q1.3), CalibrateMotorAction inherits the default +0x2c = 0x0052b0c2 = 30.0f (Q1.6, Q1.8), and the timeout fires with 0x03000018 (Q1.4). The record's title, evidence and effect need correction; the stack's `CalibrationAllowanceSec = 5.0` is the wrong value (30 s) and it must fire a timeout result, not just carry on.

**Evidence too weak to keep the status**

- **M8-008** as above: its citation 0x00540C44 is the constructor only, and it never read `IAction::UpdateInternal` 0x00540D1C. It should be corrected (and, if the timeout is to be rebuilt, moved to IMPLEMENTATION_GAP).
- **M8-011**: not contradicted, but its last evidence paragraph already says the component and stack runtime are unowned; this report supplies them. The manager decides whether they become a new M8 record or an extension of M8-011.

**Consistent**

- **M9-002** (EXACT_SOURCE) records the same `IAction::UpdateInternal` timeout at 0x00540D1C for `TriggerAnimationAction`'s 60 s per-step timeout; it is consistent with this extraction and should not change.
- **M8-011**'s description of `SmartDelegateToHelper` matches the disassembly.

## UNKNOWN (what I could not establish)

1. **BehaviorHelperComponent +0x44**: four tail bytes; not written by the constructor and not read by any BehaviorHelperComponent function read here. UNKNOWN whether it is a field or padding.
2. **The C++ name of the default vtable[+0x2c] thunk** at 0x0052b0c2: the vtable slot points to an unnamed local function. Its behaviour (returns 30.0f) and its use as the timeout are settled; the method name is not in the symbols.
