### Corners and arithmetic before projection

Use physical array indices P0..P3, not a guessed clockwise polygon. Static initialization at `0x004DD7D8..0x004DD81C`, with the four-point constructor `0x004E9636..0x004E9696`, establishes the canonical physical array:

`P0=(-.5,0,+.5), P1=(-.5,0,-.5), P2=(+.5,0,+.5), P3=(+.5,0,-.5)`.

`Get3dCorners` `0x0087E2E8..0x0087E34C` copies those 48 bytes, multiplies each x by marker width (+0x10), each z by marker height (+0x14), and applies the supplied pose transform. Multiplication is f32. `Transform3d::ApplyTo` `0x0050343C..0x00503524` processes corners in order **0,2,1,3**, preserving their physical slots. Rotation3d's stored four f64 quaternion components are individually converted to f32 at `0x0084ACA6..0x0084ACE4`; the point rotation is then entirely separate f32 products/additions/subtractions at `0x00849C1C..0x00849CFA`. Each translated coordinate is **translation + rotated coordinate**, rounded to f32. There is no normalization or finite-value gate in these two bodies. This is not a double-precision matrix projection.

For exact rotation scheduling, in the quaternion body let q=(w,x,y,z), p=(X,Y,Z), `A=w*w-x*x`, `B=w*w+x*x`, and double each cross product by `t+t` in f32. The outputs are:

`rx = (2*(w*y)+2*(x*z))*Z + (((B-y*y)-z*z)*X + (2*(x*y)-2*(w*z))*Y)`;

`ry = (2*(y*z)-2*(w*x))*Z + (((A+y*y)-z*z)*Y + (2*(x*y)+2*(w*z))*X)`;

`rz = ((A-y*y)+z*z)*Z + ((2*(x*z)-2*(w*y))*X + (2*(w*x)+2*(y*z))*Y)`.

Here `2*(...)` denotes the native duplicate-add of the already rounded product, not multiplication by a double literal; each parenthesized binary operation is separately rounded. The point input is not converted to f64. The preceding pose-tree transform construction is a dependency of the pose subsystem, not newly recovered by this report.

KnownMarker computes `u=P2-P0`, normalizes it, then `v=P1-P0`, normalizes it (`0x0087E548..0x0087E59C`). Normalization `0x0050E0C0..0x0050E138` computes `((x*x)+(y*y))+(z*z)` in f32; a nonpositive or unordered norm leaves the vector unchanged. Otherwise it uses the f32 square root (sqrtf fallback for an unordered square-root result), f32 reciprocal, then component multiplication.

The normal is **v cross u**: `(v.y*u.z-u.y*v.z, v.z*u.x-u.z*v.x, u.y*v.x-v.y*u.x)`, each product/subtraction f32. The camera-z-axis dot is accumulated as `(nx*axis.x + ny*axis.y) + nz*axis.z`, even though the canonical axis has zero x/y. Preserve those multiplications for NaNs. Strict ordered dot > 0 rejects with reason 4. Otherwise flip dot's sign bit and call `acosf(-dot)`; no clamp to [-1,1]. The angle comparison at `0x0087E63C..0x0087E644` passes on `<=` **or unordered** (BLE), so an acos NaN is not itself reason 4. Equal angle passes.
