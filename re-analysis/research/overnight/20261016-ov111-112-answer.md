**Reachability of the M15-061 L1 null dereference (0x005A610C):**

- **R1, the normal invariant.** At FeedingEat start, +0x120 == +0x94, and that cube's controller exists. A stale +0x94
  is cleared by E2 before any T2.
- **R2, the only live eraser.** The disconnect handler (0x005ACA7C..0x005ACAE2) erases the controller and sets +0x94 =
  −1. It does not stop FeedingEat.
- **R3, where the disconnect comes from.** It is delivered in the robot-message phase (UpdateRobotConnection), before
  UpdateAllRobots.
- **R4, the next tick.** BehaviorManager::Update runs before ActionList::Update, and it stops FeedingEat through stage
  13 → TransitionToBest → ChooseNext, a reaction, or SetCurrentActivity.
- **R5, the reachable window.** CheckAndUpdateTreadsState calls ActionList::Cancel(−1) without stopping the behaviour
  first (0x00512030..0x00512038). It does so on entering Falling, from the RobotState lambda 0x00537F52..0x00537F66.
  If that happens in the **same message drain after** the target cube's disconnect, while FeedingEat is in state 2, the
  sequence is:
  1. the synchronous completion runs;
  2. TransitionToEating;
  3. StartedEating;
  4. map[−1] inserts null;
  5. the fault at **0x005A610C**.

  This is reachable, but only by a hardware timing coincidence. **The M1-034 visible skip stands.**
- **R6:** HandleRobotStopped ends the behaviour before Cancel(−1), so it is safe.
- **R7:** the app's CancelAction runs before the robot-message phase, so it cannot follow a same-tick disconnect.
- **U1** (M15-069): the census of other synchronous completions in the robot-message phase.
- **U2** (M8-024): the teardown path, where AbortAll in ~Robot reaches TransitionToEating in state 2.

**Other M1-034 point:** 0x005D61D6. GetAnimation returns null (with the InvalidName log), and GetTrack then reads
null+0x68. Whether shipped data reaches it is unread (M15-069).
