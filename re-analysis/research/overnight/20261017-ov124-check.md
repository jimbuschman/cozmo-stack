## Corrections to the answer

- **Row 6:** 0x004ECA0A is an unconditional NeedsManager::Init call, not a NeedsInit test. The gates are the isMember
  checks 0x004EC820/0x004EC832/0x004EC844, UiMessageHandler::Init 0x004EC854 and InitInternal 0x004EC974 (already
  owned by M1-054).
- **Row 8:** loading starts on the first Update **in engine state 2**, not the first Update. Update's switch
  (0x004ED5C4 ldrb +0x62, tbb 0x004ED5CC) reaches the loading case 0x004ED5F0 only in state 2. State 1 → 2 happens when
  HasDesiredNumUiDevices is 1 (0x004ED5D8), then SendSupportInfo (0x004ED5E2), then SetEngineState(2) (0x004ED5EA).

## Omissions

- **O1. G2E RequestAvailableAnimations (0xB2) and RequestAvailableAnimationGroups (0xB3).** The RobotManager
  constructor subscribes both when context+4 is non-null (0x0052E51A..0x0052E5B2, 0x0052E54C). The 0xB2 handler
  (0x0052FC02) tail-calls BroadcastAvailableAnimations; the 0xB3 handler (0x0052FBA0) calls
  BroadcastAvailableAnimationGroups. Neither has a loading gate.
- **O2. The state-2 tick ends with EngineLoadingDataStatus.** After the M1-055 branch, the state-2 case always runs
  0x004ED612..0x004ED618 → 0x004ED7C0, which sends EngineLoadingDataStatus built from the progress float (ctor
  0x004ED7DE, slot +0x1C at 0x004ED7E6). The progress out-parameter is written on every DoNonConfigDataLoading call,
  before the done test (0x00523576, dmb, 0x0052357E). 0x004ED7C0 dereferences context+4 without a null check
  (0x004ED7D2). No record owned this, nor the state 1 → 2 transition.
- **O3.** Manager Init also calls steady_clock::now (0x0052E75A), and after the blacklist emits
  `sEventF("robot.init.time_spent_ms","%lld")` (0x0052E7AA..0x0052E7B0) and calls FirmwareUpdater::LoadHeader
  (0x0052E7F8). None touches the container. (FirmwareUpdater is unsupported under the app-boundary rule; its
  LoadHeader call on the Init path is a lead for M1-054's owner.)
- **O4.** The loader ctor also zeroes +0x27C (0x0051EF46).

## App senders (manager, 2026-10-17)

A grep of `unity/` for ReadAnimationFile (0xB1), RequestAvailableAnimations (0xB2) and RequestAvailableAnimationGroups
(0xB3) finds only the generated union and message classes (`MessageGameToEngine.cs:190-192` and accessors). The app
never sends them. Under the app-boundary rule the stack has no input that reaches these handlers, so they are
unreachable in the stack, like the SDK paths. That also makes the answer's row-27 concurrency question (a reload
during the initial load) unreachable, and the extractor's open question about the duplicate 0xB1 handler at
0x004EDE0C moot.
