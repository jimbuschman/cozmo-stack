The complete apply block, with instruction order preserved:

```text
0x006B50C8  LDRB  r0, [S+0xA0]
0x006B50CC  CBZ   r0, 0x006B50DC
0x006B50CE  LDRD  r0,r1, [S+0xA4]   // exposure word, gain word
0x006B50D2  MOVS  r2, #0
0x006B50D4  STRB  r2, [S+0xA0]      // pending false first
0x006B50D8  STRD  r0,r1, [S+0x98]   // current exposure and gain
```

There is no call between the load, flag clear and current store. It does not zero the stale pending payload, compare the new tuple with current, test an acknowledgment, or preserve a second queued entry. Pending=false skips all writes. Pending=true with an identical tuple still clears the flag and stores it. There is no f64 operation and no floating-point arithmetic in the consumer: f32 gain bits are copied as a word, including signed zero and any NaN payload should such a value reach this lower-level interface. Exposure is not converted to the robot message's u16 here. The producer accepts an int and the consumer copies that int; the normal public producer validates its range upstream.

This is a source-backed logical transition. LDRD/STRD plus a separate byte store is **not proof of an atomic three-field transaction for concurrent threads**. The checked producer and consumer contain no mutex acquisition, exclusive operation or memory barrier for these fields. Native instruction order must not be described as a lock-protected snapshot merely because the managed implementation uses one.
