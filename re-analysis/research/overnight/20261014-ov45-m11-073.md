## Conversion: success and failure contracts

GetWithRespectTo at 0x00845A34 takes from wrapper r0, reference wrapper r1 and output wrapper r2. It checks each node at wrapper+4 before proceeding. Missing node reaches VERIFY key `PoseBase.GetWithRespectTo.NullInputPose`, format `VERIFY(%s): FromNull:%s ToNull:%s WrtOtherNull:%s`, assertion `!fromPose.IsNull() && !toPose.IsNull() && !P_wrt_other.IsNull()` and Y/N strings at 0x00845E88/0x00845E84. It returns false. Nonidentical wrappers with different roots fail HasSameRootAs and return false at 0x00845CEE without writing the output transform or parent. **Defined false-return failures preserve the output, not clear it and not parent it.** If caller preconstructed an empty-named Pose3d, that output remains a root. Constructor/invalid-tree throws and undefined dereferences are not false-return output guarantees.

For valid same-root poses the helper copies transforms to temporaries, aligns ancestor depths and computes the relative transform; general transform writes at 0x00845C7C..0x00845CB0 include 32 quaternion bytes and three translation words. Every normal successful path joins 0x00845DFA and calls SetParent(output, reference) at 0x00845DFE, returning 1. This establishes a parent even when the reference itself is a root. A reference root is not a null pose.

The same-wrapper branch 0x00845CF6 logs Warning key `PoseBase.GetWithRespectTo.FromEqualsTo`, text `Pose w.r.t. itself requested.`, copies the source to output and also calls SetParent(output, source). Do not replace it with an inferred identity-root output. Aliasing output with the reference/source requires the native SetParent alias/tree behavior; no arbitrary cyclic-tree case is certified as normal here.

There are 1000-step ancestor-loop bounds in the body (0x00845AE2, 0x00845B74, 0x00845C12). Their `LoopBoundOverflow` Error log uses `%s:%d`, poseBase_impl.h path and lines 0x1A0 /0x1B6 /0x1D4, sets errG and conditionally debug-breaks; it is not a supported reason to classify a valid pose-tree conversion as failed and zero its output. All return/write branches of this requested helper were inspected; called quaternion/tree mathematics is not re-derived here.

Flatten helper 0x004DF628 starts with a fresh root output. A root source is assigned unchanged at 0x004DF666..0x004DF66A. A non-root source gets public FindRoot and invokes GetWithRespectTo(source, root, output) at 0x004DF67E. Success therefore yields a non-root output parented to root. False logs Error `Pose3d.GetWithRespectToRoot.Failed`, `Could not get pose w.r.t. its own root. This should never happen.` at 0x004DF69C, leaving the fresh root. Invalid-tree failure must stay separate from valid root-input behavior.

## Object and marker parents

InitPose 0x004EF562 calls object virtual +0x28 with incoming pose, distance -1.0f and supplied state, then sets initialized byte +0x50=1. Base SetPose 0x004EF580 calls helper 0x004EF590; that helper assigns to object pose +4 at 0x004EF5A2 and stores pose state +0x24. No unconditional non-root guard/SetParent appears before assignment. Thus **InitPose is not itself a proof that object poses have a parent**.

ObjectPoseConfirmer::UpdatePoseInInstance passes its supplied pose to virtual +0x28 directly or through 0x0050609C; the latter copies old pose, writes the supplied new pose at 0x005060F0 and broadcasts the change. A clamp-to-flat branch starts from a copy of the supplied pose; it is not a demonstrated mandatory reparent. SetGhostObjectPose 0x00506E40 forwards pose unchanged with -1 distance. AddLiftRelativeObservation at 0x00506E94 forwards its supplied pose and afterward copies the same pose into the confirmation record at +0x18 (0x00506ECE..0x00506ED2). These writers propagate input parenting; names such as “LiftRelative” do not prove that every caller actually supplied a child. The broader robot-relative/object-relative observation construction and all BlockWorld writers must still be joined before claiming a global object invariant.

The fixed-custom and markerless producer reads already reported in OV10 identify useful positive edges: both explicitly parent new object pose to Robot.GetPose().GetParent before InitPose (0x0061E27C and 0x00622416 are the relevant potentially failing reads). This is conditional on the robot invariant and does not cover all observed/ghost/carried/stacked objects. AddLocatedObject's root lookup, successful lookup by object ID, a Known pose-state byte or family/type test is not by itself a parent test.

For marker-owned poses there is a stronger construction invariant. Vision::ObservableObject::AddMarker at 0x00876844 copies the local pose, then at 0x00876860..0x00876862 calls SetParent(copy, object+4). It constructs the KnownMarker in the owned marker list with that pose at 0x00876872. KnownMarker constructor 0x0087E22C creates a node then calls SetPose at 0x0087E284; SetPose assigns pose at 0x0087E2BE. Its current parent is the object pose node even if that object node is a root. Parent presence and parent's parent presence are different properties.

A bounded direct-call scan found KnownMarker::SetPose calls at its constructor and PoseCluster::TryToAddMatch 0x0062ABC4. The latter mutates a **cluster-owned KnownMarker copy** in its observation-pair list, using a pose copy and transform precomposition; it does not prove mutation of the original object's owned marker pose. This supports the two ordinary PreAction constructor marker-list cases. It is not a promise that any arbitrary externally constructed KnownMarker is parented.

The transformed-copy PreAction constructor is different: its GetParent at 0x0050DFFA reads the supplied Pose3d, saved from r2, after forming a transformed pose. Actual ActionableObject::GetCurrentPreActionPoses call at 0x004DF9A8 passes its object's GetPose result (navigation and native argument window checked). A marker-parent invariant cannot certify that object pose's own parent. Ramp::IsPreActionPoseValid 0x0050F9FE reads PreActionPose+8; success of base validity, nonnull robot pose and action type 3 are not substitutes for tracing that pose's construction/failure paths.

## Robot setters, ramp and charger

Delocalize explicitly parents robot+0x298 to the new origin **at 0x00510B0A**, and parents +0x2A4 at 0x00510B44, before SetNewPose at 0x00510B4C. Thus the construction-time bare-root window ends earlier than treating SetNewPose itself as the first parent write would suggest.

SetNewPose 0x005126EC flattens incoming pose and calls SetPose, then appends the current robot pose to vision history at 0x0051271C. SetPose 0x0051502C requires same root as world origin at 0x0051503C; it does **not** require HasParent. On success it assigns incoming pose at 0x00515080, preserving robot name, then updates drive-center pose. A world-origin root could satisfy this guard; proving actual callers never supply it still matters.

The ramp/charger concern can be narrowed without first proving the ramp/charger object's own parent:

- Ramp::GetPostAscentPose reads ramp GetPose then constructs the result with that pose explicitly as parent at 0x0050F618..0x0050F61C. GetPostDescentPose does the same at 0x0050F786..0x0050F78A. Their geometry is not needed to establish this parent edge.
- SetOnRamp calls the appropriate helper, flattens the result and calls SetNewPose at 0x0051664E /0x00516672. In a defined valid tree, these are child→flatten→child-of-root, even if the ramp pose was a root. A root ramp alone is **not** a witness for the robot becoming a root.
- Charger::GetRobotDockedPose obtains charger GetPose at 0x004EA1D8 and passes it to the parent-bearing Pose3d constructor at 0x004EA202. SetPoseOnCharger flattens that result at 0x005168B2 then SetNewPose at 0x005168BA. Again, root charger alone does not create root robot.
- UpdateCurrPoseFromHistory 0x005135F8 converts a successful computed history state **with respect to world origin** at 0x0051365A, and only on nonzero result invokes SetPose at 0x00513664. Thus even a root history input is not automatically copied as a root robot pose by this path. A successful conversion is parented to world origin.

The bounded direct-call scan also found a SetNewPose producer omitted from the earlier “ramp or charger” summary: **MovementComponent::CheckForUnexpectedMovement at 0x0063E87E**. In the checked window it copies a pose from sp+0x50 to sp+0x30, replaces quaternion words with the current robot rotation and passes that pose to SetNewPose. The additional read at 0x0063E612..0x0063E644 establishes sp+0x50 as HistRobotState filled by ComputeStateAt(recorded unexpected-motion timestamp, interpolate=1), with the SetNewPose path reached only on result 0. It copies the historical pose parent and replaces rotation with current rotation. A root from raw history therefore remains a possible input to SetNewPose, but a fresh independent root fails SetPose's world-root check; it is not automatically a root robot witness. This new dependency prevents silently upgrading the ten robot consumers on the strength of the ramp/charger read alone.
