## Bounded conclusions and caller census

There is **no native zero-device route through HasDesiredNumUiDevices**, even with desired count zero.
For the actual direct/TCP slots, a nonzero count is sufficient because +0x84 remains zero. The configurable desired
count often suggested by the function name belongs to UDP Init, which the actual CreateSocketComms here does not select.
The repository's `re-analysis/protocol/engine_configuration.json:13` says NumUiDevicesToWaitFor = 1, but this repo copy
is not used as proof that the production direct object reads that setting. Its native Init simply returns 1.

UI Init calls each non-null comms object's virtual Init with its slot index and the config
(0x006601C6..0x006601E6). Direct connected count becomes 1 after its connection/message-receive progression; it is not
engine readiness or robot count. This report ends at that app-connection boundary; it does not extract the replaced game socket flow.

Native branch census over Thumb 0x004D6860..0x0095E540 and ARM 0x0095E540..0x00AE3682, including resolved PLTs,
found SetEngineState calls 0x004ED5EA (2), 0x004ED60E (3), 0x004ED66C (3).
ARM/Thumb veneer 0x008CA9DC resolves to its PLT 0x004A5104; callers 0x004ECC4A and 0x004ECDF8 pass 1 and 4.
Only 0x004ED5EA passes 2. The engine-class +0x62 store census finds the setter; constructor zero-fill of engine+0x40
for 0x23 bytes (0x004EB2A8..0x004EB2B4, __aeabi_memclr4 PLT 0x004A403C) covers that byte's initial zero.
No alternative shipped transition to state 2 was found. This is a native production caller finding, not a guarantee against arbitrary external symbol invocation.

For a stack with no UI device, these native gates cannot become true by waiting or setting desired count to zero.
Replacing the app connection prerequisite needs an explicit recorded host/startup input policy under the app-boundary rule.
This report supplies the original's predicate and downstream effects; it does not approve a replacement policy.

SetEngineState has observable API/readiness effects: store first, E2G UpdateEngineState(old,new) second, telemetry afterward.
The generated app enum corroborates 0 Stopped, 1 WaitingForUIDevices, 2 LoadingData, 3 Running, 4 UpdatingFirmware
(`unity/scripts/csharp/Anki.Cozmo/EngineState.cs:3`), and
`unity/scripts/csharp/Anki.Cozmo.ExternalInterface/UpdateEngineState.cs:73` reads the two fields in old/new order.
The native sender/serializer above establishes those widths and ordering independently.
No robot-interface send occurs within the setter; its stored state determines which later Update path performs robot work.
The report stops at E2G invocation and does not claim delivery with no UI device.

Progress starts at zero. For N normal non-SDK animation files with the normal increment tails, the animation phase adds
N binary32 increments of binary32(0.7)/N, so its accumulated value need not equal 0.7 exactly.
The coarse addition is binary32 0.2, followed eventually by an exact 1.0 overwrite. No independent 0.1 milestone was found.
No clamp/reset is inserted between phases. With N=0, the native vdiv still executes; there are no queued file completions
to consume that increment in the ordinary no-files path. Loader failures, stop flags and failure branches do not establish
a supported "failed" engine state; the operator-defined stack failed state remains an addition recorded in M1-056.
