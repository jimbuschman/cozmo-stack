The relevant direct calls are:

- `0x00522D7A`: Error, no explicit channel, key `RobotDataLoader.DasEventConfigJsonNotFound`, format `DAS Event Json config file %s not found or failed to parse`, argument relative filename, empty KV. - `0x0052E7B0`: Event (`sEventF`), no explicit channel, key `robot.init.time_spent_ms`, format `%lld`, empty KV, signed 64-bit elapsed milliseconds. Subtract the earlier steady-clock integer timestamp from the later one with low-word `subs` and high-word `sbc`, then signed divide by `0xF4240` (1,000,000). - `0x005445BC`: Event (`sEvent`), key `robot.play_animation`, no explicit channel, unformatted value and `$data` as row 15. This is the event the set gates.
- `0x007647A2..0x00764818`: unknown-name `std::cerr` output described above, not a DAS level/channel/key.

There are no floating-point decisions in blacklist selection or membership. Enum values and the loop counter are 32-bit; count/index comparison is unsigned. The only f64 operation boundary encountered here is the optional numeric-element string conversion. The original six strings do not take it.

Ordinary engine initialization loads the set before a robot needs to be connected. Its consumer remains reachable during normal non-SDK trigger actions while connected. A blacklist hit still runs playback initialization. Missing/bad resource input can reach the error branches at startup; no SDK guard protects them. Malformed JSON-type cases are resource corruption/custom-input cases, not behavior exercised by the shipped asset. This report does not infer support for a particular drone-control app flow merely from an animation name.
