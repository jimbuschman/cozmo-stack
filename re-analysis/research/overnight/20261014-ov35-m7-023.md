## Optional ActionList-unregister branch

This branch is skipped in normal Robot destruction, but it is defined when MoodManager is independently destroyed with a non-null live Robot/ActionList and nonzero ID. Init registers a raw-this `HandleActionEnded` closure using ActionList::RegisterActionEndedCallbackForAllActions and saves its ID at `+158` (`0x0067AF0E..38`).

1. ActionList::UnregisterCallback loads its ActionWatcher pointer at `+10` and forwards ID unchanged (`0x0053F916..91A`; veneer `0x008CB49C` resolves to PLT `0x004AA9A8`, recipient `0x0054182C`). It does not synthesize a RobotCompletedAction.
2. ActionWatcher searches its signed-int keyed callback tree at `+24` (root+28). Empty/missing returns0. Exact match calls erase and returns1 (`0x0054182C..7C`). Mood ignores this return and clears its ID after any normal return.
3. Erase calculates successor, updates tree begin when required, decrements count, removes/rebalances node, destroys function via inline/heap destroy slot, then deletes node (`0x00542E14..6A`). It does not call the function's invoke slot.
4. Mood's action-ended bound closure vtable is `0x01030734`; relocated destroy slots `0x0103074C/750` resolve to `0x0067C2B4/2B6`. Those are `bx lr` and operator-delete veneer respectively. No HandleActionEnded call and no last-action emotion event occurs as a consequence of unregistering.

Classification for those four steps: **M7-023, IMPLEMENTATION_GAP pending manager checking**. ActionWatcher's earlier destruction during ActionList teardown is not repeated in mood. Do not “fix” the already-null ActionList path by calling an old retained pointer or replaying completion notifications.

## Arithmetic, outputs, reachability and failure cases

There is **no f32/f64 arithmetic** in the normal mood destructor, its history/vector/tree cleanup, or the inspected disconnect/unregister recipients. All branches here are pointer, integer-key, reference-count, string-representation or iterator tests. Float map entries and history samples are discarded without reading their values. There is no RNG, timer deadline, tolerance, decay step or sample scheduling to emulate on this path.

There are **no utility log calls** in these normal teardown bodies, so there is no destructor log level/channel/key/format/argument tuple to preserve. The nearby `MoodManager.LoadedEventMap` INFO and `MoodManager.ActionCompleted.Reaction` DEBUG messages belong to initialization/runtime handling, not these destruction operations. They must not be emitted merely because a callback is unregistered. No engine-to-game publication, robot message, sleep action, file Save or audio call is present in the recovered mood-owned retirement path. This conclusion follows the actual closure destruction recipients, not just the absence of a send in the top-level destructor.

This is reachable when an ordinarily connected non-SDK Robot is removed/destroyed. Normal Robot construction installs mood; normal Robot destruction calls it. Its gate depends on component pointer state, not the current SDK mode or whether a robot is still physically connected at the instant of deletion. The ActionList-non-null alternative is a conditional API path; no separate normal Robot teardown entry taking that alternative was found or needed. Null mood skips everything; an absent external interface can leave the subscription vector empty; expired signal ownership makes the handle's reset return without touching the list. Those are defined behavior, not crash-policy departures.

The explicit cleanup landing pad `0x0067AE76..0x0067AEB8` first releases the subscription vector, then the same three trees and nine history vectors, then forwards the saved exception to `0x004E39F8`. That helper calls `__cxa_begin_catch` followed by **std::terminate** (`0x004E39FA..3A01`). It is not a normal “catch and continue” destructor branch. Precise EH table coverage for every imported call is not claimed here. The standing **M1-034** policy covers reaching this terminate, with the owning record naming this address and a visible smallest-unit skip/preserved-prior-state disposition. No new approval is needed.

Other malformed-state hazards are likewise not normal branches: ScopedHandleContainer with a null held handle dereferences it at `0x004EF1BE` before the slot+8 call; ActionList's forwarding branch with a corrupt/null watcher would dereference it at/under `0x00541830`; corrupt vector/tree/list ownership is not a valid input corpus. Existing M1-034 applies to a demonstrated undefined/terminating path, but no unobserved malformed-container traversal or blanket whole-subsystem reset is invented. No new app-input policy or ADP-1 exception is relevant to this retirement task.
