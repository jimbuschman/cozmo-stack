## Analysis: can each VERIFY fire on a running robot?

### UnownedParent (Dev_Assert)
**Condition:** parent != NULL AND `_areUnownedParentsAllowed` == false AND parent->ownerCount(+0x48) == 0.

`_areUnownedParentsAllowed` is ONLY set to true by ~PoseOriginList (0x0084798C) and restored (0x008479CC). In normal running it is false.

`PoseBase::SetParent` (0x00844A14) checks parent ownership before calling PoseTreeNode::SetParent — protected.

But `PoseTreeNode::SetParent` (0x008449EA) itself does NOT check. It is called from:
- PoseTreeNode::operator= (0x008459DA) — via PoseBase::operator= with non-null source
- PoseTreeNode ctor (0x00845FA2) — at construction, no parent yet
- PoseTreeNode::~PoseTreeNode (0x0084606C) — clears parent (null), safe

So if PoseBase::operator= is called with a non-null source whose parent has ownerCount == 0, the child's parent pointer is set to an unowned pose without any VERIFY at attach time. The UnownedParent VERIFY would then fire on the NEXT tree walk (GetWithRespectTo, HasSameRootAs, etc.) that traverses this edge.

**Reachability:** 76 operator= call sites exist. Whether any passes a non-null source with an unowned parent is UNKNOWN without per-caller analysis. The mechanism exists.

### NotLastOwner (~PoseBase and operator=)
**Condition:** RemoveOwner makes ownerCount 0 AND flag == false AND (control block == 0 OR use_count != 0).

~PoseBase has 644 call sites; operator= has 76. NotLastOwner fires if a PoseBase wrapper is destroyed while its node's count was 1 (→0) but other shared_ptr copies of the same node still exist.

**Reachability:** The mechanism exists. Whether any specific caller destroys the last wrapper while shared_ptr copies remain is UNKNOWN without per-caller analysis of all 712 call sites.

### ZeroOwners (RemoveOwner, count==0 before decrement)
**Condition:** RemoveOwner called when ownerCount == 0.

Both callers (~PoseBase and operator=null-source) call RemoveOwner on a node whose count should be ≥1 (each wrapper incremented it at construction). ZeroOwners fires only on a double-destroy: two wrappers sharing the same node both destroyed without proper count management.

**Reachability:** Possible if PoseBase::operator= with non-null source creates a second wrapper without incrementing (row 6.4), then both wrappers are destroyed — first makes count 0 (NotLastOwner may fire first), second calls RemoveOwner with count==0 → ZeroOwners. Mechanism exists; actual production triggering UNKNOWN.

### ZeroOwnersWithID (RemoveOwner, count→0, ID≠0, flag false)
**Condition:** count reaches 0 AND flag == false AND ID(+0x44) != 0.

Only origins have non-zero ID (row 8.5). Origins are destroyed ONLY by ~PoseOriginList (row 7.7: exactly 3 callers, all in Robot destruction). ~PoseOriginList sets flag=true before destroying origins (row 7.3). Therefore ZeroOwnersWithID cannot fire during normal origin destruction.

**Reachability:** No. Origins cannot lose their last wrapper outside ~PoseOriginList because:
- No tree erase/remove method exists (verified: PoseOriginList has ctor/dtor/ContainsOriginID/AddNewOrigin/AddOriginWithID/GetOriginByID/Rejigger/Flatten/SanityCheckOwnership only — no erase)
- ~PoseOriginList is the sole destroyer, called only from Robot destruction (3 call sites)
- The flag is set during origin destruction, suppressing ZeroOwnersWithID

### Cross-thread mutation
No mutex protects pose tree operations. Dev_GetMutex exists but is unused in pose tree walks. GetWithRespectTo walk caps assume no concurrent mutation. Any concurrent mutation would be undefined behavior (null parent read in Rotation3d::PreMultiplyBy at 0x0084AC82 per 20261014-pose-tree-verifies.md §3 — an M1-034 point with no production path).
