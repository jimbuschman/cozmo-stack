## What is owned and what is discarded

Robot construction allocates **32 bytes** for DockingComponent (`0x0050FE24`), calls its constructor and installs it at Robot+0x280 (`0x0050FE30/34`). It then allocates **24 bytes** for CarryingComponent (`0x0050FE38`), constructs and installs it at Robot+0x284 (`0x0050FE44/48`). These constructors make no calls and install no subscriptions:

Freeing these instances ends their native state lifetime. It does **not** call UnSetCarryObject, UnSetCarryingObjects, SetCarriedObjectAsUnattached or SendSetCarryState. It neither reparents a cube nor emits a carrying-state message. The surrounding Robot teardown has already released BlockWorld at `0x005112CE` and pose members/roots before the raw frees, as the ordered M1-044 ledger records. Calling those world-mutating routines at the raw-free point would create an unsupported access into already-destroyed owners.

A managed port may require explicit removal of delegates it introduced to represent native ownership. That is an implementation obligation to reproduce the lifetime, not evidence of a native component unsubscribe call or a new allowed policy. It must happen at the corresponding native owner boundary, with no extra state notification, wire send or reordered action cancellation. This report does not approve the existing managed replacement-instance semantics merely because they avoid stale delegates.

## The earlier action and messaging subscriptions

The actual dock-action cleanup is `IDockAction` D1/D2 at `0x00557448` (there are destructor aliases; do not infer the owner from one alias name). The relevant component writes are:

- DeselectCurrentObject first (`0x0055745C`). If PathComponent::IsActive returns exactly 1, abort path (`0x00557460..0x00557474`).
- Read docking component through action+0xCC. If docking byte+4 is nonzero, call AbortDocking (`0x00557474..0x00557484`). Then **unconditionally** write u16 docking+0x10=3 and word docking+0x0C=-1 (`0x00557484..0x0055748E`). The status bytes and three offset words are not zeroed by this reset.
- Subsequent light/squint/sub-action/reaction-lock cleanup precedes subscription releases (full direct ordering in OV03). External handle vector action+0xE4 is released first, then the DA handle control block at +0xE0, then C5 at +0xD8 (`0x00557582..0x0055759E`). The remaining sub-action is destroyed and IActionRunner base destructor follows (`0x0055759E..0x005575B6`). These are **action-owned**, not DockingComponent-owned, handles.

Thus cancellation can legitimately cause an earlier conditional AbortDocking in addition to AbortAll's unconditional explicit call. “Do not duplicate a send at raw deletion” does **not** mean deduplicate those two source-backed sends. Whether a concrete queued action is actually destroyed at Cancel(-1), deferred, or retained depends on M8-015's queue predicates; this read does not invent that outcome.

The robot message subscriber object has its own teardown before component frees. `RobotToEngineImplMessaging::~...` (`0x00532A10..0x00532A78`) destroys maps at +0x144, +0x138, +0x110 and +0x104, then releases the handle vector at +0xF8, destroys its file buffer/ios state, and tail-calls release of the handle vector at +0. Its handle-vector destructor (`0x004EAE94..0x004EAEC8`) walks **back to front**, first decrementing the stored end by 8 bytes, then releasing the old element's nonnull shared control block, and finally deleting the vector storage. This ordering matters for any callback lifetime claim.

On the final shared ownership release, the ScopedHandleContainer control block's `__on_zero_shared` at `0x004EF184` reads its +0xC pointee, invokes container cleanup if nonnull, then frees it. Container cleanup (`0x004EF1B8..0x004EF1D2`) calls the held handle's vtable+8 disconnect, then if the handle remains nonnull calls vtable+4 deletion. Robot-message scoped disconnect (`0x0051D8F8..0x0051D936`) returns if the signal's weak control block is absent/expired, or if the recovered signal/list is absent, or if the saved node is not in the current list. If found, it unlinks that node. Unlink (`0x0051D338..0x0051D3A8`) destroys/clears the callable, patches neighbors, retains the removed node's own links, and drops its node reference. This agrees with current M2-018's registration-ordered, synchronous, mutation-aware signal ownership. It is not permission to replace emission with a snapshot or to cancel subscriptions twice.

No direct log or robot message is present in these handle/vector release bodies. Held callback destructors and the external-interface signal specialization have their own concrete targets; their exhaustive effects are not settled by the generic release ordering. The component raw-free sites invoke none of them themselves.

**Buildable M12-040 rows:** bind the native carrying and docking instances to their ordered Robot lifetime slots; clear the owner before release; discard the old per-instance state; do not run a carrying reset, detach operation, extra abort or callback at raw deletion.
