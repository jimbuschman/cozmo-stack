## DA and deleted-target handlers

DA's complete body is 0x00557E82..0x00557E9C. It obtains the liftLoad payload, loads its first byte, selects value 2 if zero or 1 if nonzero, writes action byte +0xC2, then returns. There is no numeric conversion beyond selecting integer constants. In particular byte2/255 also count as true; do not add a payload==1 requirement. Every subscribed dock action for that robot is updated regardless of its target or current +0x80. No timestamp, action tag, dock-start latch, currently-picking check, or previous load value is consulted. No logs or outgoing messages. Constructor and Init begin +0xC2 at 0; repeating DA replaces the prior value. PickupObjectAction::Verify consumes that field, but its broader verification flow is outside this handler claim.

The external event is **RobotDeletedLocatedObject**, not a general game-command handler. Native 0x005524C6..0x005524CC compares 32-bit payload ObjectID to 32-bit dock ID +0x7C. Different -> return unchanged. Equal -> Info at 0x005524E2, channel `Actions`, key `IDockAction.RobotDeletedLocatedObject`, exact format `Dock object was deleted from current origin stopping dock action`, no format arguments, empty metadata; then write +0x7C=0xFFFFFFFF at 0x0055250C. There is no validation rejecting ID=-1 first, so a matching -1 event would also log/write.

Despite the log wording, this body does **not** call AbortDocking, Cancel, emit a completion, or delete itself. Its next CheckIfDone starts by testing ID+1==0 (0x005521BE..0x005521C6), before any sub-action update. That branch returns **0x03000004** via 0x005522BC..0x005522BE and 0x005523DC. Later action cleanup may abort the docking component as above; it must not be moved into the synchronous deletion callback. DA similarly records an input for later verification rather than synthesizing a completion message.
