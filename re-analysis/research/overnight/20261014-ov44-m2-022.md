## Synchronous local delivery is established

At 0x006625C6..0x006625CE Broadcast(&&) calls game delivery first. It then loads the message tag, gets the timer f32, converts it to f64 at 0x006625E6, moves the message into an AnkiEvent and calls 0x00662590 at 0x006625FA. That helper looks up event tag in the local signal table, and if found directly calls 0x00663C74. At 0x00663C8A..0x00663C90 the signal directly calls the stored function; its dispatch at 0x00663D18..0x00663D20 tail-calls the concrete callable's virtual +0x18. There is no queue, scheduling yield or call to ProcessMessages between Broadcast and the local callback. Signal code retains traversal nodes around calls; this report does not re-prove every unsubscribe/lifetime rule covered by the protocol records.

Subscribe 0x006626CC reads the 16-bit requested tag at 0x006626E4, obtains that per-tag signal at 0x006626EC..0x006626F2, then attaches a copied callback through 0x0066411C. Thus **if** a 0x60 recipient is registered it runs synchronously at this point and could alter state before the producer resumes. Proving the mechanism is not proof of which recipient exists.

## What actually executes during Clear

ActionList::Clear's +0xC flag is set before its tree destruction at 0x0053D928..0x0053D92C. Nested Clear sees it and returns. After destruction the begin/root/count fields are reset and flag cleared at 0x0053D930..0x0053D938. This protects recursive Clear, not all robot dispatch or arbitrary queue mutation.

ActionQueue destructor 0x0053F938 calls Clear and destroys remaining containers. Queue Clear 0x0053F96A sets +0x1C, deletes current and queued actions using DeleteActionAndIter, then clears that flag. DeleteActionAndIter normal path at 0x0053FA22 calls PrepForCompletion, may form RobotCompletedAction, invokes the action's deleting destructor through virtual +4 at 0x0053FA78, clears action pointer/removes iterator, then broadcasts completion through the external interface's +0x1C at 0x0053FAB2. Consequently **synchronous external/local activity inside ActionList::Clear is real** even though Clear itself contains no ProcessMessages call. The completion broadcast is after that action's deletion, but before the entire queue/tree Clear has returned.

PrepForCompletion 0x00540750..0x005407E8 does not execute the completion callback list. Already-prepped logs Debug channel Actions, key `IActionRunner.PrepForCompletion.AlreadyPrepped`, format `%s [%d]` with action name/tag. Otherwise it calls virtual +0xC with the completion union, then sets +0x55=1. Closing all virtual +0xC implementations is separate work.

IActionRunner destructor was read through normal return 0x00541286 and its unwind tail through 0x0054131C. It first switches to the base vtable. If not prepped, Error key `IActionRunner.Destructor.NotPreppedForCompletion`, format `[%d]`, tag +0x60; sets errG and conditionally debug-breaks. If +0x58 set it clears PathComponent custom motion profile. It erases tags from the static in-use set. For movement flags +A/+B/+C it checks track ownership with tag string, invokes StopHead/StopLift/StopBody for tracks 1/2/4, and logs Info channel Actions, key `IActionRunner.Destroy.StopMovement`, format `Stopping movement on the following tracks since they were locked and are still moving: %s[%s][%d]` with accumulated track labels, action name and tag. If not already unlocked and action state is not 0x02000001, it calls track unlock helper 0x004F0EB2. It calls ActionWatcher::ActionEnding at 0x00541238. It then clears the list of completion functions at +0x64 and member strings/union. **Destroying a std::function list is not invoking those functions with an ActionResult.** Callback-object destructors can still be dependencies; no blanket purity assertion is made.

Movement stop parent bodies 0x00640A08..0x00640ACC, 0x00640B3C..0x00640C00 and 0x00640C70..0x00640E1A were read. They conditionally call DirectDriveCheckSpeedAndLockTracks with zero speed and finish by building zeroed motor message arguments for helpers 0x00640ACC /0x00640C00 /0x00640E1C. No direct ProcessMessages occurs in these parents. Their send/unlock descendants are not a closed proof that pumping cannot occur.

PlayAnimationAction destructor was read from 0x00543DAC through 0x00543EC4 including unwind paths. It compares the robot's current-animation pointer with its +0x90. On equality logs Info channel Unnamed, key `PlayAnimationAction.Destructor.StillStreaming`, format `Action destructing, but AnimationStreamer is still streaming this animation(%s). TellingAnimationStreamer to stream null.` with its animation-name string. Calls SetStreamingAnimation(null,0,true,true) at 0x00543E26. Then releases owners at +B4,+AC,+A4,+9C, frees animation string and invokes base destructor.

SetStreamingAnimation's **null** branch calls Abort at 0x0057B244, stores null in streamer+0x38, and if old stream existed sets +0x73=1. It does not run InitStream for this null input. Abort can first emit **AnimationAborted** synchronously through external interface +0x1C at 0x0057B410 if +0xA0 is nonzero. It logs detailed stream state, resets face-track frame data and +0x71/+0x72, invokes RobotAudioAnimation::AbortAnimation if present and clears current audio animation. That is not a robot receive-pump call, but its event recipients and audio descendants are meaningful reentry boundaries. The null path does not create AnimationEvent 0x60 merely because the containing class is an animation class.

The ActionWatcher lead was checked at 0x00541BB4..0x00541C08: it builds completion state through virtual +0xC, gathers subaction results and queues a RobotCompletedAction in its deque. The rest of ActionEnding, recursive action-specific destructors and emitted-message recipient closure have not been fully extracted in this answer. A search for direct/veneer ProcessMessages calls in the bounded Thumb scan did not identify a route from these parents; that negative scan has unresolved virtual/ARM/tail-call limits and is not an affirmative proof.
