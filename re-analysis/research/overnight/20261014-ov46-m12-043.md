Its evidence cites the OV02 check, corners/midpoint 0x006177F0..0x00617A08 and 0x00617A8C..0x00617C32, multimap 0x00618A4C, and the then-unread GetBoundingQuad / Block::GetBoundingQuadXY. ## 1. Quad construction, floating-point order and frame

`Block::GetBoundingQuadXY` receives the pose explicitly; it does not silently substitute another object pose. Its virtual call at 0x004E62B6 obtains the block's normalized 3D vertex container. It flattens the supplied pose at 0x004E62C0 using 0x004DF628, then uses that transform's rotation and translation. The flatten helper's success path expresses the pose relative to its root (see OV45); the parent has no separate success check here. A failed flatten must retain that helper's own documented failure behavior, rather than be treated as a valid world transform.

Padding is applied in local 3D before rotation, with an individual f32 result for each operation:

```
pad2 = f32(pad + pad)                         // 0x004E62D6
expanded[k] = f32(pad2 + block.dimension[k]) // k = X,Y,Z, 0x004E62EA..F2
scaledVertex[k] = f32(expanded[k] * vertex[k])// 0x004E634A
rotated = flattenedPose.rotation * scaledVertex
points.push(rotated.X, rotated.Y)
quad = GetBoundingQuad(points)
quad[i][k] = f32(flattenedPose.translation[k] + quad[i][k])
```

Dimensions come from block+0x88/+0x8C/+0x90. Vertices retain their original container order. Rotation is the full `Rotation3d::operator*` call at 0x004E635A; it is not a yaw-only simplification. Its internal multiply/add rounding was not independently expanded in this request. The Z component is discarded only after rotation. Translation is added only after rectangle fitting and corner sorting (0x004E6396 then 0x004E63B2). The translation helper visits physical corners 0..3 and coordinates X then Y, using `vadd.f32 translation,coordinate` at 0x004E68F0. No division by two is inserted into the scaling step; normalized vertex magnitudes come from the virtual vertex provider. Negative/NaN padding is not clamped in this parent.

Consequently the returned XY coordinates are in the supplied pose's root frame, with the sort's angle ranks established on the rotated, untranslated vertices. Do not re-sort after translating: f32 translation can collapse distinct coordinates and change a reconstructed centroid's rounding. The pyramid caller supplies A's pose and zero padding (0x00617818..24).

`GetBoundingQuad<float>` copies all input float bits into a `vector<cv::Point2f>` in input order (0x004E64AA..DA), builds an input-array descriptor with flags 0x8103000D, and calls `cv::minAreaRect` at 0x004E64FE. The resulting five words are center X/Y, width, height and angle. It invokes `RotatedRect::points` at 0x004E6520, constructs a quad from OpenCV points P0,P1,P2,P3, then invokes `SortCornersClockwise` at 0x004E655A. The constructor 0x004E7E9C stores argument 1 at byte 0, argument 2 at byte 8, argument 3 at byte 0x10, argument 4 at byte 0x18. Instruction write order is not a different index order.

Reading only through 0x004E6598 would miss a defined source path: the exception landing pad 0x004E65C6 constructs a text list ` (x,y)` for the cv points and logs error key **GetBoundingQuad.CvMinAreaRectFailed.COZMO-1916**, format **cvPoints.size=%zu%s**, at 0x004E672C. It sets `_errG=1` and conditionally calls the configured error-break helper. It calls `Rectangle<float>::InitFromPointContainer` on the original points at 0x004E6778, converts min/extent to center with `f32(min + f32(extent*0.5))`, stores width/height and zero angle, ends the catch and jumps to 0x004E6512. Thus fallback still uses the shipped OpenCV points routine and angle sort. The exact exception type selector in LSDA was not decoded here; the finding is the observed landing-pad behavior, not a claim that every possible throw is caught.

The fallback rectangle helper at 0x004E81B4 is also read: empty vector produces four zero words. Otherwise the first point seeds min/max; later points update minima on strict greater-than and maxima on strict less-than, retaining previous values for equal/unordered comparisons. Width and height are f32 max−min. This is a defined fallback, not an M1-034 skip.

The shipped `libopencv_core.so` points body 0x00086188..0x0008627A computes angle-radians as f64(f32 angle) * pi / 180 using f64 operations; calls double cos/sin; converts each result to f32 then multiplies by 0.5f. With a=half-sine and b=half-cosine, its operation sequence is:

```
P0.x = f32(f32(cx - f32(a*h)) - f32(b*w))
P0.y = f32(f32(cy + f32(b*h)) - f32(a*w))
P1.x = f32(f32(cx + f32(a*h)) - f32(b*w))
P1.y = f32(f32(cy - f32(b*h)) - f32(a*w))
P2.x = f32(f32(cx+cx) - P0.x); P2.y = f32(f32(cy+cy) - P0.y)
P3.x = f32(f32(cx+cx) - P1.x); P3.y = f32(f32(cy+cy) - P1.y)
```

These are VMLA/VMLS instructions, not an authorization to replace them with arbitrary fused arithmetic. The phone's system libm implementations are not recovered by this read.

The shipped `libopencv_imgproc.so` minAreaRect body begins with clockwise, returned-point convexHull (`r2=r3=1` at 0x0009C7DC..EE), converts the hull to float if needed, and checks the number of 2D points. For >2 it runs the inlined rotating-caliper path (0x0009C8D8..0x0009CDC4); strict comparisons choose extrema, the four candidates are scanned in index order using strict greater-than, and an equal best-area candidate replaces the previous candidate (`bhi` skips only ordered greater at 0x0009CCC8). It computes center and two edge lengths, then angle. For two hull points it uses f32 coordinate sums times 0.5, f32 differences promoted to f64 for length/atan2, zero height (0x0009CDFC..0x0009CE80). One point copies its center; the five result words were zeroed first. All paths convert radians to degrees by f32 multiply by 180 followed by f64 divide by pi and conversion to f32 at 0x0009CE8E..AC. This is not an independent extraction of convexHull or every libm descendant; their exact exceptional/NaN behavior remains outside the recovered closure.

## 2. Sort layout and pyramid insertion / tie order

The centroid routine adds physical inputs in order **P0, P2, P1, P3**, each coordinate separately, then multiplies each sum by 0.25f (0x004DF7BE..0x004DF84E). Preserve that sum order, not `(P0+P1+P2+P3)/4` with arbitrary association.

The sorter iterates original indices 0..3, computes each f32 XY difference from this centroid, and calls **atan2f(deltaY,deltaX)** (0x004E7F24..60). It sorts pairs `(angle, originalIndex)` by angle only. For four elements the path dispatches to `__sort4` at 0x004E84D4..E4. The complete sort3 and sort4 bodies use ordered strict less-than (`vcmpe`, `bmi`; equal/unordered follows the no-swap branch). Sort3 can exchange nonadjacent entries; do not claim a general stable equal-angle sort. For degenerate or NaN angles, reproduce these small-sort branches rather than an arbitrary library sort. atan2f's system-library arithmetic is an external boundary.

Name the actual post-sort angle-ranked vertices a,b,c,d (ranks 0,1,2,3). At 0x004E7F7A..96 the constructor is passed **a,d,b,c**, and its physical storage is therefore:

- Q[0]=a; Q[1]=d; Q[2]=b; Q[3]=c.
- `GetBaseInteriorCorners` pushes **Q[3], Q[2], Q[1], Q[0]** at 0x00617826..90, i.e. **c,b,d,a** or ranks **2,1,3,0**.

For a finite nondegenerate axis-aligned rectangle in Cartesian XY, a=bottom-left, b=bottom-right, c=top-right, d=top-left. Physical storage is BL,TL,BR,TR; pyramid insertion is TR,BR,TL,BL. These names are an illustration, not a screen-coordinate convention or a promise about arbitrary rotated/degenerate geometry. A perimeter traversal would be physical 0,1,3,2; that is not this insertion loop.

Each candidate corner pose gets zero yaw around Z, its XY from that vector, Z from A's `GetDimInParentFrame<Z>` using A's flattened rotation, and parent `robot.GetWorldOrigin` (0x00617894..0x00617928). Z is A's height, not A's center Z plus half-height. The routine computes squared distance between each candidate pose and B's pose at 0x00617946, and inserts the float result as the multimap key at 0x00617962. On a failed pose-distance computation it destroys the temporary and returns false via 0x00617A00..08; it does not choose an arbitrary corner.

The first two tree entries are flattened into the two output poses at 0x00617984..98C and 0x006179B4..9BC. Thus distance rank controls which outputs are first and second. The checked OV02 insertion body 0x00618A4C places equal keys to the right, preserving their insertion sequence; for equal finite distances the priority is therefore **c,b,d,a**. Its NaN-right comparison is not a conventional total ordering over all NaNs and finite values; do not claim one.

Midpoint calls that corner routine first; false propagates without assigning a new output (0x00617C18). On success it flattens both corners and computes X and Y as **f32(f32(first+second)*0.5f)** at 0x00617B98..A8. It recomputes A's Z height, uses zero yaw/Z axis, takes the root of the robot's pose at 0x00617BC8, constructs the new pose at 0x00617BEE and assigns the output at 0x00617BF6. This differs from averaging each coordinate in f64 or doing two half-products. The corners' parent is the world origin, while the midpoint's parent is explicitly the robot pose's root; do not erase that source distinction even when they coincide normally.

## 3. Can the builder supply duplicate AB bases?

For the ordinary located-object tree containing distinct objects A and B once each, **no: the manager update cannot emit both AB and BA, and cannot emit the same A/B pair twice.** This follows from the builder and processed-ID loop, not merely from pair equality or the cache.

`UpdateAllBlockConfigs` loops the three configuration kinds and calls each container update (0x00616F00..44). The pyramid-base container is the manager field at +0x44; its vtable at 0x0102E6D4 has address point +8. Slots +8/+0xC/+0x10/+0x14 resolve to 0x0062C7D4 (copy current cache to old cache), 0x0062C7DE (release old cache), 0x0062C708 (clear current cache), and 0x0062C56E (build and append entries). The raw slot words and relocation for AddAllConfigs were inspected; the assignment veneer 0x008CCB8C resolves to the vector-assign PLT 0x004B8718.

Update queries located objects with allowed families {2,1} from 0x00C77784, then copies current to old cache and clears current at 0x006168EC..FE. For each seed whose numeric ObjectID is absent from a local processed-ID set (0x006169A4..B4), it invokes the container builder. **After every returned configuration** it calls `GetAllBlockIDsOrdered` and inserts every returned ID into that set (0x0061693E..64). The PyramidBase implementation returns its min-ID then max-ID (0x00618054..9E). Therefore after seed A produces AB, seed B is skipped. Even if A produces several bases, all of those bases' IDs are marked before the next seed. This is a greedy seed expansion, not enumeration of every possible graph edge; do not replace it with all unordered pairs globally.

`Pyramid::BuildAllPyramidBasesForBlock` builds another {2,1} family filter from 0x00C77A80, adds its native predicate, queries the located objects at 0x006182B0, requires at least two results, finds the seed pointer, removes that occurrence once, then tests each remaining object with `BlocksFormPyramidBase` at 0x00618372. Each passing object produces one newly allocated PyramidBase. There is no AB/BA nesting within one seed. The normal world enumeration uses current-origin selection at 0x0061EC22 and traverses origin/family/type/object trees, invoking the collector once per accepted nonnull stored object node (0x0061EB78..0x0061EEAE). It neither repeats the entire result for the other seed nor duplicates entries during collecting.

The PyramidBase constructor 0x0061749C canonicalizes distinct numeric IDs: signed max at +0xC, signed min at +0x14. Equal input IDs become invalid (-1,-1). Equality at 0x006174F8 rejects an invalid/equal pair, then compares both stored numeric IDs. ContainsBlock at 0x006167C8 checks those numeric IDs via the virtual ordered-ID vector; it is not a broad geometric membership test.

There is an important limit to the cache explanation. At 0x0062C5A8 each new raw entry is compared with the **old** cache (+0x10), using 0x0062C68C. If equal it deletes the new raw object and reuses the old shared pointer; otherwise it wraps the new raw pointer. **Either result is appended unconditionally to the current cache and returned vector** (0x0062C5AC..0x0062C60E). This preserves weak-pointer identity across updates; it is not a deduplication set over the current cache. Do not use this helper alone as a proof of uniqueness. PruneFullPyramids at 0x0062C72E removes matching bases; it does not create duplicates.

Accordingly T7's hypothesized repeated delegation from two ordinary entries both containing the same distinct A and B has no builder witness: the second matching base is absent under the enumerated-world conditions above. The top-loop's lack of an early break remains a source fact; preserve it rather than adding a deduplication/break as a supposed correction. If duplicate entries were injected or the object trees held aliased objects / repeated numeric IDs across nodes, this builder has no independent current-cache uniqueness gate. Exhaustive insertion, ID-allocation and corruption reachability were not recovered here, so a universal claim over those states is **UNKNOWN**, not a proven safety invariant. Distinct pairs sharing just A do not both contain A and B.

## 4. StopHelperWithoutCallback and replacement semantics

The component routine 0x0056DCBC reads the first stack entry and compares its raw helper pointer with the requested shared pointer. If unequal it returns false. If equal it calls `ClearStackFromTopToIter` with that begin iterator and returns true. It does not search for an arbitrary matching buried entry. It does not guard an empty stack before dereferencing begin: if that condition is reached, the original has an invalid read; the standing M1-034 policy covers the actual undefined path, not a changed normal stop rule.

`ClearStackFromTopToIter` 0x0056DCE0..0x0056DDC0 walks from the top toward that target, calling `IHelper::Stop` and removing/releasing the shared entries, stopping when the saved target helper is reached. The top helper receives **isActive=true**, subsequent buried helpers **false**. It bounds the loop at 1000. Overflow logs **LoopBoundOverflow**, format `%s:%d`, file `../../../../engine/aiComponent/behaviorHelperComponent.cpp`, line **262** (0x106), sets `_errG=1`, optionally invokes the debug-break helper, and returns. No success/failure completion callback is invoked by either of these component bodies. Shared-pointer release/destruction is still real behavior and is not a blanket promise of no external side effects.

`IBehavior::StopHelperWithoutCallback` 0x005BD21C locks the behavior's weak helper ownership at +0xC8. Missing/expired ownership or a null helper at +0xC4 returns false. A valid helper logs on **Behaviors**, key `behaviorName + ".SmartStopHelper"`, text **Behavior stopping its helper**, forwards to the robot's BehaviorHelperComponent (+0x264 then +0x10), returns that boolean and releases the temporary strong ownership. The wrapper does not clear its weak reference fields here and does not directly invoke either completion callback.

`IHelper::Stop(bool)` 0x005B6768 logs **IHelper.Stop** on **BehaviorHelpers**, format **%s isActive=%d, IsActing=%d**, then calls LogStopEvent. When active and its attached behavior has an active action (+0x84), it calls `StopActing(false,true)` at 0x005B67E6. It always invokes the helper's virtual StopInternal slot +0x24 at 0x005B67F2. LogStopEvent, every concrete StopInternal, every action stop/destructor and downstream message receiver were not fully expanded here. Their full side-effect closure is **UNKNOWN**; “without callback” must not be translated to “nothing else happens.”

The replacement call in SmartDelegateToHelper is direct at 0x005BEBE8, after its existing-helper warning. It proceeds toward the new component delegation afterward. This agrees with OV02's finding that a second delegate replaces the first rather than retaining two live independent delegates. The cache/builder proof above constrains that specific duplicate-base trigger; it does not remove replacement semantics from the general helper API.
