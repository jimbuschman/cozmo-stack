# OV27 — repair mutation and random part damage

Request: `requests/overnight/20261014-ov27-m15-029.md`. Binary: ARMv7 `resources/lib/armeabi-v7a/libcozmoEngine.so`, SHA-256 `02263c07f6bb60f4d7f351a3667dca84fd3e6c0fc6f838e18b5de7cf4e2989e1`. Native Thumb instructions read with Capstone skipdata; decompilation used only to find addresses. No code, inventory or manifest changes; no hardware run or shipped-file upload. This answer alone is committed/pushed under the operator's instruction.

Current record M15-029: **“Repair need mutation and random part-damage contract”**, **RECOVERABLE_GAP**. Evidence: “f32 store 0x0069C522; dirty +0x88 at 0x0069C528; repair id0 calls PossiblyDamageParts(1) at 0x0069C52E..0x0069C536; recipient 0x0069C5D8..0x0069C77A (triage D1).” Unresolved: “Recover exact mutation, RNG draws/order and selected part behavior.” Its effect is “Repair crossing can mutate wrong state or choose parts with different RNG/order.”

**Finding:** PossiblyDamageParts has no random probability test. It computes a target damaged count from repair thresholds, subtracts the current count, and randomly chooses that many additional parts. Every choice consumes two MT words, even when there is only one eligible part. Selection walks the ordered part map, returning the selected element's **ordinal position**, not its stored enum key. The normal initialized map makes these identical; sparse or invalid maps do not.

## Threshold data and RNG arithmetic

Config initialization clears the existing threshold vector then reads prefix plus decimal index 0..31, stopping at the first nonnumeric/missing entry; each numeric value is read asFloat and appended in that order (0x0068EB34..0x0068EC0A). Prefix global 0x0105C120 is initialized to `BrokenPartThreshold` at 0x004D881E..0x004D8858, literal 0x00C4A058. No threshold sort/normalization is introduced. Shipped `re-analysis/obb/assets/cozmo_resources/config/engine/needs_config.json:28` supplies 0.98, 0.6, 0.3 at indices 0,1,2. Their binary32 encodings are 0x3F7AE148, 0x3F19999A, 0x3E99999A. For finite valid levels and three parts: >f32(0.98) requires zero; equality through >f32(0.6) one; equality through >f32(0.3) two; <=f32(0.3) three. Missing threshold 3 ends loading. This describes that shipped file, not an unverified assertion that every alternative needs config is identical.

RandInt at 0x0082FA74..0x0082FA96 always calls GetNextDbl, widens signed range to f64, multiplies f64 random*range, and VCVT.S32.F64 converts toward zero. It does not special-case 0 or 1, clamp, or use integer modulo. For each new damaged part:

1. GetNextDbl reads distribution lower L at RNG+0x9C8 and upper H at +0x9D0.
2. Draw MT word **a first**, then **b second** (0x0082F9CA/0x0082F9D2).
3. Compute `v = f64(b)*4294967296.0`; `v = v + f64(a)`; `v = v * 2^-64`; `span = H-L`; `v = span*v`; reread L, `u=L+v`. Every operation is a separate f64 instruction; no f32 or fused multiply-add. Constants 0x0082FA18/0x0082FA20 are exactly 2^32 and 2^-64.
4. Compute `index = trunc_s32(f64(u * f64(range)))`.

GetNextDbl: 0x0082F9B0..0x0082FA14. Constructor initializes distribution L=0,H=1 and index=0 (0x0082F7F8..0x0082F816), then calls SetSeed with the caller's seed. **Damage never constructs/reseeds it**; prior engine consumers affect the same stream. Absolute next value cannot be inferred from the repair level alone.

The MT body is recovered at 0x0082FAC8..0x0082FB64. State has 624 u32 words and index at +0x9C0. For current i, j=(i+1)%624, m=(i+397)%624: `y=(state[i]&0x80000000)|(state[j]&0x7FFFFFFE)`; `z=state[m]^(y>>1)^((0-(state[j]&1))&0x9908B0DF)`; store state[i]=z, advance index=j. Temper `z ^= z>>11; z ^= (z<<7)&0x9D2C5680; z ^= (z<<15)&0xEFC60000; z ^= z>>18`, u32 wrapping. This is incremental state replacement; do not change draw order by generating an unrelated batch.

There is a rare upper-end rounding boundary: the two-word f64 assembly can round to 2^64, producing u=1 under L=0,H=1 and round-to-nearest. For a=b=0xFFFFFFFF the arithmetic does so. RandInt then returns range, the chooser exhausts the healthy entries and returns map size, and T6 can insert an invalid part key. The code contains **no retry/clamp**. This is a derived boundary from the read arithmetic, not a sampled engine observation or proof that a particular seed hits that pair. EnumToString then returns null. sEvent 0x0080D114..0x0080D13C forwards that value to the logger provider's virtual +8 if present, or does nothing if absent. The provider's null-value treatment is not established here; do not assume a crash or “fix” the defined map insertion. A reachable terminating recipient would fall under M1-034 at its actual crash point. Accepted FP mode and exact exceptional behavior remain M15-030 obligations.

## Other mutation entry: negative ApplyDelta

ApplyDelta is a second caller and must preserve RNG ordering. At 0x0069C902..0x0069C93E it reads delta center at +0 and variation at +4; computes width=f32(variation+variation), calls RandDbl(f64(width)) **unconditionally**, subtracts f64(variation), narrows to f32, adds center in f32, then adds old level in f32. This consumes two MT words before any potential part-selection words, including variation=0. It stores the resulting level and dirty flag before calling PossiblyDamageParts only when effective delta is ordered negative (MI expressed as falling through BPL at 0x0069CAA8) and need ID==0, forwarding the action supplied to ApplyDelta (0x0069CA94..0x0069CAB6). Thus negative repair variation can damage; positive repair does not invoke this function. The positive repair/energy special clamps at 0x0069C976..0x0069CA7E were inspected as an adjacent interface, not asserted to be a complete proof of every repair action caller.

For the negative path, general clamp starts at configured minimum; if candidate >minimum (BLS excludes ordered <=) it compares with maximum and substitutes maximum on GE, otherwise candidate survives (0x0069C93E..0x0069C96A). M15-030 must retain the unordered distinctions. No needs.part_damaged event occurs when target-current<=0, but the delta draw has already been consumed.
