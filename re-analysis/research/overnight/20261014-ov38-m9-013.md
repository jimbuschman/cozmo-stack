# OV38 — MIDI routing into the singing get-in branch

Request: `requests/overnight/20261014-ov38-m9-013.md`. Raw vtable words, native constants and bank bytes were checked. Earlier research served as navigation, not independent proof.

The narrow routing answer is settled: get-in participates in note-on dispatch. The record's effect text, **“a get-in recording is layered onto roughly every sung note of every song, or none at all”**, is not a complete description of the recovered possibilities. The runtime attempts this branch alongside the other target children, then makes container choices and applies descendant filters. A selected descendant can reject a note. The engine does not go back and select a pitch-compatible alternative in response to that MIDI rejection. Audible contribution therefore depends on the selected path, event, scheduling, voice creation and subsequent lifetime.

Classification in the rows is a proposed disposition for the described evidence boundary, not an edit or approval of a manifest record. `IMPLEMENTATION_GAP (recovered)` means the manager can compare/build that row from the cited primary source; it does not certify current C# behavior. `RECOVERABLE_GAP` identifies a remaining unread boundary.
