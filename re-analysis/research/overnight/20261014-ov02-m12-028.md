### Exact midpoint algorithm at its primitive boundaries

GetBaseInteriorCorners (0x006177F0..0x00617A08) obtains **A's** virtual bounding quad at slot +0x50 using A.pose and padding +0. It inserts the four returned 2-D corners into a vector in order **3,2,1,0** (0x00617826..0x00617890). This is not a search of all corner-pairs from A and B.

For each corner, construct yaw-zero/Z-axis pose `(corner.x, corner.y, A.GetDimInParentFrameZ(rootRotation(A)))` under Robot::GetWorldOrigin, and compute full 3-D squared distance to **B.pose**. Failure returns false before writing the two caller outputs (0x00617946..0x0061794C -> 0x00617A00). Insert `(f32 distance, pose)` into a `multimap<float,Pose3d>` (0x0061794E..0x00617962); after four entries take the first and its tree successor, root-express each and assign them as the two output poses (0x0061797C..0x006179C6). Equal-key insertion behavior must preserve the shipped tree's ordering; do not replace this with an unstable sort. The exact tree insertion body is a remaining primitive boundary listed below.

GetBaseInteriorMidpoint (0x00617A8C..0x00617C32) stops false if that call fails, leaving its own output unchanged. Root-express both returned poses again. Load first x, second x, first y, second y. Compute **f32** `x=f32(f32(x1+x2)*0.5f)`, `y=f32(f32(y1+y2)*0.5f)` at 0x00617B98..0x00617BB8. z is A's root-oriented **dimension**, not half-dimension and not an average of corner z. Construct yaw-zero/Z-axis pose under **Robot::GetPose().FindRoot()**, assign output, return true. These two parent sources differ in the native calls and must not be silently conflated.

The target frame helper (0x00877574..0x00877644) root-expresses target.pose; reads that root-expressed z and yaw, but reads x/y from the **original pose's** transform (0x008775C8..0x008775DA). Its z arithmetic is `f32(rootZ + f32(dimZ * input))`, multiplication then addition. Parent is the root of the root-expressed pose. All three producer uses supply input +0. Preserve this mixed-source x/y behavior if non-root parents are allowed. The stored quaternion/pose operations underneath retain their own M11 arithmetic requirements; there is no permission to replace them with yaw-only 2-D subtraction.
