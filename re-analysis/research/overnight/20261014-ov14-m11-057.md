### Reader: exact operation

Let `S` be VisionSystem, `e` the signed 32-bit exposure proposal already in `r6` at `0x006B30AE`, `gBits` the unmodified f32 gain bits in `r4`, and `maxE = *(int32*)(S+0x88)`. The following describes the instructions, not an alternative exposure design:

```text
if ((*(uint8*)(S + 0xAD) & 0x40) == 0):
    outE = e
else:
    q = trunc_signed_32(e / 10)
    r = e - 10*q
    if (r == 0):
        outE = e
    else:
        next = low32(e + (10 - r))
        ceiling = low32(10 * trunc_signed_32(maxE / 10))
        outE = signed_min(next, ceiling)
*(int32*)(S + 0x384) = outE
*(uint32*)(S + 0x388) = gBits
return 0
```

| Step | Exact original behavior | Citation | Owner / classification |
| --- | --- | --- | --- |
| L1 | Load byte `S+0xAD`, shift left 25, branch on N clear to identity. Original bit 6 becomes N; this is mask bit 14 because the mask starts at `S+0xAC`. Other mode bits do not enter this decision. | `0x006B30AE: ldrb.w`; `0x006B30B2: lsls #0x19`; `0x006B30B4: bpl` | M11-057, IMPLEMENTATION_GAP candidate |
| L2 | Load magic signed multiplier `0x66666667`. `smmul` gets signed product high word; arithmetic-shift that by 2 and add its original unsigned sign bit. This implements signed division by 10 truncating toward zero, including negative inputs. Compute `r=e-2*(q+4*q)`. | `0x006B30B6..0x006B30CC` | M11-057, candidate |
| L3 | If remainder is zero, keep `e` and **do not read maxE**. There is no revalidation, minimum clamp, or gain adjustment here. | `0x006B30D0 -> 0x006B30F4` | M11-057, candidate |
| L4 | Nonzero remainder: load signed maxE; calculate `next=e+(10-r)` with ARM 32-bit arithmetic; use the same signed divide-by-10 sequence on maxE, multiply quotient by ten; compare the two signed values. Keep ceiling unless next is strictly less. | `0x006B30D2..0x006B30F2` | M11-057, candidate |
| L5 | Store exposure and gain as two 32-bit words at `+0x384/+0x388`, set return 0. The reader emits no log, no message, and no pending-mode mutation. | `0x006B30F4..0x006B3106` | M11-057, candidate |

There is **no floating-point arithmetic in L1–L5**. Exposure remains int32, not float or double; gain bits are carried through unchanged. For ordinary nonnegative exposure this rounds upward to a 10-ms multiple, except that the rounded value is capped at the greatest 10-ms multiple not above maxE. The cap can make the result lower than the input. Signed negative and overflowing inputs must be described by the actual instruction sequence, not by an unsigned ceiling formula.

Examples derived from that sequence (not an engine execution or sensor experiment):

| Mode 14 | Proposal e | maxE | Reader output | Reason |
| --- | ---: | ---: | ---: | --- |
| off | 16 | 66 | 16 | Identity. |
| on | 16 | 66 | 20 | Next multiple is 20, cap is 60. |
| on | 60 | 66 | 60 | Remainder zero; cap is bypassed. |
| on | 66 | 66 | 60 | Next is 70, cap is 60. |
| on | 70 | 66 | 70 | Divisible proposal bypasses the cap; later validation rejects it. |
| on | 1 | 9 | 0 | Cap is zero; reader does not clamp back to minimum exposure. |

The ctor's defaults are maxE 66, minE 1, minGain f32 bits `0x3DCCCCCD`, maxGain `0x40800000` (4), current exposure 16, gain `0x40000000` (2), established at `0x006B002A..0x006B004A`. Actual maxE is mutable camera state; do not hard-code 60 in this reader. M3-021 owns limit initialization/default-camera updates. If configured minE exceeds the largest available 10-ms multiple, this modifier can produce a result below minE; SetCameraSettings rejects it instead of correcting it here.

### Placement in image processing

The normal source chain is:

`SetHeadlight -> EnableMode(14,on) request -> Update drains mode queue -> active mask -> scheduled CheckImageQuality(mode 7) -> exposure proposal -> L1–L5 -> result deque -> UpdateAllResults bit-7 handler -> UpdateImageQuality -> SetCameraSettings -> robot send / pending feedback / game report`.

SetHeadlight passes mode 14 and the same requested on/off byte to VisionComponent at `0x00632350..0x00632364` before constructing/sending the headlight message at `0x00632368..0x00632380`. This ordering is independent of eventual physical headlight acknowledgment. Update drains queued mode/bool pairs FIFO at `0x006B4FB6..0x006B4FE4`, calling EnableMode before popping each item; the current M11-061 evidence owns its mask writer. M11-057 consumes the resulting bit, not the queue entry. Two requests applied before the same image can therefore leave only their final active state for this reader.

Update tests `ShouldProcessVisionMode(7)` at `0x006B55E4..0x006B55EC`, requiring return exactly 1. That routine first checks the corresponding active bit (`0x006B5AA8..0x006B5AB2`) then the schedule; M11-034 owns the schedule mechanism. Mode 14 does not receive its own ShouldProcessVisionMode call at the reader. Enabling only mode 14 does not force checking quality or sending new exposure values on every tick.

On a due mode-7 frame, Update brackets CheckImageQuality with profiler Tic/Toc using **`CheckingImageQuality`** (`0x00C018A8`), call sites `0x006B55F6`, `0x006B5600`, `0x006B560E`. CheckImageQuality first obtains an exposure-adjustment factor from the ImagingPipeline. A nonzero status takes its failure path **before** L1; no new proposal is stored by L5. On success, the proposal stage writes quality byte `S+0x380=1`, starts from current exposure/gain at `+0x98/+0x9C`, and reaches L1 after choosing new exposure/gain or quality 2/3. The quality decision precedes quantization; L1 does not reclassify quality after changing exposure.

Bounded read of the immediate proposal stage, `0x006B2F5A..0x006B30AC`: factor thresholds are f32 `0x3F7FFF58` and `0x3F800054` (approximately 1±0.00001), with gain-bound tolerance `0x3727C5AC` and its negative `0xB727C5AC`. Exposure changes convert int32 exposure to f32, multiply by the f32 factor, call roundf, convert the returned f32 to signed int32, then clamp on the relevant exposure bound. Gain changes use f32 multiplication and f32 comparison against the configured gain bound. No f64 exposure arithmetic occurs. A factor inside the deadband can leave the original exposure unchanged at this stage, yet L1–L5 can still quantize it. For finite normal values, factor below the lower threshold tries reducing exposure before gain; above the upper threshold tries increasing gain before exposure. This report does not claim that the histogram/ROI input calculation, NaN cases throughout that wider algorithm, or quality percentiles have all been recovered.

Successful CheckImageQuality returns 0; Update ORs processed mask `S+0x37C` with `0x80` at `0x006B566A..0x006B5672`. It locks mutex `+0x35C`, pushes result beginning `S+0x378` into deque `+0x360`, unlocks, returns success (`0x006B5676..0x006B5690`; result pointer saved at `0x006B4E34..0x006B4E38`). The deque copy helper at `0x006BC8EE..0x006BC8FA`, called by `0x006BC2C2`, copies the five scalar header words and final byte without recomputing exposure/gain. Thus result `+8` is quality, `+0x0C` exposure, `+0x10` gain. Allocation/list-copy details remain the separate result-container ownership boundary.

CheckMailbox locks the same mutex, returns false for empty size at `S+0x374`, otherwise copies the front result header into its output at `0x006B2B32..0x006B2B40`, moves payload lists, pops front at `0x006B2CAE`, unlocks and returns 1 (`0x006B2AD4..0x006B2AF2`, `0x006B2CA8..0x006B2CC4`). UpdateAllResults calls CheckMailbox and loops on result 1 at `0x00654A6E..0x00654A7A`; processed bit 7 controls UpdateImageQuality at `0x00654784..0x00654794`. The mailbox/dispatch records retain ownership of their full loops, including other modes; no whole-pipeline settlement is inferred from these scalar copies.

### Camera recipient and externally visible effect

UpdateImageQuality first requires **physical Robot byte `Robot+0x14 != 0`** and **result quality byte `result+8 != 0`** (`0x0065558C..0x00655594`). This field's meaning is verified by Robot::SetPhysicalRobot storing its bool at `0x0051397A`, not inferred from a connection flag. If VisionComponent's auto-exposure byte `+0x329` is nonzero, load result exposure/gain and call SetCameraSettings (`0x00655596..0x006555A6`). Otherwise no camera-settings call is made from this result; the separate quality-state notification path still continues. There is no “only if the values changed” test before this call.

SetCameraSettings `0x006560C8..0x006561AA`, already owned by **M3-021**, does the following in order:

1. Require IsExposureValid return exactly 1, then IsGainValid exactly 1; failure returns without send, pending update, or CurrentCameraParams broadcast. Exposure validity is signed `minE <= e <= maxE` (`0x006B9DAA..0x006B9DBE`). Gain validity uses f32 comparisons `maxGain >= g` and `minGain <= g`; the actual ARM GE/LS conditions reject unordered comparisons (`0x006B9E80..0x006B9EA8`). Invalid exposure prevents even calling gain validation.
2. Emit the Info row below, promoting gain f32 to f64 only for printf. Construct SetCameraParams with raw f32 gain, **low 16 bits** of exposure, bool false. Set engine-to-robot variant tag **`0x57`** (`0x007A99A0..0x007A99AC`); call Robot::SendMessage with reliable=1, hot=0 at `0x00656166`. Its return value is not tested here. Clear the temporary message.
3. Call VizManager::SendCameraInfo with u16 exposure and f32 gain (`0x00656170..0x00656176`). The Android body `0x006C0424..0x006C043C` only constructs/clears a local CameraInfo variant; it does not send it.
4. Queue the original int32 exposure and f32 gain through SetNextCameraParams (`0x0065617A..0x00656180`). This is not an immediate write to current exposure/gain. The slot writes are gain `S+0xA8`, exposure `S+0xA4`, pending byte `S+0xA0=1` (`0x006B2302..0x006B230C`). M11-060 owns its later consumer; the consumer is at `0x006B50C8..0x006B50D8`, copying the pending pair to `+0x98/+0x9C` and clearing pending, without another quantization call there.
5. Construct CurrentCameraParams with the same f32 gain, low-u16 exposure, and **actual auto-exposure byte** from component `+0x329`; engine-to-game tag **`0x2F`** (`0x00723A94..0x00723AA0`); Robot::Broadcast at `0x006561A4`, then clear temporary. It is delivered at the stack API boundary under project app scope. It is not conditional on successful wire send.

Both payload serializers write gain's four bytes, then exposure's two bytes, then bool (`0x007BF44E..0x007BF486`, `0x00710F90..0x00710FC8`). On this little-endian binary the payload is seven bytes. The two bool fields have different sources: robot request false, game report current auto-exposure state. No new gamma curve is sent by this path. The robot's physical sensor response is outside app-side extraction; the source-backed effect is the exact request and report sequence.
