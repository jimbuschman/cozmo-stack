## Lift arithmetic, in execution order

The mathematically simplified ordinary-angle picture is a translation near `(66*cos(angle),0,66*sin(angle))` under the lift base and canceling Y rotations. That picture is **not** the native arithmetic contract. In particular, a near-zero angle can select the Z axis in the second quaternion, and rounding/rescaling is observable. The following is the native contract.

1. `Radians(float)` stores input bits, enables rescaling, calls 0x0084C87C (constructor 0x0084C832). For finite input already in **(-pi_f, pi_f]**, unchanged. `pi_f=0x40490FDB`; negative-pi `0xC0490FDB` takes the add-two-pi path. For |v|<10, repeatedly add f32 `0x40C90FDB` while v<=negative-pi; repeatedly add `0xC0C90FDB` while v>pi. Otherwise compute, with a rounding at every operation, `v - f32(f32(i32(ceilf(f32(f32(v/twoPi)-0.5f)))) * twoPi)`; native conversions at 0x0084C91E/0x0084C922. Comparison branch instructions, including unordered behavior, are 0x0084C892 BLE, 0x0084C8A0 BLS, 0x0084C8B2 BPL, 0x0084C8BC BHI. No finite-input validation is inserted.
2. Rotation3d(angle,Y), 0x0084A526..0x0084A582: `half=f32(angle*0.5f)`, call cosf(half), then sinf(half), retaining both returns. Products sin*axisX/Y/Z are **f32**, then all four components are widened separately to **f64** and normalized. Axis is Y=(0,1,0). This constructor does not first normalize the supplied axis.
3. Normalize, 0x00849DB8..0x00849E52: f64 `n2=((w*w+x*x)+y*y)+z*z`, each multiplication/add separate. If `abs(1-n2) < doubleBits(0x3E56A09E19D672B6)`, multiply each component by `2/(n2+1)`. Otherwise hardware sqrt(n2), with external sqrt fallback only if the sqrt result is NaN, then divide each component by the root. Unordered comparison chooses the sqrt branch; there is no zero guard.
4. Copy normalized q into node; write the three f32 translation words. Construct Radians from sign-bit-flipped **original input**. RotationVector3d 0x0084A224 copies those Radians and Y axis, normalizes that axis using MakeUnitLength, checks its norm. With the constant unit Y axis the norm is exactly 1 and the axis warning cannot fire. Do not replace the original angle with zero simply because Radians equality says it is near zero.
5. Rotation3d(RotationVector3d), 0x0084A598..0x0084A60E: compare its angle with zero using Radians equality. That equality uses rescaled difference with strict absolute `< f32(0x3727C5AC)` (0x0084CBDC..0x0084CC5C). If equal/near, use **Z axis**; otherwise vector's axis Y. In both cases use the original copied angle, not zero, then the same half-angle/cosf/sinf/f32-products/f64-normalization pipeline.
6. Rotate translation, 0x0084ACA6..0x0084ACE2: narrow quaternion w,x,y,z separately from f64 to f32, **without normalization**, then call 0x00849C1C. Let `ww=w*w`, etc.; every expression below is f32, non-fused, and each doubled cross product means `(a*b)+(a*b)` with the computed product reused. Form `m00=((ww+xx)-yy)-zz`, `m11=((ww-xx)+yy)-zz`, `m22=((ww-xx)-yy)+zz`; `m01=2xy-2wz`, `m10=2xy+2wz`, `m02=2wy+2xz`, `m20=2xz-2wy`, `m12=2yz-2wx`, `m21=2wx+2yz`. Outputs are `x=m02*pz+(m00*px+m01*py)`, `y=m12*pz+(m11*py+m10*px)`, `z=m22*pz+(m20*px+m21*py)`, with exactly those grouping/orderings (0x00849CAC..0x00849CF4). Input is p=(66,0,0), but the engine still executes zero products/additions, including their exceptional-value effects.
7. PreMultiplyBy, 0x0084AC78..0x0084ACA4: copy second q as left operand, multiply by first q as right operand, then copy result back. With left `(w1,x1,y1,z1)` and right `(w2,x2,y2,z2)`, f64 product at 0x00849EF4..0x00849F8E is `w=((w1*w2-x1*x2)-y1*y2)-z1*z2`; `x=((w2*x1+w1*x2)+y1*z2)-y2*z1`; `y=x2*z1+(w2*y1+(w1*y2-x1*z2))`; `z=w2*z1+((x1*y2+w1*z2)-x2*y1)`. Normalize by step 3. Translation was already written before this operation.

ADP-1 does not apply to this geometry. Imported phone `cosf`, `sinf`, `ceilf` and fallback `sqrt` bodies are outside the shipped engine; their function implementations have the existing system-library equivalence boundary, while all operand bits, width changes, decisions, operation order and engine arithmetic above remain exact obligations. No emulator/PCM or hardware test was run or claimed.

Allocation at 0x0062496E and copy at 0x0062498A precede linking at 0x0062499A..0x006249A8. ## Map and light boundaries reached by this chain

The directly called map dispatcher 0x0067EA90..0x0067EC52 does:

- Family at object+0x48 equal 6: immediate return before state handling.
- Old Invalid=0, current nonzero: AddObservableObject(obj,currentPose).
- Current Invalid=0, old nonzero: RemoveObservableObject(obj,oldPose.GetRootID()).
- Both Invalid: log/error branch shown above.
- Both nonzero: ensure object-ID outer map entry (+0x20), look up **current** pose root ID in its inner map. Missing root entry adds current pose. Existing entry constructs angle tolerance `0x3E32B8C2` and, when cached valid byte node+0x20 is nonzero, compares pose against cached node+0x14 with translation tolerance (5,5,5), bits `0x40A00000` (0x0067EBAA..0x0067EBF8). IsSameAs true returns without remove/add. Otherwise virtual +0x5C result==1 first removes the current root's old map contribution, then adds current pose; other result skips remove and still adds.

This is the dispatch contract, not a claim to have recovered rasterization. It shows why the subsequent state-change tail's possible second map call cannot simply be deduplicated: the first call can mutate map caches that control the second. The second call supplies currentPose where the first supplied oldPose. All this occurs before any cube-light callback.

Cube-light trigger selection is based on **new** state, because the callback's r2 is old and r3 is new. PlayLightAnim layer 2, trigger 0x25 for Known=1, otherwise trigger 1; empty completion function and cleared modifiers. The playback selector/stack/framing is an M4 boundary, not a new choice to make in the manipulation layer.
