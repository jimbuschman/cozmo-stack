# R-VIS M11-vision, gap pass 1 - extraction

Scope: the eight questions in the manager brief plus the M11-035 leftovers. Source: `resources/lib/armeabi-v7a/libcozmoEngine.so` only (Thumb-2; all first-party code is Thumb: the even-address ARM-mode exports start at 0x8FC244 and are the Okao face library). Record text was re-read from `re-analysis/fidelity_manifest.json` for M11-004, 007, 013, 035, 037, 038, 040. Earlier verifier reports are cited as v1-3, v4-5, v9-10; every address I rely on was re-read here. Scratch: `.scratch/r1929/` (bytescan.py, gotref.py, bscan.py, strs.py, ven.py, d.sh). I read, but did not write, `.scratch/rv/text.asm` (a linear disassembly another job produced); no conclusion rests on it alone.

Notation: veneer = ARM stub in 0x8C....; `[x+0xNN]` is a field offset. ObjectID is 8 bytes: word 0 is a vptr, value at +4; inside an ObservableObject the ObjectID is at +0x14 (value +0x18), timestamp +0x1C, PoseState byte +0x24, activeID +0x40, factoryID +0x44, family +0x48, type +0x4C.

## Q1. PoseState / pose / ObjectID writes on the observation path

One line: none of LocalizeRobot, LocalizeToObject or UseDiscardedObservation writes a located object's PoseState, pose or ObjectID directly. The writers on this path are (a) UpdateObjectOrigins' first modify function (CopyWithNewPose: pose + PoseState copied from the moved object; ObjectID copied; clones created) and (b) AddVisualObservation, reached from UseDiscardedObservation, which leads to UpdatePoseInInstance (rows 3.4-3.9 of v1-3).
