# Implementation candidates

These five proposals are ordered by expected user benefit. They are research artifacts for operator review, not authorized jobs. References use repository-relative paths. Cozmo revision `1bd44f259ee4d4c75ee6182c75a25920669e4d86` and Reachy conversation app revision `622a3a67582a1eb45c82b51251fa9f61a999b51d` were inspected. Recheck the live queue, branches, code and hardware evidence before opening any future work. Historical overlap is listed in `improvement-roadmap.md`.

## Common constraints and evidence

Original-engine behavior and observable exactness remain authoritative. Host additions should be switchable and, if integrated as C2 extensions, follow `CozmoC2Settings`, named extension logging and explicit isolation (`cozmo-stack/src/Cozmo.Robot/CozmoC2Settings.cs:7-29,125-140`). MCP's default enables named C2 extensions, while `--baseline` disables them (`cozmo-stack/src/Cozmo.Mcp/CozmoGuide.md:20`). Compare baseline before and after at the same revision and inputs, with all new features disabled, and run existing fidelity and relevant integration tests. Native reactions, action admission and safety retain control. Existing reconstructed systems stay in place, and Cozmo retains native autonomous operation when the provider is unavailable.

Reachy's background task manager and result callbacks are evidence for the value of asynchronous outcomes (`src/reachy_mini_conversation_app/tools/background_tool_manager.py:127-193`, `src/reachy_mini_conversation_app/huggingface_realtime.py:849-918`). Its movement constraints, server dependencies and hardware differ. Direct code reuse is not assumed. The app's Apache-2.0 license is documented at `LICENSE:1-3,89-108`, while compatibility with the destination and third-party assets remains to be determined.

## RC-01 — Correlate and verify intent outcomes

**Scope and motivation.** Build a host-side session record connecting a user intent to existing native admission receipts, action tags, terminal events, event cursors and action-specific postconditions. This addresses misleading claims after accepted-but-interrupted actions and native success with no observable movement. `CozmoGuide.md:10-15,37-43,49,98` already describes these distinctions, including unknown face IDs producing native success with `facePoseAvailable=false`. `CozmoMcpServer.cs:205-210` already provides state and events. Reachy correlates a tool call ID to a result and manages asynchronous status (`huggingface_realtime.py:1178-1213,849-918`). Its result can be lost after connection failure or missing `response.done`, so the pattern needs adaptation.

**Expected behavior.** Expose submitted, admitted, terminal engine result, and observed postcondition as separate states with timestamps and evidence. A queued behavior may remain selected when not runnable. A stale face, no-pose success, interrupted action, gap, disconnect, timeout or expired session must yield an explicit unknown, incomplete or failed outcome as warranted. Preserve the original native status and avoid replaying a physical action automatically.

**Affected components and dependencies.** Host MCP consumer and session lifecycle, existing `get_state`, `read_events`, action reports and native tags. Begin with face turn and charger contact, extending only where a postcondition is defined. Depends on event cursor retention and source-specific freshness, with fresh session IDs on reconnect. Existing work `HANDOFF-MCP-ACTION-WHY-1.md`, `HANDOFF-LLM-SENSES-1.md`, `HANDOFF-LLM-SESSION-FINDINGS-1.md`, `HANDOFF-FACE-TRACK-LLM-1.md` and `HANDOFF-FREEPLAY-LLM-1.md` in `re-analysis/jobs/trial-m13/` overlaps and must be reconciled first. Complexity medium, confidence high for the gap and medium for the design. User benefit is more truthful feedback and safer recovery. CPU and storage costs should be small and bounded.

**Acceptance criteria.** Exactly one intent record per submitted call and deterministic correlation to matching receipts and events. A completion cannot be called physical success without an available, fresh, action-specific observation. Retain raw native result and detail. Mark evicted events or lost connection as uncertain. Close pending records on cancellation or session expiry without claiming physical reversal. A behavior request remains subject to native chooser and reaction gates.

**Tests.** Unit test duplicate events, tag collision across sessions, stale face ID/no-pose `SUCCESS`, refusal, interruption, out-of-order or missing events, cursor gap, timeout and disconnect. Integration replay existing fixtures through actual MCP entry points and verify a reconnect cannot complete an older session's intent. Baseline comparisons and native admission tests are required. On a physical robot observe face turn with valid and stale observations, an interrupted action, and fresh charger contact where appropriate. Record timestamps, terminal evidence and freeplay state. Do not infer a pass from admission alone.

## RC-02 — Interruptible host-microphone conversation

**Scope and motivation.** Prototype a host microphone interface with explicit push-to-talk, asynchronous inference and a cancellable response lifecycle, using current Cozmo TTS and robot audio delivery. Reachy streams input and output audio (`huggingface_realtime.py:1154-1176,1275-1314`) and flushes playback on interruption (`huggingface_realtime.py:389-422`). Its experimental VAD measures still need robot tests (`README.md:124-128`). Existing Cozmo speech paths and observed delays are recorded in `re-analysis/SCOPE.md:15-23` and the `VOICE-ROBOT-DELIVERY-1` and `VOICE-ANIMATION-FIT-1` handoffs. The earlier 9–17 second onset is historical, and later offline improvement still needs hardware confirmation.

**Expected behavior.** Push-to-talk begins and ends a turn with visible host state. User cancellation stops new response submission and requests cancellation of supported active speech, reports any portion that may already have played, ignores late output for the expired turn, and permits a new turn. Existing native reaction and audio ownership continue to govern what can occur. Start with explicit control, then evaluate VAD and streaming as separate experiments. No physical mute or instantaneous silence is promised.

**Affected components and dependencies.** Host microphone capture, provider adapter, existing speech bridge and `SpeechOwner`, session lifecycle, cancellation and playback reporting. Requires RC-01-style outcomes for commands invoked in a turn and a confirmed supported stop path for speech. Do not assume a local endpoint implies independent local ASR or TTS. Complexity high, confidence medium. Benefit is more responsive interaction, while model, audio transport and echo can dominate latency and CPU.

**Acceptance criteria.** The host exposes recording, waiting, playing, cancelling and terminal states. At most one active user turn owns output. Repeated cancellation is safe, stale audio and tool replies cannot enter a new turn, disconnect returns a visible terminal state, and native freeplay remains available on inference failure. Report measured capture-to-first-audio, cancel-to-last-audible output and resource use with hardware and provider configuration.

**Tests.** Simulate late chunks, repeated cancellation, disconnect, provider stall, overlapping requests and audio owner refusal with actual bridge entry points. Compare baseline when disabled. On the robot test quiet and noisy rooms, microphone proximity, speaker feedback, long responses, cancellation during synthesis and during already-buffered playback, and freeplay/reaction interruption. Report distributions and failures rather than asserting latency from a single trial.

## RC-03 — Bounded turn context

**Scope and motivation.** Create a host-side turn snapshot from existing activity, reaction, needs, recent face/object observations and significant events. `CozmoGuide.md:5-11,102-120` describes existing timestamped state and event cursors. Reachy builds profile and memory into session instructions and attaches a camera image when its tool is called (`prompts.py:36-70`, `tools/camera.py:38-56`, `huggingface_realtime.py:929-950`). The adaptation is a bounded event-derived view of Cozmo, not a new perception or mood system.

**Expected behavior.** Each user turn gets a size-limited snapshot with source timestamps, age, current origin where relevant, explicit unavailable values and event gap indicators. Preserve significant changes and compact repeated observations using existing event feed semantics. Native needs remain the source of truth, and fresh information replaces stale context. A model can ask for an on-demand observation when relevant.

**Affected components and dependencies.** MCP state/event client and host context builder. RC-01 is recommended first so current action outcomes are reliable. No direct memory-map control or new robot sensors are required. Existing `HANDOFF-LLM-SENSES-1.md` and `HANDOFF-LLM-EVENTS-REPLAY-1.md` overlap this scope. Complexity medium, confidence medium. The benefit is replies grounded in activity without excessive tokens or repeated sensory updates. Context size and latency require measurement.

**Acceptance criteria.** A stable schema contains current activity, reaction, available needs, selected recent observations and bounded significant events with provenance and timestamps. Old or absent data cannot be labeled current. Cursor gaps are visible, event repeats are bounded, and invalid cross-origin positions are excluded or marked unavailable. The model cannot alter native needs, emotion or behavior by writing the snapshot.

**Tests.** Unit test limits, ordering, time expiry, null values, stale recognized face, identity remap, origin change and cursor gap. Replay real event fixtures and ensure repeated sightings do not grow unbounded. Run baseline parity with the feature disabled. On hardware compare snapshot timestamps and facts with recorded state during freeplay, tracking, reaction and provider outage, including a deliberate camera pause.

## RC-04 — Optional native listening and waiting acknowledgement

**Scope and motivation.** Request a short existing native animation or behavior on explicit listening and inference-wait states, subject to native admission and resource constraints. Reachy's listening state suppresses breathing and its gestures yield to competing primary moves (`huggingface_realtime.py:332-342`, `moves.py:301-306,335-345,390-406`). Cozmo already has native activity selection and reactions (`cozmo-stack/src/Cozmo.Robot/Behavior/BehaviorManager.cs:640-750,1011-1040`) and a behavior request API (`cozmo-stack/src/Cozmo.Mcp/CozmoGuide.md:12-15`).

**Expected behavior.** An enabled extension requests an appropriate short acknowledgement on a state transition, never a repeating motor loop. It skips when unavailable or conflicting, releases or cancels only its own admitted work, and responds promptly to native reactions. Verify any resumption of freeplay rather than assuming it. Acknowledgement makes Cozmo appear attentive without inference for each motion.

**Affected components and dependencies.** Host turn state from RC-02, existing behavior/animation bridge and native action tags from RC-01. Choose authored assets and compatibility through tests. Avoid head or body contention with tracking, pickup, cliffs, speech or reactions. Complexity medium, confidence medium-low until hardware test. The primary cost is admission contention and potentially distracting motion.

**Acceptance criteria.** Feature off by default for baseline, explicitly named when enabled. One bounded request per transition, no direct actuator bypass, no retry loop, and no acknowledgement on an expired turn. A refusal is observable and treated as a normal skipped acknowledgement. No new persistent emotion or motivation state is introduced.

**Tests.** Unit test transitions, duplicate signals, admission refusal, cancellation races and session expiry. Integration tests exercise resource conflicts and reaction priority. Compare baseline with disabled feature. On a physical robot evaluate speech, tracking, freeplay, pickup and cliff/reaction conditions in a safe test area, verify that no motion blocks a reaction and record whether native freeplay actually resumes.

## RC-05 — Consented durable preference recall

**Scope and motivation.** Add an optional host-local store for a small set of explicitly approved stable preferences. Reachy's `remember` tool stores a short fact and its prompt incorporates stored facts (`tools/remember.py:12-52`, `memory.py:18-23,147-169`, `prompts.py:68-70`). This is evidence of a bounded fact store, not a verified personal identity or a learned personality system. Cozmo's existing face identity and native needs remain separate (`cozmo-stack/src/Cozmo.Mcp/CozmoGuide.md:72,117-118`).

**Expected behavior.** Ask for explicit approval before saving each preference, show what was stored, allow inspection and deletion, and inject only relevant approved facts with provenance into future context. A face name is not sufficient authorization to bind a preference to a person. Operate initially as an explicitly selected local profile with memory disabled until opted in.

**Affected components and dependencies.** Host profile selection, preference store, consent interaction and RC-03 context builder. No writes to face album, native mood or needs. Recheck whether another memory implementation already exists in the current checkout before starting. Complexity medium, confidence medium. Benefits accrue across repeated sessions, and CPU cost is small. Persistence introduces identity ambiguity and data lifecycle responsibilities.

**Acceptance criteria.** No persistence before explicit approval, bounded record count and length, clear profile association, inspect/delete and full clear, explicit disable switch, and deterministic behavior on corrupt or inaccessible storage. Deleted entries no longer appear in new contexts. Uncertain identity must not silently select another person's profile. No claim of retroactive removal from an external provider's logs.

**Tests.** Exercise refusal, duplicate approval, profile switching, deletion, corrupt file, concurrent save, restart, size bounds and cancellation before confirmation. Check baseline parity with feature disabled. On hardware walk through consent, reconnect, a distinct profile and deletion, confirming native face and freeplay behavior are unaffected. No physical motion is needed to validate the store itself.
