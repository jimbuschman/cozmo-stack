- **Contradictions:** none with M10-004 (evidence "C3..C8, gap1 4a/4b/4c/4e"), M10-008 (evidence "C7, C9..C11") or M10-003's "a no-op here" for the three strategies, which is confirmed. Their `unresolved` text is now answerable from items 3 and 4.
- **Inventory row C7** (`M10-derived.md` line 144) says CompletelyUnlockAllTracks is called if any track is locked; that still holds, and the body is item 3: every non-empty lock set is cleared, whoever holds it.
- **Row C11** (`M10-derived.md` line 148) says the restore queues "MoveLiftToHeightAction" with no arguments. Now settled: tolerance 5.0f, variability 0.0f, height manager+0xC; the head action is in 4.5. Its "enable: set both / move now if the action list is empty" agrees with 4.3 and 4.4.
- **Weak evidence, M10-008:** its cited range 0x5A2BB8..0x5A2C3A shows the composition (0x5A2BB8 is the `operator new` in TryToResume) but not the skip test at 0x5A2B48..0x5A2B58 or the action-list check at 0x5A2B5A..0x5A2B66, which are the condition on which the restore runs. A record saying "restore when head and lift are set" would state the gate wrongly: it reads +8 only (4.6).
- **Open questions:**
  1. 3.5: the EnableAnimTracks payload is the track index k (0..7), and k = 0 sends byte 0. How the firmware interprets an index is not settled by any shipped artifact here. The manager decides whether to keep the byte exact and classify the firmware side HARDWARE_ONLY.
  2. 4.8: `MoveLiftToHeightAction::Init` and `CheckIfDone` were not read, so the roles of +0x88/+0x8C/+0x90 are UNKNOWN. That is enough for a record of the constructor, not of the action's runtime behaviour (M4/M5).
  3. Callers of CompletelyUnlockAllTracks other than 0x5A3610..0x5A3682 (the reaction path) were not enumerated.

### Contradictions, weak evidence, open questions (items 4 to 6)

- **Contradictions:**
  - **M5-011 `unresolved`**: "what the loader does with one that does not [exist as a clip] is not in the rows, so such entries are kept." Contradicted: the entry is rejected with an error log (4.5, `0x0058C560..0x0058C6A6`), and the group continues with its other entries (4.3, `0x0058A6CA`). Its claim that the defaults of Weight (1), Mood ("Default") and HeadAngleMin/Max_Deg (+-infinity) are "the earlier code's, not the rows'" is right, and the source has none of them: a missing or non-numeric Weight, a missing or non-string Mood, or an unrecognised Mood string rejects the entry (4.6, 4.7). HeadAngleMin/Max are required when `UseHeadAngle` is true (else the entry is rejected) and untouched when it is false or absent (4.9 to 4.11).
  - **M5-014 `unresolved`** (HeadAngleMin/Max_Deg defaults, "here +-infinity"): there is no default; the values of a `UseHeadAngle`-less entry are uninitialised and the backup rule reads them (4.11, 4.12).
  - **M5-013 `unresolved`**: "Image::Threshold(0x80) is taken as at or above 0x80" is contradicted: it is strictly above (5.1). "The index is reset to 0 when the keyframe is done" is not what the original does (5.5): the reset is lazy, on the next `GetStreamMessage` call when IsDone is already true, and that call returns no message. The title's "index reset on abort" is right (A24) but omits the two other resets and the one-frame-null behaviour: partial, not contradicted. "0 takes the even-rows-cleared one" is confirmed (5.3).
  - **M5-016 `unresolved`** ("MISSING: a colour given as a string names a NamedColors entry ... such a JSON keyframe throws NotSupportedException"): the table is now read (6.1 to 6.3), and the original does not throw or reject on an unknown name; it returns DEFAULT with a warning (6.3).
- **Weak evidence:**
  - Inventory rows D4..D6 (M5-011/M5-014) are read at the level of field names only. They never covered the rejection paths, the required-versus-optional split, the mood value-3 failure, or the uninitialised head-angle fields. Those are settled above.
  - D6 "regardless of UseHeadAngle" is right, but only fully specified for entries with `UseHeadAngle` true. For the other 766 shipped entries the window comes from uninitialised memory (4.11, 4.12), so the row's claim of a +-0.05 rad window is not by itself a defined rule.
  - C12 (M5-013 evidence) proves the two-variant storage and the `GetFrame` variant switch only now that 5.2 and 5.3 are read; before them "picks the variant by `_firstScanLine`" had no read of which variant.
- **Open questions:**
  1. The HeadAngleMin/Max value for an entry without `UseHeadAngle` is the previous loop iteration's leftover or stack garbage. Is UNKNOWN acceptable, or should a specific choice (for instance "never within the window") be named an explicit compatibility policy? It matters only when all Default entries are on cooldown, which needs the Default-mood backup path.
  2. Whether an idle or streaming animation replay re-enters the same `FaceAnimationKeyFrame` object with `idx == N` (5.5), which produces a one-frame no-message pause. Needs the `InitStream` / `GetAnimationByName` read named in 5.5.
  3. Who sets `FaceAnimationKeyFrame +0x28` (5.6), and who sets `RobotDataLoader +0x278` (which skips group loading).
  4. `GetValueOptional<bool>` semantics (4.9) were assumed, not read.
  5. Whether the reject branches after each `GetColorOptional` call (6.5) have side effects beyond returning failure.
  6. An exhaustive check that every group entry name in the shipped group JSON matches a shipped clip was not done (clips are in `.bin` FlatBuffers); it would show how often the rejection in 4.5 actually fires.
