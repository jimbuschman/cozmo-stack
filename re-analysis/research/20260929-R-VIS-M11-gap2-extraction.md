# R-VIS gap pass 2: QuadTree and the map side of M11-017

Extractor report. Read-only pass. Everything below is `libcozmoEngine.so` (Thumb) unless a row names another library. Helper scripts are in `.scratch/` (`x2.py`, `fn.py`, `wbscan.py`, `litscan.py`). Nothing else in the repo was changed.

Records checked against the current manifest: **M11-017** (IMPLEMENTATION_GAP, "The memory map's vision-derived content: the overhead edges"; its `unresolved` says Detect, GroundPlaneROI and the four MapComponent entry points are not read), **M14-007** (EXACT_SOURCE, "The memory map, and the question the face behaviour asks it before driving in"), **M11-033** (IMPLEMENTATION_GAP, "The image hand-off and the two VisionSystem::Update overloads").

## 0. Conventions and corrections up front

- EContentType (name table 0x00BFFAC8 via GOT 0x010309D0, EContentTypeToString 0x00684950): 0 Unknown, 1 ClearOfObstacle, 2 ClearOfCliff, 3 ObstacleObservable, 4 ObstacleCharger, 5 ObstacleChargerRemoved, 6 ObstacleProx, 7 ObstacleUnrecognized, 8 Cliff, 9 InterestingEdge, 10 NotInterestingEdge. `IsRemovalType` 0x00684978 is `type == 5` only. `EContentTypeToFlag` 0x00684970 is `1 << type`.
- **The address quoted for `kReviewInterestingEdges` is off by one.** Dynamic symbols: `kDebugRenderOverheadEdgeBorderQuads` = 0xC8765E, `kReviewInterestingEdges` = **0xC8765F** (size 1, file byte 0x01), `kAddUnrecognizedMarkerlessObjectsToMemMap` = 0xC87660.
- Quadrants and directions (Subdivide 0x00687BEC, table at 0x01051064, EDirectionToNormalVec3f 0x0068C538): child Q0 = (+x,+y), Q1 = (+x,-y), Q2 = (-x,+y), Q3 = (-x,-y) relative to the parent centre; the root carries quadrant value 4. Directions D0 = +x, D1 = -y, D2 = -x, D3 = +y. The enum names are not in the binary; these labels are mine.
- QuadTreeNode layout (ctor 0x0068678A, ResetBoundingBox 0x0068698C, Subdivide): +0/+4/+8 children (4-byte pointers); +0x0C centre x,y,z; +0x18 side; +0x1C..0x28 AABB (minX, minY, maxX, maxY); +0x2C and +0x54 the AABB's two diagonals as 0x28-byte LineSegments (AxisAlignedQuad ctor 0x00686890); +0x7C parent; +0x80 level byte; +0x81 quadrant byte; +0x84/+0x88 NodeContent (MemoryMapData pointer, control block). MemoryMapData: +0 vptr, +4 type byte, +8 and +0xC two u32 (both set to one timestamp on creation; TryAutoMerge takes min of +8 and max of +0xC, so +8 reads as first-seen and +0xC as last-seen; that naming is inference).
- QuadTree object (= MemoryMap+8): +0 "changed" byte (1 in ctor 0x00684C18; OR-ed with each Insert result 0x00685124..0x0068512A; set to 1 on every Expand exit 0x00685438); +8 QuadTreeProcessor; +0x50 root. Processor +0x24 = root pointer (0x00684C52).
- MemoryMap vtable base 0x01030964: +8 Insert, +0x10 TransformContent(fn), **+0x14 TransformContent(polygon, fn)**, +0x2C CalculateBorders, +0x30 HasCollisionRayWithTypes, +0x4C FillBorderInternal (slots 0x0103096C, 0x01030974, 0x01030978, 0x01030990, 0x01030994, 0x010309B0).
- **Pre-extraction row 38 correction (verifier), confirmed by me.** When the last point of a chain also breaks the run, the old run is flushed by `bne.w 0x67F9BC` (0x0067FE70), the new run is begun at 0x0067FB76..0x0067FBD0 (`str r0,[sp,#0x28]` 0x0067FBCA, `str r0,[sp,#0x2c]` 0x0067FBCE) and `b 0x67FE9C` (0x0067FBD0) skips the last-point test at 0x0067FE74..0x0067FE92, which is reached only when the point did not break the run. The final segment of such a chain is dropped.
- The polygon Transform is **not** `QuadTreeProcessor::Transform 0x68A414`. `MemoryMap::TransformContent(polygon, fn)` 0x0068147C builds a FastPolygon and calls `QuadTreeNode::Transform 0x00688378` on the root (0x00681522). `QuadTreeProcessor::Transform 0x0068A414` is the whole-map overload (vtable +0x10).

## 8. Existing records: contradicted, too weak, or misleading

**Contradicted by the source**
- **M11-017, evidence paragraph 4** ("the engine carries its regions in a quad tree subdivided to ten millimetres ... this keeps the polygons ... neither observable in what the map answers"). The tree is not a coarser store of the same regions. Rows 1.12, 1.17, 1.19, 3.3: a polygon writes every 10 mm cell it touches (overlap 1 or 3), so answers change at cell scale; ClearOfObstacle overwrites obstacle and edge cells only when they are fully inside the polygon; `HasCollisionRayWithTypes` is true for any touched cell of a matching type; an existing cell's +0xC stamp is refreshed even when its type is not overridden (1.16); a 2x2 merge takes min/max stamps over three of the four children (1.22).
- **M14-007** is right about the mask fold and the -15 mm back-off, but its sentence that the stack "answers the same ray exactly rather than to the tree's precision" describes a difference that rows 3.2-3.3 show is observable (10 mm cell quantisation).
- **M11-017, evidence paragraph 3** ("transforms the content inside the ROI ... turns type 9 into type 0"): source (2.2, 2.3) converts every type-9 leaf the ROI touches, whole, including the part outside the ROI.
- **M11-017, evidence paragraph 2** ("an interesting edge touching one of the masked types ... is written off as NotInterestingEdge"): source (4.3-4.6) marks nodes reached by the border walk through their centre point; for a merged block only the four level-0 cells at its centre change (4.6 is derived, not executed).
- **Pre-extraction row 38**: wrong, corrected in section 0.
- **Task premise**: the polygon Transform is `QuadTreeNode::Transform`, not `QuadTreeProcessor::Transform`.
- **Address**: `kReviewInterestingEdges` is 0xC8765F.

**Too weak to keep a status**
- **M11-017** stays IMPLEMENTATION_GAP. It cannot become EXACT_SOURCE while rows 1.10 (ShiftRoot), 1.12 / 3.4 (`LineSegment::IntersectsWith`), 4.3 / 4.4 (border walk), 5.4 (+0x50), 5.6, 7.2 and 7.4 stay open. Its `unresolved` text (Detect, GroundPlaneROI, the four entry points unread) is out of date against the pre-extraction, and does not mention the tree at all.
- **M14-007** (EXACT_SOURCE): evidence proves the mask fold (0x0068176E) and the caller only. The quad-tree insert and ray walk it relies on had no record before this pass.
- **M11-033**: "the colour branch is inert for the shipped grey camera" rests on the encoding byte, not on a shipped config; the colour format is HARDWARE_ONLY per AGENTS.md.
