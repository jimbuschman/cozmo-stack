## Checked path and why it must be gated

B-M1-8 check B1 traces the newly live path on every production connection:
engine Init creates NeedsManager -> mfgId connection read 0x194000 -> FinishReadFromRobot ->
InitAfterReadFromRobotAttempt -> either apply robot state plus persistence decay, or StartWriteToRobot.
The checked native clock is system_clock epoch time (resolver 0x00694D9C, stamp 0x006954F8, division
0x0069555C), while engine Init/Update use BaseStationTimer f32 (0x004EC9DE,0x004ED636).
The checked native write packs manager economy fields at 0x006955F2..0x0069560C. Current code substitutes
engine seconds for the epoch timestamp and leaves those fields zero. This is an implementation/source join defect,
not a source-authorized default-zero policy.

Checked consequences are different and require both sides of the gate:

- No robot blob (case 1), older v1-4 rewrite, or device-newer case 8 can start an NV erase/write of 0x194000.
- A usable v5 robot copy, especially case 5 without a host device file, can apply its epoch DateTime and calculate
  a large negative elapsed interval using engine seconds (native elapsed 0x00695304..0x00695330). It changes
  levels/deadlines that feed needs reporting, even if that particular v5 path does not rewrite robot flash.

The job explicitly authorizes temporarily skipping this connection persistence until its owners are built.
It does not authorize replacing the missing fields or the clock with plausible values.
