## Item 4: two conflicts to re-check

**Atomic retry is not a second progress milestone.** The job says
"per-file 0.7f/N skipped for a failed file, +0.2f twice, 1.0 last".
The adopted OV125/126 check's "Progress writers" says
"+0.2f twice (0x0051F3F2, 0x0051F424; 0x3E4CCCCD)".
Both calculations belong to one atomic addition. Direct native re-read of the complete 0x0051F3D2..0x0051F448 sequence
in `libcozmoEngine.so` shows:

- 0x0051F3F2 computes old+0.2, 0x0051F3FA attempts the store.
- On success, 0x0051F400 executes the barrier, 0x0051F404 sets r2=1 and 0x0051F406 jumps to 0x0051F412.
- **0x0051F412 cbnz r2,0x0051F44A bypasses the entire second calculation after success.**
- If the first compare/store failed, 0x0051F414 reloads, 0x0051F424 computes the same addition, 0x0051F42C retries the store.
  Failure loops at 0x0051F448 back to 0x0051F414; successful retry exits.

Thus this range publishes one successful +0.2 operation, with an exclusive retry loop. It does not publish both additions
successfully in one call. This is a contradiction in a checked row, not permission for this preflight to rewrite the job
or manifest. Manager should re-check the branch and correct the checked instruction before the dependent item is built.
The original OV125 answer described one addition, but that answer alone is not substituted for adoption here.

**"Failed file" is too broad.** Current **M5-001, IMPLEMENTATION_GAP**, title
"Clip loading: FlatBuffer fields 0..9 in engine track order, first rejected keyframe truncates, JSON clips named by their first key, the two animation directories",
has checked evidence including `20261011-m5-settling-pass.md`, `20261011-m5-fix-rows.md` and
`20261012-m5-x9-extraction.md`. Its current unresolved explicitly states:
"JSON open/read/parse exceptions take DataPlatform.readAsJson failure/error-flag and continue to loading progress
(0x0084C0E6..0x0084C120, 0x00521470..0x005214A8, 0x00521686)."

That conflicts with applying "skipped for a failed file" to all failed files. The adopted summary cites r6's gate at
0x00521684, which does skip particular flatbuffer/error paths. It does not authorize suppressing the ordinary failed-JSON
progress tail. Native 0x00521470 branches to JSON cleanup at 0x005214A2; 0x005214A8 branches straight to 0x00521686.
The manager should distinguish those tails. How a host loader surfaces a fatal stack loading failure remains the approved
failed-readiness policy; it must not be confused with native per-file progress bookkeeping.

**Comparison wording:** 0x005235A2/0x005235AA is a VFP comparison followed by BMI, so ordered progress <1 returns zero,
while unordered/NaN does not take BMI. The job asks to preserve the native comparison and is therefore supportable;
the check's shorthand "join only at >=1.0" should not be turned into a different NaN branch. Current normal writers do
not imply a need to invent NaN milestones. Keep any reachable host failure behavior under the existing failure policy.
