## Part 1, item 3 (M3-001 / M3-018: the JPEG codec the engine reaches)

All addresses are file addresses. In `libopencv_imgcodecs.so` (imgcodecs below) they are also virtual addresses, and its code is Thumb (odd symbol values). `libcozmoEngine.so` (engine) call sites are Thumb; the engine's PLT stubs are ARM.

### Short answer

- The engine's JPEG decode and encode both go through OpenCV 3.1.0's `libopencv_imgcodecs.so`.
- That library contains its own statically linked, stripped **IJG libjpeg 9 (13-Jan-2013)**, not libjpeg-turbo. `JPEG_LIB_VERSION` is 90 and the decompress struct is 0x1e8 bytes.
- The decoder runs with `dct_method = 0` (JDCT_ISLOW), `do_fancy_upsampling = 1`, `do_block_smoothing = 1`, `scale 1/1`. OpenCV never overrides them.
- The encoder runs with quality from the caller (via `jpeg_set_quality(q, force_baseline=TRUE)`), `dct_method = 0` (ISLOW), `optimize_coding = 0`, `smoothing_factor = 0`. OpenCV does not set the sampling factors; the IJG default of 2x2 luma (4:2:0) is expected from the library source, not read in the binary.
- Bit-exact decoding is reachable in principle. It needs a port of libjpeg 9's scalar `jpeg_idct_islow` (8x8), `h2v1_fancy_upsample` and `ycc_rgb_convert`.
- Two things were not read in the binary: the decode-side dispatch to the 8x8 ISLOW function, and the sampling and DCT-scaling choice on the encoder.

### Libraries that ship, and where the JPEG symbols live

- The 26 `libopencv_*.so` files plus `libtbb`, `libc++_shared`, `libunity`, `libmono` and others are in `resources/lib/armeabi-v7a/`. `libcozmoEngine.so` lists all the OpenCV libraries as DT_NEEDED, including `libopencv_imgcodecs.so`.
- The engine imports only four JPEG-related OpenCV symbols: `cv::imdecode(InputArray,int,Mat*)`, `cv::imencode(...)`, `cv::imread` and `cv::imwrite`. It imports no `jpeg_*` symbols.
- A dynamic-symbol scan of every shipped `.so` shows only `libopencv_imgcodecs.so` defines those four symbols (`imdecode` at 0xfac5 and 0xfb21, `imencode` at 0x1112d). It has no `jpeg_*` imports or exports and no DT_NEEDED libjpeg; its NEEDED list is imgproc, dl, log, z, core, tbb, m, c++_shared, stdc++ and c. The JPEG strings are inside it.
- A byte scan of all shipped `.so` files for "Wrong JPEG library version" finds two: `libopencv_imgcodecs.so` (the one the engine reaches) and `libunity.so` at 0xfbfb5f. The latter's copyright strings at 0xfc0413..0xfc04cb include "2009-2014 D. R. Commander", so it is libjpeg-turbo. It serves the Unity `Texture2D.LoadImage` viewer (row A26) and never the engine's path; it is named here only as an interface.

### Contradictions, weak evidence, open questions (item 3)

- **Contradictions with M3-001 and M3-018:**
  - The `unresolved` text says "The JPEG entropy decode is StbImageSharp in place of OpenCV's libjpeg (last-bit pixel differences possible)". That is consistent with the source: the substitution is real. The source also says exactly what the original library is (libjpeg 9, ISLOW IDCT, fancy upsampling), so the codec is recoverable. Whether stb matches libjpeg 9's ISLOW arithmetic is not judged here; only a port of the routines above would be exact.
  - M3-018's title and `provenance` describe "encoding 9 decoded from the half-width colour JPEG as RGB". The source has two different encoding-9 paths: the gray path (A8) decodes it with imdecode flags 0, which gives Y only with no chroma upsampling (0x4f28c6.. and the gray branch at 0x15bfc..0x15c04), and the colour path (A9) decodes it with flags 1, which gives RGB with fancy upsampling. The record covers only the colour path; under the rules, the gray consumer needs its own row or record.
  - M3-018's evidence "Save writes quality 90 ... others raw" is correct as far as it goes. The engine also calls the same encoder for the wire (`CompressAndSendImage`) and the calibration and tool-code images, and the record does not cover those callers.
- **Weak evidence:** M3-018's statement that resize and BGR-to-RGB are "exact ... on every OpenCV path" was not re-checked here. The decode itself (the libjpeg 9 IDCT and upsampling) has no record for which C# arithmetic is required. M3-001 A11 (`rows==240, cols==320` check) sits on top of a decode whose arithmetic is unverified; the header and 240x320 check evidence is independent of the codec.
- **Open questions for the manager:**
  1. Which JPEG paths need bit-exact decode? The gray path (encodings 5, 6, 7, 8, 9 via flags 0) needs only the Y channel's `jpeg_idct_islow` plus `range_limit` and no upsampling. The colour path (encoding 9 via flags 1) also needs `h2v1_fancy_upsample` and `ycc_rgb_convert`. Decide whether the gray-only port is a separate step.
  2. Decode-side dispatch not read: the `start_pass_idctmgr` switch on `dct_method` and scaled size (to prove 0x348d0 is what runs for 8x8), `jinit_upsampler` and `use_merged_upsample`, and `ycc_rgb_convert`. The extractor offers to read them if wanted.
  3. Encoder quality values not traced: `CompressAndSendImage`'s third argument (r2, kept in r6) and the qualities passed by `GetCalibrationImageJpegData` and `GetToolCodeImageJpegData`. Only `EncodedImage::Save`'s 90 is recorded (A25).
  4. Encoder subsampling and DCT-scaling behaviour need `jpeg_set_colorspace` (0x1f18c) and the compress-side `start_pass_fdctmgr` (0x2a780..0x2a8ff) read before anyone claims the saved file's chroma layout or byte exactness. The FDCT tables include scaled sizes 1..16, so libjpeg 9's scaled-DCT chroma downsampling may be in play; not verified.
  5. `libunity.so` also contains a libjpeg-turbo. It serves the Unity viewer (`Texture2D.LoadImage`, A26), not the engine, and was not examined further.

## Part 1, item 2 (M3-001 / M3-018: image-decode dispatch for every encoding value)

All addresses are `libcozmoEngine.so` (`resources/lib/armeabi-v7a`) in Thumb unless the row says otherwise. A `blx #0x4a....` or `0x4b....` is an ARM-mode PLT stub, resolved by its `.rel.plt` slot; where a stub target is a local function, the row says so.

### Contradictions, weak evidence, open questions (item 2)

- **Contradictions with the records and rows:**
  1. **M3-001 `unresolved`:** "case 1 with a payload that is not exactly 320 x 240 bytes ... is reported as a decode failure." The original does not check the payload length (G2, Y2, Y8): cases 1 and 2 copy or convert `rows*cols` (or `*3`) bytes from the vector start. The geometry check compares the result with the constants stored at AddChunk time (`+0x18`/`+0x14`, 240/320), not with the payload, so it cannot fail for these cases. A short payload reads stale or uninitialised bytes within the reserved buffer, and a long payload is silently truncated. The only failure is a NULL data pointer in the `Mat` constructor (`cv::error(-215, ...)`).
  2. **M3-001 `unresolved`:** "encodings 0 and above 9 (outside the tbh table): each is reported as a decode failure." Confirmed as a failure with return 1, but the reason is wrong: they go to the same `UnsupportedEncoding` error path as 3 and 4, via the unsigned `bhi` (Y0, Y1, Z0, Z1).

  4. **A6** (approved row, "On decode failure it returns without calling Update(pose, cache)") is incomplete: `ImageCache::Reset` is called with the possibly empty or wrongly sized image on both success and failure, before r6 is tested (C1).
  5. **A4 step 7** (approved row, "DecodeImageGray on the spot"): the SetNextImage call has no IsColor gate, so it can see any encoding (C2).
- **Weak evidence:** M3-018's evidence names only `case 9` in "A9 RGB dispatch tbh 0x004F21AE". **Contradictions for item 4.**
1. Row 1b "Init changes none" is true for the exposure/gain fields (`+0x88..+0x9C`), which was confirmed by scanning every store in `Init`. But the row implies `Init` is inert. It also performs the whole config load and sets `+0x58`, which `HandleDefaultCameraParams` depends on. The record's "IsInitialized is taken as always true (there is no config load that can fail)" is contradicted by 4i and 4j, because the config load can fail in the ways listed.
2. Row 1g says `VisionComponent::Init` calls `VisionSystem::Init` "only after the three ImageQuality keys and the PerformanceLogging key are read successfully". That is correct, but the ImageQuality keys read there are TimeBeforeErrorMessage_ms, RepeatedErrorMessageInverval_ms and InitialExposureTime_ms; TooBright, TooDark, MidValue and the rest are read inside `VisionSystem::Init`.
3. The manifest says the constant 16 is used "because this stack does not load vision_config.json". The original does load the file, and 16 is both the file value and the .data default. The value is the same, but the mechanism differs, and so does failure behaviour (row 4c).

**Weak evidence.** Row 1g gives `VisionComponent::Init +0x10` as an initialisation flag; that is a different flag from `VisionSystem +0x58`, which is what the DefaultCameraParams handler tests. A record claiming the handler's gate needs row 4i. Row 1o and the record claim "the engine never requests DefaultCameraParams"; that was not re-checked.
