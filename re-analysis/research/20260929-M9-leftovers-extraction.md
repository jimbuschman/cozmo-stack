# M9 leftovers: M9-013's music-track-to-target hop and M9-024's owner field

- **Answers:** `re-analysis/research/requests/20260929-M9-leftovers.md`
- **Date:** 2026-09-29
- **Kind:** independent extraction. Two read-only extractors, one per question. The manager checks the citations before any row goes into an inventory.
- **Native code:** `resources/lib/armeabi-v7a/libcozmoEngine.so`. All addresses below are ELF vaddrs in **ARM mode, not Thumb**. Both extractors found no PLT hops or veneers on these paths (direct `bl` inside `.text`).
- **Not verified by me:** every citation is the extractors'. Two things were not read (see "Weak evidence").

## Short answers

1. **M9-013 hop.** There is no function that resolves property 56 per event. The target is resolved **once, at Init of a dedicated MIDI playback instance (PBI)**, cached at `PBI+0x34`, and every 0x80/0x90 event of that PBI is delivered to it by a per-frame loop. The chain is in Part 1, rows 3 to 16. Two inputs stay UNKNOWN: which loader writes the property bundle at `track+0x3c`, and the bank flag value for object 110896138.
2. **M9-024 owner field.** `voice+0x20` is zeroed by the constructor and written by exactly one instruction, from `event+8`. On the MIDI note path `event+8` is the holder's note-state object, so **`voice+0x20` is non-null for a note-on with velocity above 0, and for a note-off that pairs with an earlier note-on. The direct attached-voice stop loop (`0x009F4A64(...,4)`) is then not the branch taken; the owner branch is.** It is null, and the direct loop is taken, for an unpaired note-off and for every non-MIDI play. Whether the singing note-off pairs depends on the shipped MIDI data and was not traced. The two questions meet: Part 1 supplies the missing link that Part 2 could not find (see "Joining the two").

## Joining the two

Part 2 could not prove that the singing MusicTrack's events reach `0x00A3DB48` (its step 15) and named the holder-insert routine `0x00A71138` as having no direct callers. Part 1 supplies that link:

- Part 1 rows 9 to 14 show a MIDI PBI's queued events drain through `0x00A71B34` to host post `0x00A70D90`, which builds the holder records through `0x00A3E2C0` and `0x00A3E460`, then fires them through `0x00A3E688` to `0x00A3DB48` and `[target]+0x128`.
- Part 2's `0x00A3E460` call site `0x00A70EF4` (row 11) lies inside `0x00A70D90` (row 12 of Part 1, `0x00A70D90..0x00A71134`).
- So a singing track whose source has plugin high half `0x0010` does enter through `0x00A3DB48`, and `0x00A71138` is the tail of the same routine, not a separate one. This is an inference from address ranges across the two reports; neither extractor stated it. It should be checked by disassembling the end of `0x00A70D90`.

If that holds, the answer to question 2 for the singing voices is: `voice+0x20` is the note-state object for a note-on, and for a note-off it is that object only when the pairing at row 12 matches; otherwise it is null.

## Contradictions with earlier research files

- `20260929-M9-013-014-midi-routing-velocity-extraction.md` row 2 says the target is named by the track's inherited music setting and each parsed track event is submitted to it. The source shows resolution once at PBI Init (`0x00A3CBE0` to `0x00A70528` to `0x00A3BDFC`), cached at `PBI+0x34`; a PBI with property-56 ID 0 or a failed lookup returns 2 from Init (`0x00A3CC48`) and never runs. Also only status 0x80/0x90 events reach the target; CC and bend become RTPC updates (Part 1 row 13).
- `20260929-M9-024-note-off-envelope-extraction.md`, row "Direct attached-voice stop path", says cleanup takes the direct loop when there is "no alternate owner at `+0x20`". The gate is right; the premise that `+0x20` is usually null is not established. For MIDI-note voices `+0x20` is the note-state object, so the direct loop is not the branch taken. Its "Open question 2" is answered by Part 2 row 15.
- `20260929-M9-024-default-addendum.md` was not in the tree and could not be checked. It only concerns the `0x009D7EA4` gate.
