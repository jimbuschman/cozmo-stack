# live-bodies-3 (job B-M6b-4): streaming layer, source stream bodies, mix rate and frame count

> **Status (manager, 2026-10-03): UNVERIFIED.** Saved verbatim from the cozmo-extractor's scratch file. A verifier checks the rows before any inventory correction adopts them.


Everything below is read from `resources/lib/armeabi-v7a/libcozmoEngine.so` (capstone ARM and Thumb on the `.so` bytes). Nothing was executed or emulated. My scripts are in `...\scratchpad\lb3` (`base.py`, `dx.py`, `callers.py`, `refscan2.py`, `q.py`). Nothing under the repo was touched.

## 0. Method and limits

- Vtable slots were read as in-place words and checked against the dynamic relocations. Each slot cited (0x103E160, 0x103E168, 0x10392D0.., 0x1038520.., 0x1038548.., 0x101BE18.., 0x103D868, 0x1039170) is `R_ARM_RELATIVE`.
- Callers come from a sweep of every `bl/blx/b` in Thumb 0x4DE000..0x95E000 and ARM 0x95E000..0xAE3000, plus PLT-stub scans. The Thumb scan was tested on a known global (the stack canary 0x103E84C: hits found).
- Result codes are raw numbers. Names such as "DataReady" are my inference from the SDK; numbers and branches are exact.
- Float constants are given as bits: `1.0f = 0x3F800000`, `380.0f = 0x43BE0000`, `1000.0f = 0x447A0000`.
- A `0x3F` used as a character (the `?` split in `std::getline` at 0x8DE0C4) is not the result code 0x3F.
- Not read (section 12, open question 5): the I/O memory manager (buddy allocator and stream cache), the Vorbis block decoder and codebook cache, the WAVE header walker `0x9CD340`, the ADPCM stream class bodies.

## 10. Where 0x3F is produced and consumed, and how it is retried

**Production** (`mov rN,#0x3f` in ARM, stream path): 0xA54570 (`NotReadyCheck` 0xA544BC), 0xA74D08 (F5: GetBuffer 0x2E, or a non-1 result of vt+0x78), 0xA750A4 and 0xA75354 (F6 gate), 0xA7537C, 0xA75648 and 0xA75670 (F7 gate), 0xAB1FA0 (G3: `[S+0x44] == 0` at entry, also reached from 0xAB1E44 on 0x2E), 0xAB20F0 (G2: GetBuffer 0x2E), 0xAB21B8 (G2: header state machine returned 0x3F with no data left), 0xAB261C and 0xAB2668 (G1 gate), 0xAB2D4C (G4 gate). The other `mov #0x3f` hits (0x9F73E0, 0x9F744C, 0x9F7C38, 0xA97BDC, 0xA97E4C, 0xA9879C) are constants of unrelated code.

**Consumption** (`cmp rN,#0x3f`): 0xAB218C (G2), 0xA74CD4 (F5: loop again), 0xA52C1C, 0xA544E4, 0xA554FC, 0xA5591C, 0xA55ACC (the StartStream callers; existing rows C27, C30, C31.5 R5.2..R5.6), 0xA430BC and 0xA431C0 (voice attach: AddSrc 0xA558AC returning 0x3F links the voice into the list at `[0x108DA2C]` (0xA43130..0xA4315C) and returns 1; `0xA544BC` returning 0x3F returns at once, 0xA431C4), 0x9D39E4 (voice list: `0xA431A8` returning 0x3F sets r6 = 1; any other non-2 result sets bit 0 of byte `[x+0xD]`). The other `cmp #0x3f` hits (0xA71894, 0xA914F8, 0xA91518, 0xAB63A8) are unrelated.

**Retry.** No source-class loop retries a 0x3F except F5 (re-GetBuffer) and the header state machine, which resumes on the next call from its saved state (`[S+0x68]`, `[S+0xE8]`, `[S+0xEC..0xF8]`). The real retry is the voice pass: `0xA56650` (existing row R5.1) leaves the latch (bit 0 of `[S+0x10]`) clear for any result other than 1, so the next voice pass calls StartStream again; the caller arms are in C31.5 R5.2..R5.6. `NotReadyCheck 0xA544BC`: result 0x3F with `[r1+0x1D8] >= 0` returns 0x3F; with it negative, 0xA54580 (bit 1 of `byte[[voice+0xD4]+0x10]` set returns 0x3F; the rest continues past 0xA54590, outside this extraction).

**Whether StartStream returns 0x3F for shipped Vorbis data.** For a sound with a DIDX prefix the first StartStream returns 1 (G1, has != 0) unless the prefix ends before the seek table and setup packet. I checked this for all 1891 Vorbis wems that have a DIDX entry (fmt chunk size 0x42, the field at fmt+0x28 read as the setup packet offset relative to the data chunk, as ww2ogg does; this layout is my assumption, the runtime parse 0x9CD340 is unread): `dataStart + setupOffset + 2 + setupSize` is at most 5504, the shortest DIDX prefix is 514, and the prefix covers it in **every** case (0 of 1891 short). So for those sounds a 0x3F from StartStream arises only through `0xAB2088` after a start offset (bit 7 of `byte[pbi+0x1BD]` makes `0xA7482C` report "no prefetch") or for sounds without a prefix. The buffering gate (G4, the G1 tail, the gate in G7) is inactive on the prefix path because bit 1 of `[S+0x10]` is only set by `0xA74A8C`, `0xA74C80`, `0xAB2088`. For those sounds timing shows up later, as the status 0x2E of G7 when the prefix is used up before the first read has completed (that read starts at the prefix length).
