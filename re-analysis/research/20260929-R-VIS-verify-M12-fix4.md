# Verifier report: R-VIS M12 round 4 (FlipBlockAction only)

Verifier: cozmo-verifier (read-only), 2026-09-29. The full report came back as text; this file is the manager's transcription. The verifier disassembled `FlipBlockAction::CheckIfDone` (0x0055F074..0x0055F208) and the destructor (0x0055ED54) itself. **VERDICT: FAIL.**

## Objections

1. **`FlipBlockAction.cs:88-93` and `:145`: the queued carry lift is not part of the compound (behavioural).** The C# comment reads "the carry-height lift CheckIfDone queued IN_PARALLEL belongs to the same compound"; `RunEmbeddedCompound` then awaits `_raise` and replaces a successful drive result with `LiftFailureResult(o)`. The engine queues the lift on the robot's `ActionList`, not on the embedded compound at +0x80: 0x0055F160 `ldr r0,[r0,#0x250]` loads the robot's ActionList; 0x0055F164 `movs r1,#5` sets the position; 0x0055F166 `mov r2,r5` passes the action; 0x0055F16A `blx ActionList::QueueAction`; 0x0055F174 `mov.w r5,#0x1000000` and 0x0055F178 `b 0x55F204` then return RUNNING. The destructor confirms the lift is independent of the flip's outcome: 0x0055ED6C loads `[this+0x13C]`; 0x0055ED70 `adds r0,r1,#1` and 0x0055ED72 `beq` skip the cancel when the id is -1; 0x0055ED76 `ldr r0,[r0,#0x250]` and 0x0055ED7A `blx ActionList::Cancel(unsigned)` cancel the lift. `re-analysis/inventory/M13-navigation.md:1761` says the same ("the +0x13C row cites 'The destructor 0x0055ED54 cancels that id on the robot's ActionList'"). Effects of the engine's behaviour: the flip never waits on the lift; the flip's result is the compound's result only; a lift still unfinished when the flip ends is cancelled. The C# does the opposite: after a successful drive it waits for the lift, up to `LiftWaitStandIn` (5 s); it can turn a successful flip into 0x04000004, 0x03000016 or Timeout; it never cancels the lift. M13-028 `unresolved` repeats the claim, so the manifest text is wrong too. This is an undisclosed live-path change (the 5 s stall and the changed result). The KnockOverCubes and FlipDrives tests only pass because `Idle()` acks every lift.
2. **`FlipBlockAction.cs:128`: the per-tick object lookup differs from the engine's (silent stand-in).** The C# uses `(_m.World.GetObjectById(ObjectId) ?? target)`; `GetObjectById` (`BlockWorld.cs:763-767`) also returns forgotten objects and falls back to the Init-time `target`. The engine runs `GetLocatedObjectByIdHelper(id, -1)` every tick (0x0055F090), before the RUNNING test at 0x0055F094. If the compound is RUNNING and the object is not located, the engine takes 0x0055F09C `cmp r0,#0; beq 0x55F18C`, calls `sWarningF` and returns 0x03000004 (`movs r5,#4; movt r5,#0x300` at 0x0055F1C4), so the flip fails with BadObject. The C# keeps driving, never checks for a lost object and never returns BadObject. The not-RUNNING branch with a null object (0x0055F17A `cbz r0,0x55F1CC`) warns and returns the compound's result without marking anything Unknown; the C# `MarkUnknown` is a no-op for a non-located object, so that side is equivalent.
3. **`FlipBlockAction.cs:145` and `:80`: other steps in the RUNNING branch are not modelled (undisclosed).** 0x0055F152..0x0055F154 `movs r0,#1; strb.w r0,[r5,#0x56]` sets a byte at +0x56 on the queued action (role unnamed in the repo, `M12-gap3-extraction.md:120`; `M13-navigation.md:1761` records the write). The destructor's `BehaviorManager::RemoveDisableReactionsLock` (0x0055ED88) is unmodelled (matches the counted M8 non-modelling of DisableReactionsWithLock but is not mentioned). The +0x56 write is not in the 'not modelled' list and has no counter.
4. **`NavigationTests.r4.patch`, `FlipDrivesThroughTheCubeRaisingTheLiftAndForgetsItsPose`: weak test / masking.** `Assert.Equal(flip.LiftRaised ? new[]{CarryMm} : Array.Empty<float>(), rig.LiftHeights)` passes whether or not the lift was queued (a tautology on the C# state); the comment admits it is 'a race of the rig'. The intermittent failure was handled by accepting both outcomes, not by fixing it. It is a rig artefact (the fake robot jumps to the path's end) and the deterministic `M13_028_TheCarryLiftIsQueuedOnlyWithinFortyMillimetresInThreeDimensions` theory does cover the trigger; the masking is disclosed in the comment and in M13-028. The trailing comment on the `SpinUntil` line is stale and garbled ('the rig never acks the carry-height lift ... the fake robot streams none while idle'; `Idle()` does ack lifts); the same stale comment appears in `DriveAndFlipBlockIgnoresTheFailedDrive...`. `M13_028_TheLiftMoveToleranceIsFiveMillimetres` asserts a constant against itself and `0x40A00000`; `FlipBlockAction.LiftToleranceMm` is not used by any code (`SetLiftHeightAsync` uses its own `GameLiftToleranceMm`), so the test is circular with respect to production behaviour. Expected values in `M13_028_AFailedCompoundMarksTheObjectUnknown...` (Timeout) and `..._ALiftFailureReturnsTheEnginesResultCode` come from the stand-in and from `EngineResult`; disclosed as unsourced, not citation-derived.
