# B-M6b-2: the V7 `0xA54F1C` P2F==0 branch and the `0x9E9E78` seam

Read-only extraction from `resources/lib/armeabi-v7a/libcozmoEngine.so` (3.4.0-1204, ARM mode).
Every behaviour below was read from the raw instruction stream with
`re-analysis/tools/arm_disasm.py` (capstone, ARM mode); the Ghidra tree was navigation only.
Addresses are ELF VAs (`.text` VA == file offset). The existing report
`re-analysis/research/20260928-B-M6b-voice-callees.md` Q4 and the manifest M6-022 are claims,
not evidence; each row below cites the instructions.

Register names in `0xA54F1C` (from the prologue and `re-analysis/research/20260928-B-M6b-2-v7-completion.md`):
`r4`=voice, `r6`=`[source+0xC]` (called "bus" throughout the existing reports; the object is the
PBI per the source-classes pass -- see the note at the end), `r7`=params, `r5`=scratch,
`s16`=the sample count `round([params+0xC] * [r6+0x164])`, `P2F`=`[sp+0x2f]` (the byte produced by
`0xA4BC58` and loaded at `0xA5509C`), `E4`=`[voice+0xE4]`, `E0`=`[voice+0xE0]`, `N`=`[r6+0x1D8]`,
`A`=`[voice+0xCD]` bit0, `E8`=`[voice+0xE8]` bit0.

Legend: EXACT_SOURCE = step read from instructions; UNKNOWN = not established.

## 1. Control flow after the P2F branch

`0xA550C8: beq #0xa5532c` is the P2F test (`0xA550BC: cmp r5,#0` with `r5=[sp+0x2f]` loaded at
`0xA5509C`). So `P2F != 0` continues at `0xA550CC` (the four ramps) and `P2F == 0` enters the
branch at `0xA5532C`. The `P2F==0` entry resets nothing: `r5` still holds `P2F` = 0.

### Correction to `20260928-B-M6b-voice-callees.md` line 227

The verifier is right. Line 227 says:

> `0xA554A4`/`0xA5521C`: `r5=0`; `[voice+0xCD] |= 8`; return 0.

This is wrong on all three counts:
- `0xA5521C` is **not** the tail. It is the E8 gate: `0xA5521C ldrb r3,[r4,#0xe8]`;
  `0xA55220 tst r3,#1`; `0xA55224 bne #0xa553a4`.
- The real tail is `0xA5528C`: `0xA5528C ldrb r3,[r4,#0xcd]`; `0xA55294 orr r3,r3,#8`;
  `0xA55298 strb r3,[r4,#0xcd]`.
- The return value is `r5`, not 0: `0xA55290 mov r0,r5` (and `r5` can be 1 via `0xA55218`).

`0xA554A4` itself is correct in line 227 (`0xA554A4 mov r5,#0`), but it branches to the E8 gate
(`0xA554A8 b #0xa5521c`), not to the tail. The line should read:
"`0xA554A4`: `r5=0` -> `0xA5521C`; tail `0xA5528C`: `[voice+0xCD] |= 8`; return `r5`."
Note the same report already states the E8 gate correctly at line 194, so line 227 contradicts its
own line 194 and must be corrected.

**Ramp formula (raw).** Let `cur` be the field at `+0`, `tgt` the field at `+4`, `rate` the u16 at
`+8`, `coef` = 0.125 (`vmov.f32 s11,#0.125`). The body executes, in order:

```
s13 = cur                     ; e.g. 0xA55444 vldr s13,[r4,#0x340]
flag = 1                      ; e.g. 0xA55450 strb r2,[r4,#0x34b]
rate = u16[base+8]            ; e.g. 0xA55454 ldrh r3,[r3,#8]
tgt  = new_clamped_target     ; e.g. 0xA5545C vstr s15,[r4,#0x344]
s14  = tgt_old - cur          ; s14 was loaded from +4 before the store
s14  = s14 * 0.125
cur  = cur + s14 * (float)rate
store cur                     ; e.g. 0xA55474 vstr s13,[r4,#0x340]
```

So `cur_new = cur + (tgt_old - cur) * 0.125 * rate`, and `tgt` is then overwritten with the new
clamped target. `tgt_old` is the value read at the gate compare (`0xA550F8`/`0xA5513C`/`0xA5516C`/
`0xA551B0`) before the store. The four flag bytes set to 1 are `+0x34b`, `+0x51b`, `+0x35b`,
`+0x52b` (at `0xA55450`, `0xA5541C`, `0xA553E4`, `0xA551CC` respectively). Classification:
EXACT_SOURCE.
