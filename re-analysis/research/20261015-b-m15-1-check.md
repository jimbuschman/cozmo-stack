## Manager ruling: what comes after an M1-034 skip

After a skip, the backup code carries on as though the skipped data were absent. It then runs the original's
**defined** absent-data path, with its logs and reports:
- **Restore:** "RestoreFromBackup.NoBackup" with RestoreRobotStatus(0,0).
- **The unlock request:** the NoBackup or FailedToParseBackup Info, then a default UnlockStatus.

**This is the "carry on" the standing rule means,** with the same precedent as the loader skips: downstream code sees
the data as absent. The app still gets its answer, and no request is left hanging.

**The skip itself** suppresses only the failure log the original never reaches (`JsonWasSkipped`). Its own visible
stack-channel entry names M1-034 and the owning record. That entry says the downstream absent-data path follows.

No change is needed beyond item 3 of B-M15-1b, which names it in the skip log text.
