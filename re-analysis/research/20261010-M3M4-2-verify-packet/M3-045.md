### A.4 Conclusions for M3-045

1. The shipped imgcodecs registers ten decoders in this order: BMP, HDR, JPEG, WebP (inferred), Sun raster, PxM, TIFF, PNG, JPEG 2000, OpenEXR. A payload starting FF D8 FF is JPEG (no earlier signature overlaps it). A payload that matches nothing returns the empty Mat silently, and so does a payload that matches a decoder whose readHeader or readData fails (A5, A7).
2. The port behaviour (empty Mat for anything not FF D8 FF) therefore differs from the original only for a payload that is a VALID image in one of the nine other formats. For any malformed or random non-JPEG payload the original also returns the empty Mat. HDR, Sun raster, TIFF, JPEG 2000 and OpenEXR are not memory-capable and would go through the temp-file route (A6).
3. Reachability: the engine cannot request 5/6/7 (E7) and has no internal producer (E8). They arrive only if the firmware sends them, which no shipped artifact settles (E9, E10). So a bounded policy (do the signature dispatch of A3/A4, return the empty Mat for every payload whose decoder is not ported, visibly) reproduces the original for every payload except a valid non-JPEG image inside an encoding named JPEG*, for which there is no evidence. Whether to accept that residual is the manager decision (Open questions).
4. live_path stays true for the dispatch (it runs on every image); the non-JPEG branch is reachable only if the firmware sends 5/6/7.

### C.1 Correction to A3 and A.2: the window is always 32 bytes

The window's length is always exactly 32 bytes, the maximum signatureLength. It is the payload followed by 0x20
(space) bytes when the payload is shorter than 32. A3's sentence "the window is the first min(32, size) bytes" is
wrong. The evidence:
- The window is allocated at 0xF78A (`cv::String::allocate(32)`). allocate sets the string's length to the full
  requested length: in libopencv_core.so, `stm.w r4,{r0,r5}` at 0xBFFA4..0xBFFC2.
- It is filled with 0x20 at 0xF78E..0xF792 (`movs r1,#0x20`, then memset).
- Only min(32, payload) bytes are copied in, at 0xF7B8..0xF7C8.

**Consequences** for the A.2 checks, which every decoder applies to that 32-byte window:
- The "window >= len" test of the base check always passes.
- PxM's "size > 2", TIFF's "size > 3" and HDR's "window >= 6" always pass.
- Padding can decide a match. For example, the 2-byte payload "P5" has 0x20 at byte 2, and that passes PxM's isspace
  test.

The windows the probe accepts are exactly the ones these rules accept. Typical shapes:
- RIFF/WEBP with a VP8X chunk;
- a VP8L bitstream that starts 0x2F, reached raw, through RIFF, through a chunk, or through an ALPH chain;
- a VP8 key frame with 9D 01 2A, through the same routes.

A short payload padded with 0x20 can be accepted. One example is a raw payload of 1 to 31 bytes that starts with 0x2F.

### C.4 Naming and readHeader

Decoder 4 is **WebP, by evidence**, which replaces A.2 note (a):
- Its vtable's typeinfo, 0x1725B4 -> 0x172614, has the name 0x172618 -> 0xCE2D8, "N2cv11WebPDecoderE".
- The probe tests the tags RIFF, WEBP, VP8X, ALPH, "VP8 " and VP8L.

**readHeader** (vtable address point 0x1725B8 + 0x18 = 0x1725D0, which points to 0x1A5E4):
- It copies m_buf when the buffer is in memory, at 0x1A5FC..0x1A684. Otherwise it reads the file with
  fopen/fseek/ftell/fread at 0x1A6C6..0x1A71C.
- It then calls the same probe with size 0x20 on the real buffer (0x1A686..0x1A690). A nonzero status returns false.
- On success it sets width and height, and type CV_8UC4 (has_alpha) or CV_8UC3, at 0x1A69A..0x1A6B6.

For a payload under 32 bytes, that probe reads past the end of the buffer into heap contents. **Its outcome is
UNKNOWN** and cannot be settled from the shipped files.

readData (slot +0x1C, 0x1A730) and the libwebp decode were not read: RECOVERABLE_GAP, relevant only if WebP is ported.

Authority 6, a cross-check only: the structure matches an older libwebp's WebPGetFeaturesInternal -> GetFeatures ->
ParseHeadersInternal -> VP8GetInfo/VP8LGetInfo. The version was not pinned.
