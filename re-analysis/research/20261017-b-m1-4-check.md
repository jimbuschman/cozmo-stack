## The 0x588190 name order

- Container: `std::__ndk1::unordered_map<std::string, Anki::Cozmo::Animation>`. GetAnimationNames (0x00588190..
  0x0058826A) walks the node list from map+8 (0x005881AC) via node->next (0x00588262/0x00588266), skips
  `_PROCEDURAL_` (0x005881E6, 0x0058820A..0x0058821C, memcmp 0x00588222), appends in list order.
- Hash: 0x00587E70 → 0x00514EF8 → libc++ 32-bit murmur2 (0x005198E0..0x00519958, m=0x5BD1E995).
- Insert (AddAnimation 0x00587E4C..0x0058802E): find first (0x00587E56), an existing name keeps the old one (bne
  0x0058802A); bucket `h & (bc-1)` for power-of-two bc else `h % bc` (0x00587E7A..0x00587E94); grow when
  (size+1) > bc*mlf (0x00587F54..0x00587F7E) to max(2*bc | (bc<3 || !pow2), ceil((size+1)/mlf)) (0x00587F80..
  0x00587FB2), libc++ rehash (PLT 0x004AE62C); link rules 0x00587FD2..0x0058801E. Constructor sets mlf 1.0
  (0x00587CAC) and inserts `_PROCEDURAL_` first (0x00587CB2).
- Insertion order is not fixed by the binary: Define calls under loader+0x26C mutex (0x0052147A..0x00521490,
  0x00521580..0x00521592) from up to three DispatchWorkers plus the loader thread (Process 0x00521AFC..0x00521C0C;
  X9 G3a HARDWARE_ONLY), file list in readdir order (X9 G2b, 0x00802CF8..0x00802FF6, HARDWARE_ONLY).
- **Answer:** the native order is not one fixed sequence (readdir + thread interleaving). Given an insertion sequence
  it is exactly computable by libc++ emulation. Either way it needs an operator decision (M11-047 style). No engine code
  reads the payload or its order (OV126 routine 6); it matters only for API delivery.
