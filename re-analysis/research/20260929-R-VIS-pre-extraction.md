## Part 2, item 6 (M11-017 overhead edges: Detect, GroundPlaneROI, the four MapComponent entry points)

All addresses are `libcozmoEngine.so` (Thumb), read with capstone unless a row says otherwise.

**Method and findings that change the record.**
- The OpenCV libraries are Thumb: `libopencv_imgproc.so` has 367 of 367 dynamic function symbols with the odd (Thumb) bit, `libopencv_core.so` 1693 of 1693.
- The manifest record and the approved inventory row (line 41 of `inventory/M11-vision.md`) still say "not read". Everything below is read. Two things in the record's evidence are wrong or incomplete: **the clear region is not a triangle to the robot (row 41)** and **the 6.00001 threshold is on a squared length (row 40)**.
- **Detect return value.** Detect returns `Anki::Result`. It returns 1 only when the lift-pose lookup fails (0x006ac4de `movs r7,#1`). Every other exit returns 0 (0x006ad506 `movs r7,#0`), including the "frame abandoned" exits.
- **Which path is live.** The image is colour or grey (row 3). Inventory M11-033 says the shipped camera is grey, so the grey path is the expected live one. Both paths are identical in algorithm and constants except channel count, so both are cited.
- **Naming.** Detect's local names are the extractor's. Fields such as the chain kind byte are unnamed in the binary.
- **Terms.** `ROI` = GroundPlaneROI. `H` = `VisionPoseData+0x7c`, a 3x3 float matrix mapping robot ground (x,y,1) to image pixels. Ground coordinates are mm in the robot frame. Quad corner order is TL(0), BL(1), TR(2), BR(3); stride 8 bytes for 2D and 12 bytes for 3D. `frame` = OverheadEdgeFrame: `+0` u32 timestamp, `+4` byte flag, `+8` Quad2f (32 bytes), `+0x28` begin / `+0x2C` end / `+0x30` cap of a vector of chains. A chain is 16 bytes: a vector of points (begin/end/cap) plus a kind byte at `+0xC`. A point is 20 bytes: x, y, then 3 floats of response.

## Part 1, items 1 to 3 (M11-013 ObjectID and unconnected cubes, M11-004 FindLocatedObjectHelper, M11-007 PoseState)

Everything is read from `resources/lib/armeabi-v7a/libcozmoEngine.so` (Thumb-2); the OpenCV libraries were not opened. Addresses are virtual addresses. Calls into the library's own exports go through 12-byte PLT stubs (`0x4a....` / `0x4b....`). Arm-mode veneers are `bx pc; ldr ip,[pc]; add pc,ip,pc`: `0x8cab5c` reaches PLT `0x4a55f0` (`ObjectID::Set()`), `0x8cad0c` reaches `0x4a700c` (`MarkObjectUnknown`), `0x8cad1c` reaches `0x4a7024` (`BroadcastObjectPoseStateChanged`), `0x8ccb7c` reaches `0x4a7174` (`MarkObjectDirty`).

**Conventions derived and checked.**
- **Object layout** (offsets from the `ObservableObject*`): `+0x14` is the `ObjectID` object and `+0x18` its integer value. `ObjectID::Set()` at `0x008412D8` does `ldr r2,[counter]; str r3(r2+1),[counter]; str r2,[r0,#4]`; the counter is `Anki::ObjectID::UniqueIDCounter` (GOT slot `0x103fe30`). `ObservableObject::SetPose` at `0x004EF5A8` writes `strb r7,[sl,#0x24]`, so `+0x24` is the PoseState byte. `+0x1c` is the observation timestamp (CreateObjectsFromMarkers writes it at `0x006255AC`). `+0x40` is ActiveID and `+0x44` FactoryID (the `ActiveCube(ObjectType)` ctor writes -1 to `+0x40` at `0x004E0C4C` and 0 to `+0x44` at `0x004E0C58`). `+0x48` is the family and `+0x4c` the type.
- **PoseState** (`unity/scripts/csharp/Anki/PoseState.cs`, `EnumToString` table at `0x007982B8`): Invalid=0, Known=1, Dirty=2.
- **ObservableObject virtual slots** (offsets from the subobject's vptr, read in the ActiveCube vtable `0x101CD24` and the Charger vtable): `+0x00` Clone, `+0x0c` IsActive, `+0x18` CanBeUsedForLocalization, `+0x24` `ObservableObject::SetID()`, `+0x28` SetPose, `+0x30`/`+0x34` match tolerances, `+0x5c` IsUnique. ### Contradictions, weak evidence, open questions (items 9 and 10)

- **Contradictions:**
  1. **Row V3 of `M11-vision.md` (line 123), the M11-033 row (line 57), and the `fidelity_manifest.json` evidence line 7072** say `Update(PoseData, ImageCache)` "requires the pose data and image present" (guards 0x006B4D66/0x006B4D70). The bytes there are `ldrb.w r0,[fp,#0x58]` (the VisionSystem init flag) and `ldr.w r0,[fp,#0x64]` (the VisionSystem camera-calibration pointer). Neither is a pose or image test. The failure path is the `NotReady` warning and return 1.
  2. **M11-040 `unresolved`** ("the stack uses a single-in-flight managed stand-in"): the original is a **two-slot latest-wins mailbox** (one pending "next" slot, one "current" slot) polled every 2 ms, and it discards a frame that arrived while one was in flight (rows 14 and 20). "Single-in-flight" is consistent only for the processing itself; the drop and discard rules are described nowhere in the record.
  3. **Policy-review row M11-012** ("the code site testing it was not found") is superseded: the site is 0x006B4D66..0x006B4FFC. Its provenance text ("used only when the operator asks with --nominal") is about the C# and is outside what was read.
- **Weak evidence:**
  - M11-040's evidence ("SetNextImage 0x00652B04; Processor 0x00651F08") proves two function entry points only. It does not prove the mailbox, drop rule, lock, poll interval or result path, and must not keep any EXACT_SOURCE claim as written.
  - M11-012's evidence is empty although the record claims "the live path reads the robot own calibration and fails closed without it". The gate is now supported by rows 1 and 3 to 5, but "reads the robot's own calibration" rests on row 6, only partly traced.
  - M11-038 (CheckMailbox 0x006B2AD4) is now readable (row 22, and Part 1 item 5c), but it is a separate record.
- **Open questions:**
  1. Who writes VC+0x48 (SetNextImage "enabled") and VC+0x4B (paused)? VC+0x48 gates every frame (row 7); if it stays 0, `SetNextImage` accepts nothing. No store to either byte was found: `0x006500A8..0x00658400` was searched for stores and `add ..,#0x48/#0x4B` forms, and the whole `.text` was scanned for `str*/stm*` to `[reg,#0x44..0x48]` and `strb [reg,#0x48]`, checking every hit's enclosing exported symbol; none is a VisionComponent writer.   2. The shipped config value for `PerformanceLogging.DropStatsWindowLength_sec` (key at 0x00650DEE/0x00650E02) was not located.
  3. The `UpdateAllResults` handler bodies (`UpdateVisionMarkers` etc.) and the `RobotProcessedImage` field layout were not read; they belong to other M11 records or to CLAD.

- **Contradictions** with M11-037 and inventory C3.2 (`M11-vision.md:1068-1070`): both say `Camera::AddOccluder` is called "with the transform z scale".
