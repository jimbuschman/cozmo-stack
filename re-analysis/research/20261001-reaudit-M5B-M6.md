## M6-wwise-bank

### `M6-003` — DEFECT

> **Current text:** “IMA ADPCM exactly: header predictor is sample 0, 63 nibbles, diff ((2n+1)*step)>>3, interleaved int16, 64 frames per block.”

Decoder `0x00A7A194..0x00A7A3C4`, the 89-entry i16 step table at `0x00FFD650`, the 16-entry i16 index table at `0x00FFD708`, and the three callers confirm the claimed predictor-first, 63-nibble, diff, saturation, channel-half and interleave arithmetic. The shipped mono/stereo samples therefore decode correctly.

The complete gate does not hold. The current manifest evidence and correction C4 explicitly say the native source gates only on format tag 2 at `0x00A72704` and `0x00A73B2C`, and that decoder `0x00A7A194` is channel-count generic: each caller loops over channels, advances input by `0x24`, and passes `channels*2` as the output stride (`0x00A72618`, `0x00A73EA0`, `0x00A74100`). HEAD still throws unless `channels is 1 or 2` at `WwiseAdpcm.cs:52-53`. Both live consumers reach that rejection (`WwiseAudioSource.cs:518`, `WwiseVoiceSources.cs:246`). It also clamps the header's initial step-index byte at `WwiseAdpcm.cs:76`; correction C4 records that this defensive clamp has no native counterpart. Those paths are unreachable in the 227 shipped ADPCM files, but “unreachable in current assets” does not make the implementation source-exact, especially when the record's own evidence claims the absent gate.

The arithmetic tests use native constants or fixed shipped samples and are not circular. The supposed gate test is insufficient: `WhatIsDecodableIsDecidedInExactlyOnePlace` checks only mono and stereo and asserts `WwiseMedia.IsDecodable`; it never calls `Decode` with more than two channels, so it cannot see the contradictory later gate. The record is therefore **DEFECT**, not 2/2 clean.

### `M6-019` — HOLDS

> **Current text:** “The STMG state-manager reader (0x9B0B14): the threshold, max voices, the two group tables and the 37-parameter table.”

Reader `0x009B0B14` consumes threshold f32, u16 max voices, state groups, switch groups with u8 flags/12-byte items, then 37 packed 21-byte parameter entries with f32 values/ramps and u8 built-in. `WwiseBank.Parse` dispatches the shipped `STMG` chunk to `WwiseStmg.Parse`; `WwiseSoundLibrary.Stmg`, the RTPC store and playback limiter consume that same parsed object. `WwiseStmg.cs` preserves byte widths/order and rejects truncation rather than guessing. The shipped `Init.bnk` offsets/counts/defaults (including 1.0f=`0x3F800000`) reparse identically.

`AnStmgChunkIsReadInTheRuntimeFieldOrder` uses hand-built source-shaped bytes, so it is a non-circular direct-parser test. `TheShippedStmgTableHoldsTheRecoveredDefaults` uses the real bank, but returns early when the assets are absent. Neither starts production Wwise construction and observes the downstream defaults/max-voice consumers. The code claim holds, but this is a **test-entry gap** (and an asset-skip gap), not end-to-end proof.
