## Item 1. The per-voice bus and connection creation

All addresses are ELF VAs in `resources/lib/armeabi-v7a/libcozmoEngine.so` (ARM mode), each disassembled with capstone. The Ghidra decomps under `re-analysis/decomp/` were used only to navigate. The C# was read only to see that `WwisePlaybackBridge.LinkVoiceA42DEC` is an unbuilt seam.

### Headline

- **Where.** The voice's mix-bus connections are created in `0xA42DEC(voice, pbi)`. It is called from the end of `0xA4304C` (`0xA43178 bl 0xA42DEC`) and, for deferred voices, from `0xA431A8` (`0xA43248 b 0xA42DEC`). It calls `0xA42C60`, which calls `0xA4C280`, which builds the connection. That is C21's missing "link" body.
- **List and object.** The connection list at `voice+0x28` holds 0x70-byte connection objects. `voice+0x24` is their count. Each object's `+0x30` is the bus line ("VPL") it feeds, and `+0x48/+0x4C` is a 64-bit output-device id.
- **Gains.** No gain is passed at creation. The constructor sets the four floats `conn+8..+0x17` to 1.0f and leaves the rest zero. Gains come from the existing per-frame refresh (`0xA4BE6C`, M6-012 rows 2.5/2.6).
- **Target bus.** It is `pbi+0xE0 -> vt+0x88()`: the node's own output bus, or its parent's, with buses that need no instance collapsed upward. When there is no bus, a default main-device bus is used.

### Sequence for a Cozmo Sound Play

1. **Voice creation.** Perform runs `0x9D3C98` (`0x9AFA7C`), then `0x9D3644`, then `0xA4304C`. `0xA4304C` allocates the voice, runs `0xA54650` and `0xA548B8`, and calls `AddSrc(voice, pbi, 1)`.
2. **Immediate branch.** If `AddSrc` returns 1, `0xA42DEC(voice, pbi)` runs at once and its result is the return value of `0xA4304C`.
3. **Deferred branch.** If `AddSrc` returns 0x3F (source not ready), the voice is only queued. `0x9D3864` later calls `0xA431A8`, and that reaches `0xA42DEC` once `0xA544BC` returns 1.
4. **Inside `0xA42DEC`.** Init `0xA54A30`, once. Per output device: `0xA42C60`, then find or create the bus line, then `0xA4C280`, then the constructor `0xA6F90C`, then `0xA4F664` (add the input to the bus). Then sorted insertion into the live-voice list.
5. **Rendering.** LEngine `0xA57FF8` (`0x9AFA90`) runs in the same Perform, after the drain.

## Item 7. The Sound `PlayInternal` special branch, PBI `+0x1E4` / `+0x14C` / `+0x1F8`, `0x9BC90C`, `params+0x14` and the `params+0x28..+0x6B` block

All native addresses are ELF vaddrs in `libcozmoEngine.so`, in ARM mode. PLT hop: `0x4D6778` is a PLT stub whose GOT slot `0x1050FB4` has an `R_ARM_JUMP_SLOT` reloc for `powf`; `0x4D37F0` is the same kind of stub for `memcpy`, via slot `0x104FFDC`. No branch veneers were needed on this item's paths.

### Short answers

1. **The branch is a MIDI note-on hook.** The four bytes `params+0x84..+0x87` are status, channel, note and velocity. The branch is taken for a note-on (status `0x90`, velocity non-zero). It publishes two RTPC values and registers the Sound node on the note-state (`params+0x88`) for the later note-off. It then plays the Sound now only if the inherited "play on" property (property 46) equals 1; otherwise the branch returns `0x52`. **The bridge report's row 2a.4 is wrong:** when `0x9EE230` returns 1, the branch falls into the normal path (`0xA1D5D4 beq 0xA1D464`). It does not skip it.
2. **PBI `+0x1E4` is the whole 4-byte MIDI event dword,** not one byte.
3. **PBI `+0x14C` is `params+4`,** the play target: the action's node on the Play path, or the holder's MIDI target on the MIDI path. Layer copies it down unchanged.
4. **PBI `+0x1F8` is a frame-limit word.** The base PBI constructor stores -1, meaning no limit. Only the derived music PBI class can set a lower limit.
5. **`0x9BC90C` is the constructor of the PBI parameter-context sub-object at `pbi+0xC`.**
6. **`params+0x14` has no writer and no reader on any path read.** In `params+0x28..+0x6B`, only `+0x28` is initialised by the Play, MIDI and music/switch builders. The event-post builder `0xA2E494` and music builder `0xA62ED4` copy 0x48 bytes from their own argument. The block is copied into `pbi+0x170`, and no reader was found.

## Items 2 and 3. `0x9BEB30`, `node->vt+0x90`, `0xA00618`, and `0x9CD340`

Read-only. Every address is an ELF VA in `resources/lib/armeabi-v7a/libcozmoEngine.so`, ARM mode, disassembled with capstone. The bank censuses below are authority 3 (bank bytes in `re-analysis/obb/sound_meta/*.bnk`), run with the extractor's own parsers, not the repo C#. All other calls are direct `bl`; no veneers were found on these paths.

### Headline findings (read first)

1. **`node->vt+0x90` is the playback-limit (max-instances) walker.** It is not inert for the shipped data, and no record covers it.
   - All five node classes share one body, `0x9ED2CC`. The output-bus class has its own, `0x9C4F30`.
   - Bank census: in Cozmo.bnk, 1872 of 2231 Sounds sit under actor-mixer 62050212, which has max instances 1, global, kill-oldest. A further 11 sit under 66225135 (max 5, global). All 14 UI.bnk Sounds sit under 47220736 (max 2, global).
   - In SFX.bnk, 101 Sounds sit under one or more limiters (615722439 max 5 per object; 675247210 max 1 global; seven Sounds max 1; one Sound max 50).
   - A second Play under such a mixer can stop the first, or itself fail with return 2 (table 2B).
2. **`0x9BEB30` is not a "parameter/source init".** It never touches a source. It initialises the context at `pbi+0xC` (pbi = PBI object base): initial pan values, the first CalcEffectiveParams call, and the below-volume-threshold test. CalcEffectiveParams first runs here, before vt+0x90 (via the thunk `0xA000E0` to `0x9FFAD4`). Result 1 is required and holds on the shipped Sound path unless the effective volume is at or below the STMG threshold.
3. **`0xA00618`** is a loop-count and init-flag step. Its path-start half is unreachable in the shipped data.
4. **`0x9CD340` is a RIFF/WAVE chunk parser, not a stream reader.** `pbi+0x158..+0x163` is a 12-byte Wwise `AkAudioFormat`: the sample rate word (fmt+4), then the channel-config word (fmt+0x14), then a packed bitfield. The bank media confirm this (table 3B). The writer of `pbi+0x1DC/+0x1E0` (the media pointer and size that `0xA01E24` tests) was in no record: it is `0xA0285C` to `0xA1EC54`.

### Contradictions, weak evidence, open questions (items 2 and 3)

- **Existing records contradicted by the source:**
  - **M6-025 B7 / bridge 2b.3:** the block passed to `vt+0x90` is not "a 0x20-byte block {params+0x70?, params+0x1ec, ...}".   - **M6-025 B7 / bridge 2b.2 label "PBI parameter/source init":** contradicted; `0x9BEB30` touches no source (A1 to A11).
  - **Bridge 2c.11 / M6-025 B6** ("`pbi+0x15C/0x15D` set from `params+0x10/+0x11`-like bytes"): contradicted. `0xA001F0` stores zero. The value is the 0x00004101 default at `0xA00338..0xA00374` (E3).
  - **M6-025 B12 / bridge 5.2 / Item 7.8** ("`0x9CD340` ... internals RECOVERABLE_GAP", "the media-format/stream reader"): it is a RIFF/WAVE chunk walker (D1 to D9). The refinement rule is in E4.
  - **Bridge Item 7.9 / M6 residual "`0x9BC90C` is the RTPC-key init":** `0x9BC90C` is the context (pbi+0xC) ctor; it calls `0xA19CDC`, `0x9E8728` and the node's vt+8 (AddRef-like at `0x9BCA30..0x9BCA38`), sets the flag bytes (A2), and stores `this[0xB8] = 101.0` (`0x9BCA40`).
- **Evidence too weak to keep the status:**
  - **M6-025 B7** (EXACT_SOURCE, claims the whole path `0xA379D8` to `0xA0067C`) omits C6 (a) to (h), the whole limiter and its shipped-data reach (B4 to B14), the volume-threshold reject (A9 to A11) and the pan init (A4 to A7). Those change what plays. A record owning this path needs them added before it is settled.
  - **M6-025 B9** (CalcEffectiveParams): the body is read, but the record does not say it is first called from `0x9BEB30`'s L70 (A8), before vt+0x90.
  - **M6-022 / V7-b** cite the global dword `0x108DE78` as a counter. It is the base of the global PBI list G (C6 h): count at `+0x48`, tail `+0x4C`, head `+0x50`.
  - **M6 line 847** ("the dB to linear store is not read"): now read (A10).
- **Open questions:**
  1. The limiter changes audible behaviour on shipped data (headline 1, B14). Does it become a new M6 record, or extend M6-025? Its stop-with-fade tail (B11), the ordering rule (B12), the per-object map (B13), and the global check `0xA376C0`/`0xA37880` (B15) are unread and need a second pass before an implementer can reproduce it.
  2. The 348 Cozmo.bnk Sounds with an empty chain: the parent-id walk found no limiter above them. If any of their parents are in another bank, the chain census would change; parents were not resolved across banks beyond the global id map.
  3. Who fills `params+0x108` (the array `0xA01918` registers)? On the Sound path it is zero from `0xA62A1C`. The container PlayInternals may fill it.
  4. `pbi+0xE4` (`this+0xD8`): no reader traced.
  5. The tie keys `pbi+0x1C4/+0x1C8` and the sort direction (B12) were only partly read.
  6. If a 3D-positioned or path node is ever to be played (none in shipped data), `0x9BE898`, `0x9BC66C`, `0xA11F98`, `0x9FF0D8` and `0x9FED00` need reading.

### 3. What is passed down, and answers to the open questions of earlier reports

- **`params` is passed by reference (RanSeq) or by stack copy L (Switch, Layer).** The fields `+4` (instigator), `+8` (gameObj), `+0xC`, `+0x10`, `+0x24`, `+0x74`, `+0x7C`, `+0x84..` and `+0x128` bits 0-4 are propagated. The only node-specific things added on the way to a Sound are: the path stack `params+0x28` (count), `+0x2C..+0x6B` (32 u16 indices) and `+0x6C` (bitmask), written by RanSeq only (R9, R14, R15); the accumulated node-parameter block `+0x8C..+0xE7` and vectors `+0xE8`, `+0x108`, written by Layer, and by Switch with more than 1 node (C1); and for a continuous RanSeq, `params[0]=1`, `params+4=this` and `params+0x78` (R13).
- **`20260929-B-M6b-3-residuals.md` open question 2** (is `params+0x28..+0x6B` filled by the container PlayInternals?): yes, by RanSeq only (R9, R14, R15). Switch and Layer only copy the block (S10, L5). The block is not zeroed: only `params+0x28` (count, 0) and `+0x6C` (mask, 0) are initialised at `0xA62B7C` and `0xA62A88`. Entries at `+0x2C..+0x6B` beyond `count` are stack garbage on every path. Every reader found uses `count` and the mask (`0x9EE954`); none was found that reads an entry at index >= count. The wholesale `memcpy` of 0x44 bytes to `pbi+0x170` (`0xA00344/0xA0035C/0xA00380`, from the residuals report) therefore copies uninitialised bytes on the Sound path, both for a Sound played directly and for a Sound reached through a RanSeq, whose used prefix is `count` entries.
- **`params+0x14`:** not written (`0xA62A1C`), not read (`0xA000E8`, `0xA379D8`, `0xA1D448`, `0x9F12E0`, `0xA02494`), and skipped by both the Switch and Layer L copies (no copy of word `+0x14` in `0xA2C9B0..0xA2CA20` or `0x9D092C..0x9D09A0`). This supports dropping it. It does not prove it is unused: all container-body call sites found were read, but the continuous-only bodies `0x9E8FCC/0x9E91F8` were not.
- **Open question 4 of that report** (`params+0x70`, `params+0x7C` hardcoded 0): no PlayInternal body here writes `+0x70` or `+0x7C`. Switch and Layer only copy them (S10, L5); RanSeq writes neither. So on this path `+0x7C` stays 0 and `+0x70` stays 0 (`0xA62BD0`), with one caveat: continuous and delayed paths (`0x9F12E0` positive-delay branch writes `params+0x74` only) were not exhaustively searched for `+0x7C`/`+0x70` stores.

### 4. Contradictions with existing records, rows or code

1. **Bridge extraction (`20260929-B-M6b-3-bridge-extraction.md`) rows 2b.1 and 2c.2** say `node->vt+0x14(node, node, ...)` and that the `0xA000E8` ctor's `param_3` is the target node. From `0xA37CA0..0xA37CC8`, `this` is `[params+4]` (the instigator) and `r1` is `r5`, the node that received `PlayInternal` (`mov r1,r5`; r5 = arg0 of `0xA379D8`). `0xA02EC8` passes that r1 on as the ctor's second argument, and `0xA000E8` passes it to `0x9BC90C` (`0xA00144`). So the **Sound** is the ctor's node argument and the **instigator** (`params+4`, stored at `pbi+0x14C`) is the object whose `vt+0x14` runs. For a Sound played directly the two are the same. For a Sound reached through a RanSeq (R11) they differ: `vt+0x14` is the RanSeq's `0xA0B22C` (picks ContinuousPBI on `params[0]==1`), whereas other classes use `0xA02EC8`. This affects any model that calls the creator on the Sound.
2. **`20260929-M9-013-014-midi-routing-velocity-extraction.md` and `20260929-M9-leftovers-extraction.md`** (row 15: "`ctx+0x84`, which is what `0x009D0758` reads (`ldrb r4,[fp,#0x84]` at `0x009D0774`)"): at `0x9D0774` `fp` is `this` (`0x9D075C mov fp,r0`), so that read is the container's own `+0x84` flag, not `params+0x84`. The params MIDI status is read per child on the L copy (`0x9D085C ldrb r3,[sp,#0x110]`, `0x9D0CA0`) and inside `0xA024B8` (`0xA024CC`).
3. **Inventory gapA 4.1** lists `0xA2D054` as RECOVERABLE_GAP. It is read (S6): in step mode it returns 1 and plays nothing.
4. **Inventory gapA 3.5** says the playable retry applies in general. For playlist length 1 it does not apply (R3, `0xA0A654..0xA0A684`): no `vt+0x48` check, no state access.
5. **Bridge extraction Item 1 row 1.8 / inventory C21 B2** treat `0xA667D0` as a PlayInternal body. It is `mov r0,#0; bx lr` (A1).
6. **`20260929-B-M6b-3-residuals.md` "Likely the node's own `PlayInternal` fills the block for container nodes":** true for RanSeq only, and only the count, one bit and one u16 per level (R9).

### 5. Weak evidence

- Inventory C21/M6-025 B2, "the `+0x128` PlayInternal per shipped class", is EXACT_SOURCE only for the vtable and slot mapping (re-verified above). It carries no evidence about what the bodies do.
- Switch selection (`0xA347A8`): only the group hash, the chain walk, and the default fallback (`0xA348C0`) are read. The key-level precedence is not.
- Switch last-switch state (`0xA0CCF8/0xA0CD78`): the compare and the counter are read; the store and load bodies are not. It has no effect on shipped data because all per-node bit3 flags are 0 (S11).
- `this+0x92` bit0 = "was played" is inferred from a single destructor read.
- The census tool is a copy of an earlier session's script (`nodes.py`/`bnk.py` re-pointed at `re-analysis/obb/sound_meta/*.bnk`). Run against the repo banks it parsed all 2886 nodes (2360 Sound, 468 RanSeq, 31 ActorMixer, 21 Switch, 6 Layer) with 0 leftover bytes.

### 6. Open questions

1. Are the Layer `0x9D0F3C` validation path (L2) and the Switch continuous branch (S4, S14) needed? Shipped data has `cont=0` in every Switch and Layer, and no Switch or Layer is a child of a RanSeq. To model them, read `0x9D0F3C..0x9D1100`, `0x9E8940`, `0x9E8FCC`, `0x9E8F10`, `0x9E91F8`, `0xA04EDC`, `vt+0x98`/`vt+0x9c`. Otherwise mark them not exercised.
2. The layer/blend records and the path-stack semantic: `0x9EE954` (R8) and the `+0x6C` mask sense (set = continuation level, clear = step level) need `0x9EE9C4..0x9EEA5C` read fully for a continuous-mode model.
