## Per-record results

### M11-001 — HOLDS

The extracted 598 x 1024 byte library and the label/code/reorder/orientation arrays match `0x00C9BCA8`, `0x00DC6CA8`, `0x00DC7154`, `0x00DC73AC` and `0x00DC7D0C`; `VisionMarker::Extract` consumes those tables at `0x008A0130..0x008A018A`. `MarkerLibrary.cs:69-150` parses the extractor's byte-for-byte blob and `MarkerLibrary.cs:197-203` places it on the live decoder path. The extraction tool pins the complete blob hash; `VisionTests.cs:30-59` checks source-derived shape/table samples, although the test itself is weaker than the extractor's complete SHA-256 check.

### M11-002 — FAILS

1. **The nearest-neighbour search has the wrong initial bound.** The engine copies the caller's threshold into the best-distance output at `0x008C093E`/`0x008C098A`, then only accepts a row when its distance is strictly less at `0x008C0B72..0x008C0BA0`. `MarkerLibrary.cs:273` instead seeds both distances with `int.MaxValue`. A nearest row at or above the threshold can therefore become the C# winner and participate in second-place ambiguity processing, while the engine retains no winner. The later `distance >= 50` rejection does not repair all observable result/reason and second-candidate behavior.
2. **The tests miss that gate.** `VisionTests.cs:137-183` independently pins rounding, integer ambiguity averaging and min/max normalization, but no test supplies a nearest distance at the threshold or above. The rendered-row tests use near-zero distances and cannot distinguish the two initializations.

The table lookup and final label/distance/149/150 gates at `0x008A00F8..0x008A018A` otherwise match `MarkerLibrary.cs:355-372`.

### M11-003 — PARTIAL

The cube sizes, marker sizes, canonical-corner order, code map and the nine camera-matrix words do match `0x004E4C8C`, the four `BlockFaceDef_t` tables, `0x004DD7D8..0x004DD81A`, and `0x00C4A854`. In particular, `CameraModel.cs:24-27` stores the exact binary32 matrix values widened to double.

The face transforms are not bit-exact. `Block::AddFace` materializes binary32 `-pi/2 = 0xBFC90FDB`, `+pi/2 = 0x3FC90FDB`, `pi = 0x40490FDB`, `2pi/3 = 0x40060A92`, and axis component `0x3F13CD3A` at `0x004E5442`, `0x004E54EA`, `0x004E557C`, `0x004E5490/0x004E55D6`. `CubeGeometry.cs:79,84-91` instead keeps `Math.PI` and full-precision double `0.5773502691896258` / `2.0943951023931953`, and `CubeGeometry.cs:121-124` performs the live pose construction in double. These are different values before any pose composition. `VisionTests.cs:1408-1428` checks canonical corner order and table reordering, not the native face-transform bit patterns or the resulting poses.

### M11-005 — HOLDS

`CornerRefinement.cs:31-61,148-192,200-372` now follows the source's `RefineCorners` order (`0x0089FD98..0x0089FFEA`), uses binary32 samples/Jacobian/residuals, forms `J'J`, runs natural-order Cholesky with the `FLT_EPSILON` pivot flag from `0x0088DE68..0x0088E138`, applies `H = H * inv(U)`, and preserves the source's surprising `flag != 0` accept branch at `0x008C6418`. ### M11-006 — FAILS

Both non-integral tolerances are rounded decimal substitutions. The engine constructs the cluster angle as `0x3DB2B8C3` at `0x00625498..0x006254E0` and the flat clamp as `0x3EB2B8C2` at `0x00505F10..0x00505F22`. `BlockWorld.cs:480` uses `0.0872665`, which converts to binary32 `0x3DB2B8C7`; `BlockWorld.cs:487` uses `0.349066`, which converts to `0x3EB2B8C7`. The 5.0 mm value is exact and holds.

### M11-008 — PARTIAL

The record's 40-pixel value itself holds: the engine passes `0x42200000` at `0x006220F0`, and `BlockWorld.cs:536,1836-1837` passes exactly 40 on the live unobserved-object path. The whole decision does not: the same native call passes face-normal angle `0x3F490FDB` at `0x006220E2..0x006220EC`, while `BlockWorld.cs:511` supplies decimal `0.785398` (`0x3F490FD8` when converted to binary32), and `ObservableObject.MarkerVisibility` performs the source's binary32 geometry (`0x0087E4A8..0x0087E87C`) in double at `BlockWorld.cs:390-425`. ### M11-019 — FAILS

The engine delocalizes through `Robot::Delocalize` `0x00510A24`, reached from the tread-boundary path at `0x00512B88..0x00512BA6`; that routine moves carried objects at `0x00510CF0`. ### M11-020 — FAILS

The engine calls OpenCV `solve(..., DECOMP_SVD)` at `0x008A6714..0x008A68E0` on the float matrices. `QuadCorners.cs:381-425` explicitly substitutes double normal equations and a hand-written rank-deficient minimum-norm case.
