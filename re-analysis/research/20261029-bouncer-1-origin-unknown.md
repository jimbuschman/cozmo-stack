## Answer

**The face's stored origin comes from the computed robot-history state at the face observation timestamp.** It is not inferred from the face's numeric world coordinates, taken unconditionally from the robot's present origin, or simply inherited from whichever camera object processed the image.

In FaceWorld::AddOrUpdateFace itself, the engine asks RobotStateHistory::ComputeAndInsertStateAt(face.timestamp, ..., interpolate=true), obtains that returned HistRobotState pose's **current root ID**, obtains the corresponding origin object from Robot's PoseOriginList, and parents a copy of the incoming face HeadPose to that origin object. The selected stored FaceEntry gets that resulting pose. Thus the origin lookup is performed when this observation is consumed, against the timestamp-selected computed history state; it is not an independently sampled “current camera origin” value.

Eligibility later compares **current root node identity after ancestry traversal**, not root-ID integers directly. Numeric geometry and ancestry provenance are independent source inputs. An origin identity retained separately from flattened geometry can represent this provenance only if it identifies the exact origin selected by the history lookup and preserves/resolves its later parent relations. A stale captured numeric ID compared directly to a live numeric ID is not the native HasSameRootAs contract. No production origin can be inferred from an identity/flat HeadPose.

## What this establishes about captured-frame metadata

The required source-native identity is **the origin selected by O2-O4**, not any arbitrary processing-time origin. The requested history timestamp is the tracked face's timestamp (copied from its detector image on the established M14 result path), and ComputeStateAt may return an interpolated or otherwise adjusted returned timestamp under its current checked query rules. Root provenance follows the returned HistRobotState, not a separately invented closest-time policy.

The incoming camera/face geometry does not override O4: regardless of which Camera was used to obtain the incoming HeadPose transform, AddOrUpdateFace explicitly attaches its copy to GetOriginByID(historyState.GetRootID()). No additional numeric pose recovery is necessary to establish that ancestry identity. Numeric world coordinates alone contain no tag from which O4's selected root could be recovered.

Native ancestry remains live: the stored HeadPose is parented to an origin object; the later predicate walks that object's current ancestors. If origin A is subsequently parented under origin B, a face parented to A and a current-origin pose rooted in B can share the same root without their originally selected ID being the same. This consequence follows O11's pointer traversal; it is not a proposed C# design. Conversely, equal geometry or a host “current origin” label cannot establish matching root pointers. Any separate provenance representation must preserve those relations to represent the native question faithfully.

This report establishes producer argument, temporal source, copy/reparent/store and predicate. It does not assert that a current C# processingPose/history metadata value already supplies O2's returned-state root, nor that the existing flattened FaceEntry.HeadPose's implicit origin is trustworthy. Those are the manager/builder's independent C# audits. Missing history must remain a defined failed observation with visible diagnostic; no guess of present origin, universal eligibility or new indefinite wait is supported.
