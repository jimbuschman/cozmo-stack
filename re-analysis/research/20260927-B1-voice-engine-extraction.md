# B1 - Voice engine extraction (live render path: sink frame -> Hijack bus output)

Read-only extraction from `resources/lib/armeabi-v7a/libcozmoEngine.so` (3.4.0-1204, ARM mode, statically linked Wwise 2016.2 at 0x0095E540..0x00AE2E40). All addresses are VAs. Disassembly used `re-analysis/tools/arm_disasm.py` (capstone 5.0.7). The Ghidra decomp directory `re-analysis/decomp/libcozmoEngine/` named in the brief is **absent from this clone** (`re-analysis/decomp` does not exist), so every citation below is an instruction in the `.so`.

**Correction to the task's premise.** `0xA57FF8` is not the LEngine body. It is a two-instruction wrapper that calls `0xA57D64` and then tail-calls the render body `0xA44D4C`. `0xA44D4C` is the function that runs the voice pass `0xA44948`, then the bus pass `0xA44C18`, then idle removal. That matches gapD D2.7.

**GOT arithmetic note.** All the runtime-global loads use GOT base `0x104028C` (computed from `0x9AF8C4+0x6909C8` and `0xA44D60+0x5FB52C`, which agree). The slot address is `base + signed_offset`; the value at that slot is a pointer to the global.

**Answer summary (per question).**
1. `0xA57FF8` = wrapper; body `0xA44D4C` is a coherent transliterable loop over a global list, then `0xA44948(arg)` and `0xA44C18(arg)`. The per-voice and per-bus work dispatches through vtables (list below).
2. `0xA44948` walks the global voice list (base `0x108DF54`, head `[0x108DF68]`, next `+0xD0`, state `+0xDC`). Per voice it renders/mixes via `0xA44630`; the DSP is `0xA548C0` (source), `0xA53134` (resampler SetPitch), `0xA52D4C`->`0xA47178` (resampler Execute), then `0xA4FBEC`->`0xA45E9C` (mixer) or the connection device `vt+0x28` (filter/gain). The chaining/stop/destroy tail is `0xA55D04`, `0xA55A84`, `0xA54A30`, `0xA56478`, `vt+0x48`, `0x9D40C4`.
3. `0xA44C18` iterates the global bus array from last to first, `0xA4FEF8` (GetResultingBuffer, which lazily instantiates FX), mixes child buses `0xA4F9E0`, `0xA4F36C` (ReleaseBuffer), then falls into the shared cleanup; FX execute is `0xA4FD84` (slot order, only when state==1).
4. Idle removal = `0xA43F64`, called at `0xA44C6C`. Predicate: destroy when state `+0x1BC != 1` and connections `+0x1C0 == 0`; otherwise clear `+0x1CC` bit0.
5. The four "buses" group members are described in B1-V25..B1-V28; they are sub-manager Perform passes, not audio buses. Their Wwise class names are not recoverable from the binary (no RTTI strings read); behaviour is given.
6. `0xA38420` flushes the queued PBI/parameter notifications; for reason 4 it runs `0x9D3470`, `vt+0x10` (Term), `vt+4` (delete). It is called at `0x9AFA94`, after LEngine and before `tick++`.
7. Frames-per-Perform: `0x9D4778` is `b 0x9EC38C`; `0x9EC38C` is `mov r0,#0; b 0x9EBE6C`. The Perform gate byte is `0x108DAF0` (GOT slot 0x10400BC), the second gate is `0x108DB08` (GOT 0x10400C0), and the third is `0x1052430` (GOT 0x10400C8, `.data` holding 0x00000001). **No writer to any of them was found** (no `movw/movt`, and the only pointer to each is its GOT slot). `0x108DAF0`/`0x108DB08` are `.bss` zero, so the engine always takes the device path `0x9D4778() -> 0x9EBE6C(0)`; the clock-paced branch is dead in 3.4.0-1204. That count is read from the audio device/sink and is HARDWARE_ONLY.
8. The path is transliterable in structure but has behaviour-changing steps with no source in this build: the device frame count `0x9EBE6C`, the sink/thread pacing, and the four group members' Wwise identity. Listed at the end.

## Appendices

### Appendix 1 - `0xA57D64` sub-calls (for B1-V2)
`vt+0x18` (0xA57DD0) on `[r7]`; `vt+0x18` (0xA57E20) on `[sp]`; `vt+0x29c` (0xA57E3C); `vt+0x84` (0xA57E64, 0xA57E9C); `0x593E58` (0xA57E78); `0xA58008` (0xA57EAC, 0xA57EE0) - each `0xA58008` calls `vt+0x98`; `0x9EA66C` (0xA57F38). `0xA58008` is a 3-instruction thunk to `vt+0x98`.

### Appendix 2 - voice-pass per-voice order (for B1-V6..V16)
`state = [voice+0xDC]`. If `state == 1`: `0xA54F1C(voice,&p)`; if `(ret & arg)`: `0xA44630(&p)`, then if `p+0x28 == 0x2E` -> `0xA55CC4(voice,&p)` else `0xA5495C(voice)`; then re-read bus. ## Judgement

The voice engine **can be built exactly in structure**: `0xA57FF8`->`0xA57D64`+`0xA44D4C` is a coherent, transliterable control flow, and the per-voice DSP chain (`0xA44630` -> `0xA548C0` -> `0xA53134` -> `0xA52D4C`->`0xA47178` -> `0xA4FBEC`->`0xA45E9C` / connection `vt+0x28`) is fully addressable with the already-approved M6-004/M6-010/M6-011/M6-012/M6-013/M6-014 records plugging in. It is **not** a single flat routine: it dispatches through vtables (`+0x38`, `+0x3c`, `+0x30`, `+0x28`, `+0x20`, `+0x0c`, `+0x10`, `+0x48`, `+0x98`) and through the FX-slot array, so a transliteration must model those objects. The one genuinely unrecoverable-from-source step is the device frame count `0x9EBE6C(0)` and the audio-thread/sink pacing (HARDWARE_ONLY). The gate bytes `0x108DAF0`/`0x108DB08` are `.bss`-zero and `0x1052430` is `.data` 1, with no writer found, so the shipped engine always takes the device path and `arg=1`; the clock-paced branches are dead in 3.4.0-1204. The four group members' *behaviour* is read; their Wwise class names are not (no RTTI), which is a labelling gap, not a behaviour gap.
