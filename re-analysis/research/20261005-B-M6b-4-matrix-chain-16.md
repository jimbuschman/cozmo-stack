# B-M6b-4 pass 16: connection gain/matrix chain and the bus gain stage - extractor report, UNVERIFIED; manager-condensed

Wwise region 0x95E540..0xAE2E40 is ARM. Notation: cfg word = AkChannelConfig-shaped: byte 0 channel count, bits 8..11 type (1 = standard), bits 12..31 mask (mask bit 3 = LFE). Mono = 0x4101, stereo = 0x3102. P = second argument of 0xA4BC58 = [[voice+0xD4]+0xC]+0xC; its constructor 0x9BC90C is the "ctx" object; P+0xDC = [pbi+0xE8]. conn = the 0x70-byte voice-to-line connection built by 0xA6F90C.

## 0. Findings first
1. Mono to mono is established: the matrix is [1.0,0,0,0] (1x1 in a row padded to 4 floats). It comes from 0xA25FF8 -> tail 0xA2616C b 0xA1F79C -> 0xA1FA50 -> 0xA1FE00 memset -> 0xA1FA64 cmp r4,#1; bls 0xA1FE14 -> 0xA1FE18 str 1.0f,[matrix]. Independent of pan x/y/center and of the flag byte. Also holds for an anonymous mono voice (cfg 0x0001) into a standard mono line. The engine's own A25FF8 and A5975C were run (configs in section 3).
2. The "object in r3" is not an object: a byte 0 or 1. A25FF8's 4th argument (r3) is only copied to ip and passed as r0 to A1F79C (0xA25FFC, 0xA2616A) where it is compared `cmp r1,r0` at 0xA1F800. A5975C and A4D994 set it with ldrb from P+0xB4 or bus+0xA0. The only pointer-like argument is the 4th stack argument, an output-device record, used only by the tail call to 0xA234FC for an ambisonic input (0xA26158..0xA26168); not read on the standard path. The repo's std_hooks() hooks memmove but not PLT memset (0x4D36DC); A25FF8 calls memset at 0xA26130 and 0xA26638, which would run into a zeroed GOT block (extractor's guess at the cause of the earlier failing run).
3. [conn+0x14] and the matrix have a producer in the engine order: 0xA4BC58 (per voice, from V7) -> 0xA5975C -> 0xA25FF8 -> 0xA1F79C. [conn+0x14] = ([conn+0x68] ? 1.0f : [[voice+0x10]+0x34]); for a dry connection that is lin([ctx+0x58]*0.05)*[GO+0x60], the muted-dry gain. The matrix pair is held in the connection descriptor conn+0x18..0x24; "next" [conn+0x20] is written and "prev" [conn+0x24] is read by A45E9C. Nothing in the C# engine order does this: Refresh is called only in RenderLegacyOrder so `_prevMatrix![m]` throws on the first engine-order mix.
4. 0xA5D70C is dead on Cozmo: it delivers a callback of type 0x10 (speaker-volume matrix) through 0xA03DA0, only when [pbi+4]&0x10 is set; Anki's single PostEvent call site (0x8D8D32 blx 0x9a6704; all executable segments scanned, ARM and Thumb) passes flags in {0,1,5,9,13}, so the bit never appears. Same for [bus+0xC0] bit 2, which gates the bus-volume callback block of A4D994: its registrar API stub (0x9A03DC, the only caller of 0x9C7B6C) has no caller and no data reference; registry 0x9C8108 is empty; A4D994 never runs the 0xA4DC8C block.
5. 0xA4D994 touches no samples: it writes bus+0x80/0x84 (prev/next linear gain, 0.99903899 at 0 dB) and the prev/next bus matrices bus+0x3C/0x40. Only caller 0xA4FEF8, after the insert-FX loop 0xA4FD84. The Hijack executes inside that FX loop, so its PCM is taken before A4D994 and is not affected by bus gain or matrix; results matter only to the parent mix 0xA4F9E0 (Master Audio Bus, then device).
6. C# contradicts the binary: the UpdateConnectionGains per-connection loop sets C08/C10 at the wrong time, omits the bit1, bit2 and 3D branches and the matrix copies; MixOutputBus uses the wrong gains and the wrong mixing kernel (section 6).
