# M6-002 Vorbis decoder arithmetic — extractor inventory (pass 3)

Read-only pass. Scope: the five remaining M6-002 build gaps C5/C6 left open. Engine:
`resources/lib/armeabi-v7a/libcozmoEngine.so` (Wwise 2016.2 region is ARM mode). All addresses are VAs.
C5 (`re-analysis/evidence/m6-vorbis/vorbis-arithmetic.md`) and C6 (`.../vorbis-arithmetic-2.md`) are not
re-derived except where contradicted; the reference sources used for comparison are the Tremor-lowmem fork the
engine actually descends from, not libvorbis 1.3.

Scratch: `.scratch/m6-vorbis3/` — `dis2.py`, `makedecode.txt`, `makewords.txt`, `bookunpack.txt`, `decodemap.txt`,

`trig*.py`. Nothing outside `.scratch/` was written.

## Reference match (the fork is identified)

The engine is the **Tremor *lowmem*** fork, not mainline Tremor and not libvorbis 1.3:

- `vorbis_book_unpack` (0x00ABA188) reads `dim=read(4)`, `entries=read(14)`, a **1-bit** lookup type, a 3-bit
  unordered length width, and a `q_seq` bit it discards — i.e. the **ww2ogg packed** codebook form, and the codebook
  struct is the lowmem one (`dec_maxlength/dec_table/dec_nodeb/dec_leafw/dec_type/q_min/q_minp/q_del/q_delp/q_bits/q_pack/q_val`).
- The decoder is `res012.c` / `floor1.c` / `codebook.c` of that fork, and the MDCT is the lowmem
  `mdct_backward(int n, DATA_TYPE *in)` (2 args, in place), not libvorbis's `mdct_backward(lookup*,in,out)`.
- The matching sources are `eulerdisk/tremor-lowmem-zephyr` (BSD-3), files `codebook.c`, `res012.c`, `floor1.c`,
  `mdct.c`, `mdct_lookup.h`. They are used only to interpret the binary; every claim below is anchored to a binary address.

> **Resolution.** C6's "16-bit store vs 32-bit read unreconciled" is not a defect. The builder and the decoder both
> select on `dec_nodeb` (1/2/4) and, for 1/2, on `dec_leafw` (1/2). The 32-bit table is built by the `dec_nodeb==4`

> only one of the five (nodeb,leafw) cases.

## Existing records contradicted by the source

1. **C6 1c, in two parts.** (a) "the `[+0x14]==4` pre-path also writes 8-bit (`strb`, bit7 marker)" is wrong: `0x00AB9718 beq 0x00AB9A0C` leads to a 32-bit allocation and a direct `_make_words` call (0x00AB9A0C..0x00AB9A64), with no byte store. (b) "the builder never writes a 32-bit entry - there is no `str` to the table, only `strh`/`strb`" is wrong: `_make_words` writes 32-bit words (0x00AB950C `str r6,[sl,r3,lsl#2]`, 0x00AB93C0 `str fp,[sl,r3,lsl#3]`), and the `dec_nodeb==4` path passes the real table to it.
2. **C6 1f's apparent contradiction is void.** "For `[+0x14]==4` ... the builder emits an 8-bit table while the decoder's default path reads 32-bit" is not what the code does (see 1). There is no width mismatch: builder and decoder both dispatch on `dec_nodeb` and both use 32-bit for 4.
3. **C6 1b terminology.** `+0x14` is not a "format selector" and `+0x18` is not a "sub-variant"; they are `dec_nodeb` and `dec_leafw`. The values "1 in the ordered path, r3 in the quantized path, 4 when used_entries<=1" are the `_determine_node_bytes` results, not format codes.
4. **C5 3c.** "It allocates at `codebook+0x10` ... and fills it with 16-bit leaf words ... the alternate no-lookup path (`codebook+0x14==4`) builds a byte table." The 16-bit `strh` stores are the `dec_nodeb==2` **repack** (0x00AB97E4, 0x00AB994C); the `==4` path is 32-bit (1c).

## Existing records whose evidence is too weak to keep their status

- **M6-002's provenance line "the decode-table builder 0x00AB96EC (16-bit store vs 32-bit read unreconciled)".** The reconciliation is now read (1a-1k, 5a/5b); rewrite to name `dec_nodeb`/`dec_leafw` and the five table forms, and remove the `+0x14==4` item as a gap (dead for shipped books, 5c).
- **gapG 6.4 "nodeb/leafw come from `(q_bits*dim+8)/8`".** That is only the `leafwidth` input for maptype 1; `dec_nodeb`/`dec_leafw` come from `_determine_node_bytes` (used_entries and leafwidth), read in 1k. Keep the field, extend it.
- **C6 2a/2b** are sound; only the `mdct_lookup` location (.bss 0x0108E648, GOT 0x01040268) was not named.
- **C5 7a** ("read its structure only") stays RECOVERABLE_GAP: the stage order and table addresses are now read (2a-2g), but the per-stage butterfly arithmetic and the trig-table indexing are not.

## Open questions for the manager

1. **The MDCT kernel is still a live RECOVERABLE_GAP.** 2a/2c/2g/2h are settled, but 2d/2e and 2f are not. This is the one remaining M6-002 blocker that is genuinely large.
