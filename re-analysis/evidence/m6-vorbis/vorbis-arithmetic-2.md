# M6-002 Vorbis decoder arithmetic — extractor inventory (pass 2)

Read-only pass. Scope: the seven remaining `M6-002` RECOVERABLE_GAPs left by
`re-analysis/evidence/m6-vorbis/vorbis-arithmetic.md` (correction C5). Engine:
`resources/lib/armeabi-v7a/libcozmoEngine.so` (Wwise region is ARM mode). All addresses are VAs.
C5 is not re-derived; only the items it left open are read.

Scratch (`/scratch/m6-vorbis2/`): `adis.py` (ARM disassembler, start/end), `xref.py`
(word-pattern scan for `b`/`bl` targets), plus dumps `f39d8.txt`, `floor_scan.txt`,
`floor_helper_rest.txt`, `window.txt`, `overlap_rest.txt`, `overlap_tail.txt`,
`bookunpack.txt`, `bookdecode.txt`, `caller_args.txt`. Nothing outside `.scratch/` was written.

Note on tooling: the previous pass's `t.py d` takes a *length*, not an end address, so
`t.py`-generated dumps from C5 must not be re-used as ranges without checking; all ranges
below were produced with `adis.py <start> <end>`.

## Existing records contradicted by the source

1. **C5 rows 3a/3b (M6-002/gapG 6.5) invert the leaf/internal polarity.**
   The walk loops while the entry is **non-negative** (`0x00AB9C44 cmp ip,#0`; `0x00AB9C48 bge 0x00AB9C28`), so internal nodes are `>=0` and leaves are the **bit31-set** entries (`0x00AB9C4C bic ip,ip,#0x80000000`). The scalar decoder does the same (`0x00ABA8B8 cmp r0,#0`; `0x00ABA8BC bge ...`). Row 3a's "if `entry < 0` continue, else stop" and row 3b's "negative entries are internal nodes" are both wrong. The automated test that pins this should assert non-negative = internal.

2. **C5 row 7b / gapG 6.11: "0x00AB39D8 has no decode caller."**
   `0x00AB4E34` tail-branches into it: `0x00AB5A44 b 0x00AB39D8` (bytes `ea ff f7 e3`, target 0x00AB39D8). A word-pattern scan of the whole code segment finds no other reference. So 0x00AB39D8 is the decode MDCT's second half, and the decode output **is** scaled by `2^-24` there.

3. **C5 row 9b: "0x00AB3520 allocates n/2*4*channels and stores per-channel base pointers at [vd+0x14][c]."**
   0x00AB3520 selects the two windows and drives the overlap per channel (it calls 0x00AB5A94 at 0x00AB3664 and memmoves at 0x4D37F0), but performs **no allocation**. The per-channel allocation and the stores to `[dsp+0x14][c]` are in 0x00AB3780 (0x00AB37BC `bl 0x4B3E70`; 0x00AB37D0 `str r5,[r2,r3,lsl#2]`). The record should name 0x00AB3780 for the allocation and 0x00AB3520 for the overlap driver.

## Existing records whose evidence is too weak to keep their status

- **gapG 6.11 (RECOVERABLE_GAP).** Now that the decode scale is found (`2^-24` in the tail continuation), the record should be rewritten: the *mechanism* is EXACT_SOURCE, but the "output is nominally +/-1.0" claim still has no source multiplying floor dB, residue integers and the MDCT into a known nominal range. Keep the nominal-output claim RECOVERABLE_GAP/UNKNOWN rather than upgrading it.
- **gapG 6.8 ("both types call decodev_add").** Correct for types 0 and 1 (they share 0x00AB770C); type 2 calls `decodevv_add` (0x00ABABB8). The wording conflates "the two channels" with "two residue types" and should be corrected.
- **gapG 6.8 "stagebooks[(pw<<3)+s]" (C5 row 4b).** The index is the decoded class digit `partword[ch][pw]`, not the partition number; the byte address is `info+0x08 + class*8 + s` and the cascade gate is `info+0x04[class] & (1<<s)`. The record's `pw` naming must be corrected before it can be settled.
- **C5 row 4a: `ldrb r1,[r1,#0x19]` labelled "grouping".** The byte is used as an index into the codebook array (`fullbooks[byte]`) and the value read is that codebook's `dim`, which then serves as the per-codeword channel count. Whether the field is "grouping" or "groupbook" cannot be told without the residue setup walk (0x00AB63E0's residue section, not in `setup.txt`); the row's field naming is weak.
- **M6-002 row 3c (`_make_decode_table`, RECOVERABLE_GAP).** The widths are now established, but the `+0x14==4` single-entry case still cannot be reconciled, so the record cannot be settled yet.

## Open questions for the manager

1. **`codebook+0x14` domain.** Read 0x00ABA6D0..0x00ABA7A0 to determine what values `+0x14` can take (`1`, `2`, or `4`) and whether `used_entries<=1` ever occurs in a shipped codebook, then decide whether the decoder's 32-bit default path is dead code or a latent defect. The builder has no 32-bit store at all, so the 32-bit path cannot be fed by 0x00AB96EC.
2. **0-window path.** Is any shipped mode's blocksize outside 256..4096 (i.e. 64/128/8192)? If not, record the 0-window as an unexercised branch; if yes, it is a real NULL dereference and the manager must decide whether it is a policy guard or a fidelity gap.
3. **Residue field names.** The residue setup walk is needed to name `info+0x04`, `+0x08`, `+0x18`, `+0x19`, `+0x1A` so that the residue records can say "cascade"/"stagebook"/"groupbook" with a citation instead of the register-level description used above.
4. **M6-002 output-scale claim.** With `2^-24` established on the decode MDCT and no 2^8/2^16 anywhere on the decode path, decide whether M6-002 may claim any nominal output scale, or whether the whole chain (floor dB table x residue integers x MDCT) must stay UNKNOWN.
